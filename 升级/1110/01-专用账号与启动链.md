# 专用账号与启动链 Implementation Plan

> **For agentic workers:** Use `executing-plans` to implement this plan task by task.

**目标：** 让现有 PTOBench 启动路径只把 Pi Agent 切换到 `ptobench-agent`，Broker 和 NPU Worker 继续使用原宿主账号；移除运行时 subordinate UID/GID 发现、映射和清组状态机。

**架构：** 管理员一次性创建锁定的 Agent 账号和共享组，并安装精确 sudoers 规则。Broker 从已验证的 `environments/LOCK.json` 取得规范化的 Python executable 路径；Broker argv 与 sudoers 使用同一固定路径，以 Agent 用户运行 `-I -S` 和固定的 `evaluator/agent_dispatch.py` 参数。隔离模式忽略 Python 环境变量并禁用 `site` 启动钩子，dispatcher 只用标准库读取一次性请求并以 argv 执行 Bubblewrap 命令。sudo 不以 root 身份运行 dispatcher、PTOBench 或 Agent 命令；不增加 setuid 程序或 root helper，也不新增 PTOBench 顶层模块。运行时不从 `PATH` 或 Agent 环境读取 Python 路径。

**唯一运行路径：** 新建的 Pi Agent 一律经固定 dispatcher 以 `ptobench-agent` 身份启动 Bubblewrap。不得保留 Broker UID 直接启动、subordinate UID/GID 映射、setpriv 清组分支、旧 runner 回退或旧 Session 启动兼容；配置未就绪时 fail closed。旧 Session 文件不迁移或恢复为可执行状态。

**Tech Stack：** Python 3 标准库、sudo/sudoers、Linux 用户账户和 POSIX DAC、Bubblewrap。

**Spec：** [`00-overview.md`](00-overview.md)。

## 全局约束

- `ptobench-agent` 的主组是 `ptobench-share`，账号密码锁定且没有交互式 Shell；它没有其他有效或附加组。
- Broker 保持现有 UID 和有效硬件权限，只增加 `ptobench-share` 成员资格。NPU Worker 继续由 Broker UID 启动；Agent 对实际 NPU 设备节点的访问必须由 canary 验证为拒绝。
- sudoers 只允许 Broker 用户以 `ptobench-agent:ptobench-share` 身份运行 `<resolved-locked-python> -I -S <fixed-dispatcher>`；该 Python 路径取自 `environments/LOCK.json` 并解析为规范绝对路径，Broker argv 与生成的 sudoers 必须一致。命令与参数精确匹配，不使用通配符、`SETENV`、root 目标或任意 Shell。命令级 `env_keep = "PTOBENCH_AGENT_LAUNCH_REQUEST"` 取代继承/追加式白名单；实测 dispatcher 环境不含其他调用者变量，且 Request 路径变量从 Bubblewrap/Pi 环境移除。通过 `visudo -cf`、`sudo -n -l`、额外参数负向调用和环境探针检查。
- Request 不含模型凭据，Agent Sandbox 不挂载 launcher request 目录。Plan 01 唯一负责创建 `session_root/agent/` 与 `launcher/`：两者由 Broker 所有、共享组为 `ptobench-share`、mode `2710`；Agent 组只能按已知路径遍历，不能列举、创建、删除或替换目录项。setgid 保证 Broker 创建的 Request 继承共享组。Request 文件由 Broker 所有、共享组可读、mode `0640`、单链接且随机命名；Broker 在子进程退出后删除 Request，并在崩溃恢复时清理残留。Plan 03 只在该父目录下创建 `pi-config/`、`pi-tools/`、`native/`，不修改 `agent/` 权限。并发 Session 测试验证请求不能互相删除或替换。
- UID/GID 在宿主安装时从 `getent` 发现并用于验证；实现代码不固化数字 UID/GID、subordinate range、硬件组或安装目录。
- `agent_launch.prepare()` 的 sudo argv 必须明确为 `sudo -n -u <agent-user> -g <share-group> -- <resolved-locked-python> -I -S <fixed-dispatcher>`；路径由现有环境锁读取并解析，不能使用环境覆盖。sudoers 精确匹配该完整 argv。dispatcher 不接收额外参数，只通过 sudoers 命令限定的 Request 环境变量读取请求。命令测试断言目标身份、固定 argv、隔离 Python 启动选项、拒绝额外参数、有效环境白名单和 fail-closed。
- `sudo` 和 Bubblewrap 都必须从系统可信搜索路径解析到规范真实路径；复用 Plan 01 的 `_trusted_binary()` 检查合同：真实文件是 root-owned 普通文件、不可被组/其他用户写入，所有父目录 root-owned 且不可被组/其他用户写入，并检查 ACL 的有效权限没有额外写授权。发现可写符号链接目标、祖先目录或 ACL 写权限时 fail closed；不能只验证文件本身的 mode。

## Review Focus

1. `sudo` 规则是否确实只运行固定 Python/dispatcher argv，显式指定 Agent 用户与共享组，拒绝附加参数，且最终进程在执行任何请求代码前已是 Agent 用户。
2. Agent 能否从 request、环境变量或 `sudo` 获得 API Key、Broker 身份或任意其他 sudo 命令。
3. Agent 账号/组设置是否会移除 Broker 的现有硬件组，或让 Agent 意外获得硬件访问。

## 管理员预配置模板

在代码修缮前，将下列内容写入独立 sudoers 文件；把 `<broker-user>` 替换为 `id -un` 得到的 Broker 账号，把 `<resolved-locked-python>` 替换为 `environments/LOCK.json` 中 Python executable 的规范化绝对路径，把 `<absolute-checkout>` 替换为 PTOBench 的真实绝对路径。该 Python 路径不是 `/usr/bin/python3` 常量，也不从运行时 `PATH` 选择。即使 dispatcher 文件尚未创建，也可先用 `visudo -cf` 检查语法，并用 `sudo -n` 实际调用固定命令验证免密授权；使用额外参数的 `sudo -n` 实际调用验证它没有免密授权。`sudo -l` 仅查询授权列表，不作为参数拒绝的执行证据。

```sudoers
Cmnd_Alias PTOBENCH_AGENT_DISPATCH = <resolved-locked-python> -I -S <absolute-checkout>/evaluator/agent_dispatch.py
Defaults!PTOBENCH_AGENT_DISPATCH env_keep = "PTOBENCH_AGENT_LAUNCH_REQUEST"
<broker-user> ALL = (ptobench-agent:ptobench-share) NOPASSWD: NOSETENV: PTOBENCH_AGENT_DISPATCH
```

该规则只新增 Broker 到专用 Agent 的固定无密码命令；不授予 Agent 任何 sudo 权限，也不改变 Broker 原有 sudo 授权。规则文件归 root 所有、权限 `0440`；不要加入通配参数、`SETENV`、Shell 或 root runas。真实 dispatcher 启动测试等 Plan 01 创建固定入口后进行。

**开工前宿主预检命令：** 完成人类准备中的账号、共享组、Bubblewrap 和 ACL 后，由管理员运行以下探针。`bwrap` 路径从系统 PATH 解析，不使用 Broker HOME 内的副本。管理员还须用 `passwd -S ptobench-agent` 确认 shadow 状态为 locked（通常显示 `L`），并检查 `getent passwd ptobench-agent` 的 shell 指向可执行的系统 `nologin` 程序；`getent passwd` 本身不能证明密码已锁定。

```bash
getent passwd ptobench-agent
getent group ptobench-share
id ptobench-agent
passwd -S ptobench-agent
BWRAP="$(readlink -f "$(command -v bwrap)")"
sudo -u ptobench-agent -g ptobench-share -- "$BWRAP" --version
sudo -l -U ptobench-agent
```

使用 Bubblewrap 运行 `/usr/bin/id` 前，预检必须通过 `readelf -l` 与 `ldd` 找出该二进制的 ELF interpreter、共享库和必要 loader cache，并以只读 mount 将这些依赖按原绝对路径放入沙箱；`/usr` 单独挂载不够。只挂载依赖闭包和最小所需系统路径，不 bind 整个 `/`。实际启动形式为 `sudo -u ptobench-agent -g ptobench-share -- "$BWRAP" --unshare-user --uid 0 --gid 0 --cap-drop ALL --ro-bind /usr /usr <resolved-id-runtime-bind-args> --dev /dev --proc /proc --tmpfs /tmp -- /bin/sh -c 'id -u; id -g; id -G; exec sleep 60'`；`<resolved-id-runtime-bind-args>` 必须替换为目标主机查出的动态 loader/library/cache mount 参数，不得原样执行。启动前确认 `/bin/sh`、`id`、`sleep` 的依赖闭包都在 mount manifest 中。记录 namespace 内 `id` 输出，并在 `sleep` 存活期间从宿主读取对应 PID 的 `/proc/<pid>/status` 与 uid/gid map。预期：账号锁定且只属于 `ptobench-share`，shell 为非交互 `nologin`；Bubblewrap 可运行；namespace 内报告 uid/gid 0，宿主侧同一探针进程仍属于 Agent UID 与共享 GID，`Groups` 不含其他组、`CapEff` 为零。最后的管理员 `sudo -l -U` 查询不得列出 Agent 可执行的 sudo 命令；沙箱内 `sudo -n -l` 只能作为补充检查，不能以 `sudo` 未挂载或命令不存在代替此检查。随后按本计划步骤在临时真实 Workspace 执行 DAC 与存活进程动态发布探针。每个路径的 `getfacl -e` 变更前后快照和命令结果写入本地 `host_preflight.md`；不得把 ACL 报告、Case 数据或凭据提交到 Git。
