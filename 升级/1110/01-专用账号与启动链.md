# 专用账号与启动链 Implementation Plan

> **For agentic workers:** Use `executing-plans` to implement this plan task by task.

**目标：** 让现有 PTOBench 启动路径只把 Pi Agent 切换到 `ptobench-agent`，Broker 和 NPU Worker 继续使用原宿主账号；移除运行时 subordinate UID/GID 发现、映射和清组状态机。

**架构：** 管理员一次性创建锁定的 Agent 账号和共享组，并安装精确 sudoers 规则。Broker 通过 sudo 以 Agent 用户身份运行固定的 `ops/ptobench-agent-dispatch.py`；dispatcher 只读取一次性请求并用 argv 执行现有 Bubblewrap 命令。sudo 不以 root 身份运行 dispatcher、PTOBench 或 Agent 命令；不增加 setuid 程序或 root helper。

**唯一运行路径：** 新建或重启的 Pi Agent 一律经固定 launcher 以 `ptobench-agent` 身份启动 Bubblewrap。不得保留 Broker UID 直接启动、subordinate UID/GID 映射、setpriv 清组分支或旧 runner 回退；配置未就绪时 fail closed。旧 Session 不迁移。

**Tech Stack：** Python 3 标准库、sudo/sudoers、Linux 用户账户和 POSIX DAC、Bubblewrap。

**Spec：** [`00-overview.md`](00-overview.md)。

## 全局约束

- `ptobench-agent` 的主组是 `ptobench-share`，账号密码锁定且没有交互式 Shell；它不属于 `wheel`、`HwHiAiUser` 或其他无关组。
- Broker 保持现有 UID 和硬件组，只增加 `ptobench-share` 成员资格。NPU Worker 继续由 Broker UID 启动，继承共享组不等于获得新的硬件权限。
- sudoers 只允许 Broker 用户以 `ptobench-agent:ptobench-share` 身份执行固定的 system Python 和 dispatcher 路径；规则限定完整 argv，不使用通配符、`SETENV`、root 目标或任意 Shell。
- Request 不含模型凭据，Agent Sandbox 不挂载 launcher request 目录；dispatcher 在 Bubblewrap 启动前读完并删除 Request。
- UID/GID 在宿主安装时从 `getent` 发现并用于验证；实现代码不固化数字 UID/GID、subordinate range、硬件组或安装目录。

## Review Focus

1. `sudo` 规则是否确实只运行固定 Python/dispatcher argv，且最终进程在执行任何 PTOBench 请求代码前已是 Agent 用户。
2. Agent 能否从 request、环境变量或 `sudo` 获得 API Key、Broker 身份或任意其他 sudo 命令。
3. Agent 账号/组设置是否会移除 Broker 的现有硬件组，或让 Agent 意外获得硬件访问。

**依赖：** 无。完成后提供 `agent_command(...) -> (argv, env)` 的稳定启动接口，供 Plan 02–03 使用。

## 修改文件

- Modify `evaluator/agent_launch.py::prepare`、`_host_credentials` 及其测试：删除 subordinate range 选择、`newuidmap/newgidmap` 与 setpriv 分支，改为检查当前 Broker 身份、共享组和固定 Agent launcher 是否安装；Agent 身份、组或权限不符时拒绝启动，不尝试旧机制。
- Modify `evaluator/isolation.py::agent_command`：保留 Bubblewrap `View.argv`、`--unshare-user`、network、mount、environment 与 `--cap-drop ALL`；把生成的 argv 交给新启动前缀。
- Modify `ops/ptobench-agent-dispatch.py::main`、`read_request`、`check_identity`：删除 namespace/bootstrap 逻辑；脚本固定无参数，从仅 sudo 保留的 `PTOBENCH_AGENT_LAUNCH_REQUEST` 环境变量读取请求。验证文件普通、无链接/硬链接、Broker 所有、共享组可读、请求大小和 schema；读取后 unlink，再 `execve` Bubblewrap argv。
- Create `ops/ptobench-agent-user.sudoers.example`：按当前 Broker 用户名、共享组名、系统 Python 路径和仓库绝对路径生成；只允许固定命令以 `ptobench-agent:ptobench-share` 身份运行。仅对该命令保留 request 环境变量；不给 Agent 用户 sudo 授权。
- Create `ops/README-agent-user.md`：记录一次性创建 `ptobench-share`、锁定密码的 `ptobench-agent`，将其主组设为共享组、将 Broker 加入共享组、重新登录以加载新组、生成精确 sudoers 并用 `visudo` 校验的步骤。根据目标 Linux 主机发现 `useradd/groupadd/nologin/visudo` 和系统 Python 路径；不适配时停止，不猜测发行版命令。
- Test `evaluator/tests/test_agent_launch.py`、`evaluator/tests/test_isolation.py`、`evaluator/tests/test_portability.py`。

## 步骤

- [ ] 先添加无特权单元测试：固定 launcher 无参数、请求文件 O_NOFOLLOW/单链接/权限校验、损坏 schema 拒绝、命令以 argv 执行；request 内容不含上游 API Key。
- [ ] 建立独立身份探针：在临时目录经固定 sudo 命令运行 Bubblewrap，记录宿主侧 UID/GID/Groups 与 namespace map。Agent 的有效组仅有共享组；`CapEff` 为零。Broker UID 和现有硬件组保持不变，新增共享组只是 Candidate 文件访问权限。
- [ ] 探测 sudo 对 stdin/stdout/stderr、进程组、退出码与信号的传递。当前 `session_actions._run_process` 的 `pass_fds` Action gate 属于受信任 Evaluator，不应经过 Agent sudo；断言 Candidate Worker/Action gate 路径未切换到 Agent 身份。不得开放 sudo 通配参数。
- [ ] 固定 Request 布局：`session_root/agent/launcher/` 由 Broker 所有、共享组 `0730`，Request 由 Broker 所有、共享组 `0640`、单链接且随机命名。Agent 可以按环境变量给定路径读取并在消费时 unlink，但不能列出该目录。Request 不挂载到 Agent Sandbox，Broker 在异常退出恢复时清理残留文件。
- [ ] 实现一次性账号配置步骤和 sudoers 示例。对已存在的账号/组，先验证 shell、锁定状态和成员清单；不符合就停止，不接管或改写未知主体。
- [ ] 接入 `agent_command`：Basic/CANNBot Pi 启动只调用该 launcher；目标账户、仅共享组成员、Broker 组成员、launcher owner/mode、request 路径任一不合格时停止并报具体项目。测试断言启动失败不会落入 Broker UID、setpriv 或 namespace ID 映射路径。
- [ ] 加入真实 DAC canary：Broker 创建一个共享组可读写文件和一个仅对 Broker 原有硬件组可读的 `0640` 文件。Agent 必须能读写前者、不能读后者；测试检查宿主 `/proc` 身份，不以 Sandbox 内 `id` 作为唯一证据。
- [ ] 确认 Basic/CANNBot 都使用此入口，`session_actions._run_process` 的 Action 启动 gate 和信号清理未变化；Candidate Worker 与 NPU 执行没有调用 Agent launcher。
- [ ] 在管理员实际安装步骤完成后，从普通 SSH 和 PTOBench 队列/tmux 启动真实 Pi smoke；Agent 不能 `sudo`，Broker 与 NPU Worker 仍有原权限。

## 验证

```bash
python -m unittest discover -s evaluator/tests -p 'test_agent_launch.py' -v
python -m unittest discover -s evaluator/tests -p 'test_isolation.py' -v
python -m unittest discover -s evaluator/tests -p 'test_portability.py' -v
visudo -cf /tmp/ptobench-agent-user.sudoers
sudo -n -l
```

预期：单元与隔离测试通过；sudoers 仅授权固定 Python/dispatcher argv 作为 `ptobench-agent:ptobench-share` 运行；实际安装后 Broker 可无密码启动 Agent，Agent 仅有共享组且无 capability。CI 不安装 sudoers；生产身份 canary 在管理员安装后单独运行。

## 完成标准与停止条件

仅当精确 sudoers 路径能承载 Bubblewrap 的完整 argv/环境/信号行为，且 Agent 与 Broker 的 DAC canary 通过，才进入 Plan 02。任何实现需要 sudo 通配命令、root 执行 repo/PTOBench 代码、给 Agent 加硬件组、切换 Candidate Worker 身份或静默退回 Broker 身份时立即停止。失败时修复专用账号路径或报告宿主配置阻塞，不启用旧隔离方法；不得因本任务失败清理现有用户/组或修改系统 sudoers。
