# SLUICE 分阶段实现计划

## 目标

用最少的在线模块完成一个可运行、可停止、可复核的 SLUICE 闭环，并让知识库和 Profiling Tool 能够独立构建、独立测试、按小接口接入。

## 非目标

- 现在就实现中断后恢复；
- 通过多个 Pi 或多个模型并行搜索；
- 用一个评分器代替 Pi 作机制判断；
- 把原始 Profile 全量塞给 Agent；
- 把 PTOBench 真实运行记录、具体 Case、隐藏答案或 commit 编号写入离线知识库。

```text
        ├── stage1-2_profile_tool ─────────┤
        ├── stage1-3_knowledge_base ───────┼── stage3_context_pi_loop
        └── stage2_state_reducer ──────────┘              │
                                                         ├── stage4-1_knowledge_integration ──┐
                                                         └── stage4-2_profile_integration ────┤
                                                                                               ▼
                                                                            stage5_opportunity_decision
                                                                                               │
                                                                                               ▼

```

`stage1-1`、`stage1-2`、`stage1-3` 和 `stage2` 在 `stage0` 的共享契约冻结后可以并行。`stage4-1` 和 `stage4-2` 在 Context 和状态接口稳定、各自的知识/Profile 产物就绪后也可以并行。

## 阶段摘要

| 阶段 | 目的 | 是否可并行 | 完成标志 |
|---|---|---:|---|
| 0 | 固定最小架构、术语、数据契约和验收边界 | 否 | 共享契约可被并行阶段引用 |
| 1-1 | 建立单 Pi、PTOBench Adapter 和 Controller 骨架 | 与 1-2/1-3/2 并行 | 能创建一个 Session 并拒绝非法动作 |
| 1-2 | 整理 PTOBench 原始 Profile 的读取和呈现 | 与 1-1/1-3/2 并行 | 输入相同时得到稳定、保留原始事实的观测 |
| 1-3 | 用 Pi 工作流重新生成离线知识包 | 与 1-1/1-2/2 并行 | 只发布干净卡片，来源和实验不泄漏答案 |
| 2 | 实现唯一 State、事件和 Reducer | 与 1-1/1-2/1-3 并行 | 状态更新可重放且不混淆程序版本 |
| 3 | 接入 Context 投影和单 Pi 持续循环 | 否 | 多周期在同一个 Pi 中继续 |
| 4-1 | 将离线知识接入动态 Context 和查询入口 | 与 4-2 并行 | Pi 可按当前问题检索，不写回在线结果 |
| 4-2 | 将 Profiling Tool 接入受控运行 | 与 4-1 并行 | Profile 事实完整，证据与版本正确绑定 |
| 5 | 在唯一 State 内实现证据驱动的机会/下一步决策 | 否 | 继续、诊断、重查和停止有清楚且可追溯的依据 |
| 6 | 停止控制、端到端验收和冗余清理 | 否 | 显式停止、预算停止和失败路径都安全结束 |

## 统一完成标准

每个阶段必须有：

1. 一个小而明确的模块接口；
2. 能通过接口验证的测试或自检；
3. 明确记录的失败行为；
4. 不重复创建另一套状态或事实来源；
5. 在对应 `progress.md` 中记录完成证据和未解决问题。

## 变更规则

- 阶段实施发现缺口时，先修改对应阶段的契约和计划，再写代码。
- 如果一个新模块只是转发已有接口，做删除测试；不能证明它带来深度、局部性或真实适配差异，就不添加。
- Knowledge 和 Profile 可以重新生成，不把旧产物当作兼容性负担。
- 不为未来的多 Pi、恢复或复杂预测器预留空壳接口。

## Codex Goal 模式的通用执行要求

执行某一阶段时，先读本文件、`architecture_v0.md`、总 `progress.md` 和所选阶段的 `plan.md`。再检查实现该阶段所必需的现有代码、配置和测试；改动只限于该阶段及直接依赖。完成计划中的实现、测试和失败路径后，更新阶段与总进展记录。遇到实际 PTOBench/Pi 接口与计划不符时，先修订阶段计划并记录原因，不得虚构接口或悄悄扩大范围；不要顺手开始后续阶段。
