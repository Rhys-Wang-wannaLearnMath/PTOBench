# Stage 1-3：离线知识库重新生成

## 目的

构建一个可重复运行的 Pi agent workflow，从批准的原始来源形成干净的离线机制知识包。成品只保留组织后的知识卡片，不把原始来源目录、运行审计信息或当前 Case 内容混进 Agent-facing 知识库。

## 允许读取的来源

1. 由 source manifest 明确列出的官方文档、设计文档、运行时/编译器/Profiler 通用源代码中关于机制、约束和可观测信号的内容。不能对整个仓库做无边界抓取。
2. Git 历史中关于变化原因、机制演进和已知限制的内容；成品不保留 commit 编号、提交者和提交时间。
3. 批准的软件环境、版本和硬件说明，用于核查或修正卡片中的适用条件；这不是在线运行门禁。
4. 构建阶段允许的受控自主测试，用于核查机制和趋势；只用通用合成输入或专门的非 benchmark 微型程序。知识卡片只记录一般性趋势、适用条件和观测信号，不记录具体实验内容、Case、输入、参数、答案或可反向推断答案的细节。

明确不读取或不写入：PTOBench 真实运行记录、PTOBench case/candidate 源码和输入、隐藏 Fixture、Sealed Reference、Oracle、Candidate 答案、在线 SLUICE 结果和具体 benchmark case 内容。允许读取的仓库路径必须先进入 source manifest；未经批准的路径默认不读。

## Pi 和 harness

知识构建由 Pi 驱动，但不是在线优化 Session。使用约定的 Pi 配置：

- `benchmarks/PTOBench/modes/_shared/profiles/pi/deepseek-flash-max.yaml`；
- 环境文件以 `benchmarks/PTOBench/modes/basic/.env` 为模板复制到本地构建工作目录；`.env` 仅供本地运行，不提交到仓库，也不把密钥写入知识包。

Harness 为每次构建提供固定的来源清单、卡片 schema、允许的工具、测试预算和发布目录。Pi 可以抽取、合并、改写和提出验证任务，但发布前必须经过确定性 schema 校验和去重检查。

## 工作流

```text
source manifest
  → 读取与分段
  → Pi 提取机制和信号
  → 统一术语、去重、合并限制
  → 受控测试核查（按需）
  → 只保留一般性结论
  → schema/泄漏/重复检查
  → 发布干净 knowledge package
```

每张卡片至少包含：机制标识、简短机制说明、适用线索、预期观测信号、限制、建议验证问题和简洁证据说明。卡片不包含原始长段落、commit 标识、审计哈希、具体实验数值、具体 Case 或答案。

## 重新生成规则

- 原始来源变化、Profile 观测字段变化或发现重复/错误卡片时，重新运行构建流程。
- 不在在线 Session 中修改知识库。
- 新包通过静态检查后整体发布；不维护复杂的在线增量写入协议。
- Pi 的构建对话、测试临时工件和审核记录不进入发布包；发布目录只含组织后的知识卡片及其必要索引。
- 若来源冲突，保留清晰的适用条件和待验证问题，不用主观标签伪装确定性。

## 验收

1. 从同一来源清单可以重复生成结构相同的卡片集合。
2. 成品目录只包含发布卡片和必要索引，不包含原始资料和内部审计信息。
3. 扫描结果不含 commit 编号、具体 Case、隐藏评测内容、答案或可复现答案的实验细节。
4. 每张卡片都能被 Knowledge Port 按机制或信号查询。
5. 卡片不替 Pi 作瓶颈、因果或停止决定。
