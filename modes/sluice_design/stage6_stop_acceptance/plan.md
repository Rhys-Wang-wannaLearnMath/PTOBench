# Stage 6：停止控制、端到端验收和冗余清理

## 目的

验证完整 SLUICE 闭环，并证明它能及时停止、保留最佳合法程序、正确记录证据；随后删除实现过程中重新出现的重复职责。

## 停止规则

### Pi 主动停止

Pi 在一个完整周期后提交 `stop`，说明当前没有成本合理且有证据支持的下一步，或剩余预算不值得继续。理由作为判断提议记录，不覆盖 PTOBench 事实。

### 系统强制停止

Controller 在 PTOBench 公开预算耗尽、Session 已关闭/取消、当前状态与 workspace 无法对应、Context 无法可信生成或动作无法安全完成时拒绝继续消耗资源。停止发生在当前受控动作结束后，不粗暴中断正在运行的正式评测。

### 收尾

`close` 只在 `stopping` 状态执行：检查未完成动作、提交最终 State、保留 `best_verified`，请求 PTOBench 收尾并关闭同一个 Pi。中断后恢复不属于第一版验收。

## 端到端验收

1. 同一个 Pi 连续完成多个周期，Context 每次反映最新 State revision。
2. 正确性失败或性能变差后仍保留此前最佳合法程序。
3. Profile 部分缺失、完全不可用、无变化和评测失败都能安全处理。
4. Pi 提交 stop 后不会再偷偷执行新评测。
5. 预算耗尽、取消和 Context 失败会阻止新动作并进入可收尾状态。
6. 最终 State、Candidate、EvidenceBundle 和 PTOBench 记录相互一致。
7. 知识包中不存在 PTOBench 真实运行记录、具体 Case、实验细节、答案、commit 编号或审计哈希。

## 冗余清理

- 第二个可写状态：删除或改为唯一 State 的派生视图。
- 只转发请求的浅层模块：合并进 Controller 或 Adapter。
- Profile/Knowledge 中的主观决策逻辑：移回 Pi 或删除。
- 管理 Pi 历史/compact 的 SLUICE 代码：删除。
- 多份有效知识包：只保留一个明确发布版本。

## 完成条件

- 端到端验收和核心不变量检查通过。
- 对未覆盖情形、失败行为和已知限制有记录。
- 架构、阶段计划和代码使用同一套职责名称。
- 没有把 Session 恢复、多 Pi、复杂评分模型或其他未批准需求带入第一版。
