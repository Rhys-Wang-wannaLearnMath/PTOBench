# Stage 1-2：Profiling Tool

## 目的

把 PTOBench 原始 Profile 变成 Agent 能读的、结构化的事实。这个工具做信息整理，不做主观判断。

## 设计输入与职责

1. 从 PTOBench 的公开 Profile 输出读取指标、单位、采集模式和缺失信息。
2. 对照 Stage 0 的 `Observation` 和 `EvidenceBundle` 找出重复字段，以及无法绑定到程序版本的字段。
3. 保留来源明确的原始观测；工具只负责整理，不输出瓶颈或因果判断。
4. 使用满足当前运行需要的最小格式，不增加兼容层或额外状态存储。

## 目标结构

Profiling Tool 的输入是 PTOBench 公开 Profile 工件和一个具体观测问题；输出是：

- 相关指标和原始数值；
- 单位、采集模式和程序版本；
- 结果的周期和 Hypothesis 关联；
- 缺失、不可用或未请求字段的明确表示；
- Agent 可读的简短结构化摘要。

输出不包含“瓶颈是某机制”“该变换有效”“应继续”等判断。`available/unavailable` 是数据可得性，不是对知识可信度的评价。

## 原始工件和 Agent 视图

- 原始 Profile 由 PTOBench 的受控运行目录保存；结构化结果保留所支持的字段，不能因问题筛选而丢弃信息。
- 按问题返回的内容是原始观测的视图；未解析字段留在原始工件中，不得静默丢弃。
- 原始 Profile 是否向 Agent 开放由运行配置决定，不在 Prompt 中强制禁止；内部路径和采集实现细节不进入 EvidenceBundle。
- Profile 结果须通过 PTOBench 的公开接口读取，并与对应运行和程序版本关联。

## 验收

1. 相同输入得到相同结构化输出。
2. 数值、单位和缺失信息不因筛选而丢失或被改写。
3. 不同 ProgramRef 的结果不会混合。
4. 输出可以直接绑定 Hypothesis、Cycle 和 ProgramRef。
5. 单元测试覆盖空结果、部分字段、失败 Profile 和重复采集。
6. 使用 PTOBench 实际 Profile 输出验证解析和单位还原；硬件可用时，对照一次真实采集结果检查结构化输出与原始结果一致。此验证数据留在受控运行工件中，不进入知识包。
