# PTOmni 架构修缮建议

> 本文是基于 2026-11-02 架构稿的历史审查建议；当前设计以 [PTOmni_架构设计_2026-11-03.md](PTOmni_架构设计_2026-11-03.md) 为准。

## 总体判断

新架构的主方向清楚：一个长期工作的 Owner、按需专业协作、PTOBench 提供真实验证、确定性状态与动态经验共同支持后续搜索。暂时不需要重做整体分层；建议在冻结共享契约和进入实现前，先收敛下面几项职责与概念，避免把同一事实或决策分散到多个位置。

## P0：实现前应明确

### 1. 固定优化周期与记录单位

文档把 **Episode** 定义为团队相对稳定的规划周期，把 **Round** 定义为一次正式优化尝试；同时 **Attempt** 又承载该次尝试及评测结果。Round 与 Attempt 语义接近，而一个 Hypothesis 又允许关联多次 Attempt。

建议明确为：

- **Case Session**：一次 PTOBench Case 优化运行；
- **Episode**：围绕一个较大问题的规划阶段，可包含多轮；
- **Round / Attempt**：一项明确的优化动作，从确定假设、修改出一个候选，到收集必要证据、总结结果并决定下一步。两者一一对应，持久化只保留一个 `Attempt` 记录；
- **PTOBench CLI Test**：一次 `evaluate` 或 `profile` 命令及其结果，是 Round/Attempt 中的子事件，不单独算一轮；
- **Hypothesis**：可跨多轮持续验证的主张，每轮记录本次测试了它的哪个变换。

同一候选的 `evaluate`、按需 `profile` 及必要的重跑都属于同一轮；只要开始新的优化变更，就开始新一轮，即使它仍在验证同一个 Hypothesis。轮次在该候选的结果被判读、证据被记录、团队选定继续/换方向/停止后结束。Curator 按轮总结，事实与每次 CLI 测试结果仍由确定性记录保存。

这样“一轮”表示完整的优化闭环，而不是单条命令；持久化只维护一份 Attempt 事实，避免 Round 和 Attempt 重复计数。

### 2. 明确决策权与预算权

当前 Supervisor 被描述为决定继续、切换或停止；Owner 持续工作并提出下一步；State Layer 更新状态；PTOBench 又负责正式预算和测量。建议明确分工：

- **Owner**提出优化假设、实施变更并请求验证；
- **Supervisor**调整 Episode 目标和团队，并提出继续或停止的策略决定；
- **确定性 Controller/State**校验状态转移、权限与停止条件，不替 Agent 判断优化方向；
- **PTOBench**是正确性、Clean Benchmark 和硬件动作预算的权威来源；PTOmni 只记录其公开结果与剩余预算。

同时区分硬件动作预算与 LLM/墙钟成本。TeamPlan 中的局部预算只能限制协作开销，不能形成第二个正式评测预算。正常停止是策略决定；预算耗尽、Session 关闭等是系统强制停止；最终收尾由受控流程完成。

### 3. 保持一份权威进展，避免 Memory 与 Opportunity 重复

文档将 Attempt、Evidence、机会状态和事实放入确定性 Progress State；Case Memory 也包含事实、失败尝试和下一步机会；Opportunity Frontier 又单独记录机会状态。虽然文档说明事实状态权威，但三者的写入和读取关系仍可更明确。

建议把 **Event Ledger** 作为客观事件记录，把 **Progress State** 作为其确定性投影；Opportunity 状态只在 Progress State 中维护。Case Memory 保持为可重建的短摘要，只引用 Attempt/Evidence，并容纳带不确定性标记的解释。Curator 可提出经验与机会建议，Supervisor 决定搜索方向，确定性状态逻辑负责记录已接受的状态变化。

这样事实只维护一次，摘要可替换，机会排序也不会变成另一份隐性状态。

## P1：进入对应实现阶段前明确

### 4. 用只读工具向团队提供知识与性能证据

知识库和 Profiling 都不需要变成新的 Agent。把它们作为统一 Runner 可调用的两种只读工具：

- **知识检索**：每个角色先拿到精简的 Case、设备/软件版本和权限上下文；遇到具体问题时再按主题检索。返回短章节、来源和适用版本。角色标签只用于推荐检索方向，不限制专家跨主题查阅。
- **性能证据**：Supervisor 的 `TeamPlan` 写明关注主题和所需证据；Owner 或只读专家可请求 `profile_summary(candidate, focus)` / `profile_compare(before, after, focus)`。工具返回结构化指标、来源、候选身份、可比性和缺失项，不输出未经证实的因果判断。

知识保持只读且在实验期间固定；Profiling 只解释性能现象。PTOBench Clean Benchmark 仍是正式性能结论的唯一依据。Agent 不需要直接读取全部原始 Profile，也不应绕过受控接口自行拼接测量结果。

这样所有角色可以共用同一小组接口，而不是给每个角色另建一套知识注入和数据解析逻辑。Profile 结果按需加载，并将证据引用写入 Attempt，避免重复采集和版本串用。

### 5. 让逻辑角色共用 Runner，并明确阶段

八种逻辑角色不等于八套长期 Session 或八个在线子系统。建议由同一个 Runner 执行不同提示任务：Owner 持续工作；Supervisor 仅在规划节点调用；Specialist/Challenger 只读、按需短时调用；Curator 在正式尝试后做一次短总结。多角色并行时记录其 Token/墙钟成本。

运行阶段收敛为：

1. **Plan**：Supervisor 读取 State 和 Case Memory，输出经校验的 `TeamPlan`；
2. **Diagnose**：所选 Specialist（必要时 Challenger）并行只读分析，提出建议和证据缺口；
3. **Implement**：Owner 综合建议并独占 Candidate 写入；
4. **Evaluate**：PTOBench 串行完成正确性和 Clean Benchmark，按需补充 Profile；
5. **Learn / Monitor**：确定性更新 Attempt、Best、预算和证据引用；Curator 更新 Case Memory；仅遇到重要状态变化时重新规划。

默认从 Owner 单人开始，常规最多加一名 Specialist；只有明确的跨机制问题才加第二名或 Challenger。单一写入者适合作为第一版默认，减少冲突并保持结果可追溯；若后续证明写入串行成为瓶颈，再考虑隔离候选分支并行探索，而不是让多人共享编辑同一份 Candidate。

### 6. 完整定义候选与证据的可比身份

文档允许修改源码和白名单编译选项；Evidence Bundle 示例也包含 Shape、设备和编译配置。但 ProgramVersion 的语义尚未明确说明这些信息如何共同标识一次候选及其测量结果。

建议明确：候选身份至少能区分源码快照与编译配置；评测/证据还要绑定输入或 Shape、设备和软件环境。Before/After Compare 仅在相关身份条件可比时给出直接差异，否则明确标为不可比。无需引入复杂版本系统，只需保证 Best、Attempt 和 Evidence 能追溯到同一份可复现配置。

## 文档精简建议

当前架构主张在概览、论文故事线、角色定义、端到端例子和最终总结中多次重复。建议将本文件定位为规范性架构说明：保留职责、状态所有权、主流程、不变量和阶段路线；将论文叙事与贯穿案例移到研究说明，最终总结压缩为一页摘要。这样可以让后续实现以单一、较短的设计依据为准。

## 建议顺序

先确定“Episode / Hypothesis / Attempt”的关系，以及谁对策略、事实、预算和收尾负责；再冻结 Candidate/Evidence 身份与 `TeamPlan` 的阶段、知识主题、所需证据和只读/写入权限。随后跑通最小执行闭环；知识检索与 Profiling 可在接口冻结后并行实现，不需要增加新的 Agent 或抽象层。
