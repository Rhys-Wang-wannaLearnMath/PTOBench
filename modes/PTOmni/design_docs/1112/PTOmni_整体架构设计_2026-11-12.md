# PTOmni 整体架构与设计

> 日期：2026-11-12
> 最近更新：2026-11-16（明确 Assembler 综合与诊断权限，以及各角色按需查看原始 Profile）
> 状态：当前完整设计基线，供后续架构讨论和实施拆分使用。
> 本文只描述 PTOmni 自身的目标架构。文中标为“待讨论”的事项尚未冻结，不应在实现中默认为已决定。

## 1. 设计摘要

PTOmni 是一个面向 PyPTO/NPU Kernel 优化的**动态轻量 Agent Team**。首版采用一个 Host 顺序推进 Round：Lead 规划，入选 Tuner 独立探索，Assembler 综合各 Tuner 的方案并选择交付候选，Runner 通过 PTOBench 公共 CLI 执行动作。首个优化 Round 固定启用 Compute、Dataflow、Schedule 三个 Tuner；后续每轮启用哪些、启用几个，完全由 Lead 决定，不偏向多选或少选。每轮在 Tuner 修改前，Host 对 Parent Candidate 采集一份新的 `combined` Profile，并把同一事件交给入选 Tuner 的专长 Analyzer；首版不跨 Round 复用 Parent Profile。所有角色都可按需请求 Host 只读查看与任务相关的原始 Profile 产物，但不默认推送，也不开放任意归档路径。Assembler 可只读查看所有入选 Tuner 的 workspace 和记录；若要组合改动，Host 才为它创建临时 workspace。Assembler 可在明确授权下验证组合 Candidate，并在 Evaluate 结果需要诊断时按需 Profile 和使用相关 PTOAnalyzer 工具。每个 Round 的原始产物保留在各自归档中，Curator 在 Round 结束时更新同一份贯穿本次 Run 的 `CASE_MEMORY.md`，供后续角色按需查阅。PTOBench 仍是 correctness、Clean Benchmark 和硬件动作记录的权威来源。Challenger 是针对具体风险或证据争议的按需只读复核角色；Curator 每轮固定调用一次整理经验。二者都使用短时独立会话，不常驻。

“Team”描述的是不同职责，不要求多个 Agent 进程同时运行。首版由 Lead、入选 Tuner 和 Assembler 完成优化主流程；Curator 每轮在收尾阶段调用一次，Challenger 只在有具体复核问题时调用。角色任务默认顺序调用；除首个优化 Round 固定启动三个 Tuner 外，后续每轮的 Tuner 人数和专长由 Lead 自行决定，不存在推荐人数或自动增减。Tuner 负责独立探索；Assembler 必须检查多个方案之间是否互补，并在改动可组合、计划授权且预算允许时实际验证组合候选，不预设最终选择现成或组合方案。它只在诊断组装候选有明确需要且获得授权时请求额外 Profile / Analyzer，不重复采 Parent 基线。PTOmni 不训练一个学习型调度器，也不建立第二套评测、硬件预算或事实账本。

Agent 使用两类指导资料和一份由 Curator 持续维护的实验记忆：

1. **PTO Wiki** 提供经整理的 PyPTO、编译器、运行时、模型和 NPU 机制资料。知识应按需、短片段、带来源与适用范围地呈现。
2. **PTOAnalyzer** 把某一确切 PTOBench Profile Event 的受保护归档转成可追溯的结构化观测。它只读、离线，不采集 Profile，也不输出自动根因判断。
3. **CASE_MEMORY.md** 在本次 Run 生命周期内累积每个 Round 的问题、修改、实测结果、决策和经验；详细原始记录仍保存在对应 Round 目录。

PTO Wiki 和 PTOAnalyzer 帮助 Agent 提出更好的假设，但不能取代 PTOBench 的实际执行和正式测量。每个 Round 的原始记录保存在各自目录，Curator 将精简且带来源的跨轮经验持续更新到 Run 级 `CASE_MEMORY.md`。这是一份普通文件，不另建数据库、记忆服务或向量索引。当前 Wiki 内容已整理为离线主题资料；PTOAnalyzer 的九个只读工具已通过 CPU 测试与既有归档回放。PTOAnalyzer 仍需接入正式 PTOmni Host，才会成为 Agent 可调用的在线工具。

## 2. 目标与设计原则

### 2.1 目标

- 让 Agent 基于 Case、Candidate、历史实验和适用的机制资料形成**可证伪的优化假设**，减少没有信息增量的硬件尝试。
- 用动态团队按需组织机制专长，让本轮团队规模和角色调用次数由问题、证据缺口和预算决定。
- 让代码改动、Profile、评测、解释与结论绑定到相同的 Candidate 和 PTOBench Event，便于复查与复现。
- 在有限接口后隐藏知识检索、Profile 身份验证、工具权限、候选隔离、PTOBench 调用和状态恢复等实现细节。
- 允许功能从一个 Case 的最小闭环逐步增加，不要求先造通用 Agent 平台或一次性并行所有模块。

### 2.2 原则

1. **PTOBench 是执行事实的权威来源。** PTOmni 不改写 correctness、Clean Benchmark、硬件动作计数或正式结果。
2. **Profile 是诊断证据。** Profile 不提供 correctness 或 Clean Latency，也不能单独证明根因或加速。
3. **Candidate 写入权清楚。** 每个 Tuner 写自己的 fork workspace；Assembler 是本轮唯一候选综合与交付决策者。首版通过 Host 分配路径和候选交接减少互相干扰，不承诺共享 Shell 下的强文件系统隔离。
4. **Agent 解释与观测事实分开。** 机制解释、知识片段和 Profile 指标各有不同来源与语义。
5. **按需组队。** 角色是逻辑职责，不是常驻进程；本次 Run 的首个优化 Round 固定启用三种 Tuner，后续由 Lead 按当时证据决定团队构成，不默认多选或少选。
6. **事实不重复记账。** PTOBench Event 保存执行事实；PTOmni 的 Round 文件保存计划、产物和引用。Host 只维护推进流程所需的最小状态。
7. **读取接口收窄，模块实现做深。** Team Loop 不知道 Wiki 文件布局和 Profile 解析格式；知识、Analyzer、Runner 和状态更新各自封装实现。
8. **缺失信息明确表达。** 不可用、未采集、空数据、损坏数据和不兼容证据不能坍缩成数字零或“没有瓶颈”。

### 2.3 轻量化首版边界（2026-11-13）

PTOmni 借鉴 EAT 的简单 Harness 思路：Host 按阶段启动角色、用文件化结果交接、统一调用正式评测并保存本轮结果。首版沿用 PTOBench 与已有 Wiki / PTOAnalyzer，不另建通用 Agent 平台。具体约束如下：

- **一个 Host、顺序流程。** Host 内部可以有清楚的函数边界，但首版不把角色、Runner、State、Wiki 和 Analyzer 拆成服务或独立常驻进程；不建 Agent 消息总线或复杂工作流引擎。
- **短时独立角色会话。** 每次角色调用使用自己的短时 Session；同一次调用内可多轮使用获批工具。角色之间不共享对话 Session，通过 Round 文件交接所需内容；新 Round 不复用旧对话。
- **辅助角色保持单一职责。** Lead、入选 Tuner 和 Assembler 构成优化主流程。Curator 在每个 Round 收尾时调用一次，读取本轮结果并更新 Run 级 `CASE_MEMORY.md`；Challenger 只在具体风险、争议或证据缺口出现时按需调用。两者都经同一个短时 Role Session Adapter 顺序启动，不常驻；Case Memory 是普通方法记录文件，不建设独立记忆服务。
- **工作区按写代码的需要创建。** 每个入选 Tuner 从同一个 Parent Candidate fork 一个独立 workspace；Host 在一轮开始时创建一次，不因每条 CLI 或每次 Evaluate 重复 fork。Lead、Runner、Challenger 和 PTOAnalyzer 不需要独立代码 workspace。Assembler 可只读查看本轮所有 Tuner workspace 和记录；确需合并或修改时，才从明确的 Parent 创建临时 workspace，新 Candidate 仍须经 PTOBench 验证。
- **历史保留、按需读取。** 每个 Round 的计划、结果、决定、代码差异和 PTOBench Event 引用保留在本次 Run 的可访问历史目录中。新 Round 的 Agent 可自行查阅上一轮目录，但 Host 不把全部历史或其他角色对话自动塞进 Prompt；当前 Tuner 只被告知 Parent 与自己的 workspace 路径，不主动提供同轮其他 Tuner 的路径。
- **不把路径分开放大成安全承诺。** 独立目录和最小路径传递可减少无意接触，但共享 Shell 能力下不能保证 Agent 无法主动搜索其他目录。首版不为此新增容器或完整文件系统沙箱，也不修改 PTOBench 公共代码；如实际运行环境后来提供低成本挂载隔离，可直接采用。
- **用 PTOBench 事件做事实，用少量文件做交接。** PTOBench Events 是硬件动作和评测事实来源；PTOmni 只保存 RoundPlan、角色结果、Assembler 决定和 EventRef。当前 Run 状态保持为可重建的最小数据，不另建数据库、重复账本或独立 Case Memory 服务。
- **指导信息复用现有资产。** Wiki 首版使用现有目录 / 索引做有界本地读取；PTOAnalyzer 通过 Host 内薄 Adapter 调用现有 Python Interface。不新增向量数据库、检索服务、Analyzer Server 或 Profile 副本。

这种设计复用了 EAT 的阶段式启动、文件交接和 Harness 统一评测；不照搬其通用团队配置、并行执行和依靠 Prompt / 目录约定实现的权限保证。PTOmni 保留 PTOBench Candidate / Event 身份以及受管 Runner，因为它们直接关系正确性、硬件预算和结果可追溯性。

## 3. 当前基础与实现状态

### 3.1 PTO Wiki

当前知识库位于 [`pto_wiki/pypto_wiki`](../../../../pto_wiki/pypto_wiki/README.md)，包括问题索引 `INDEX.md`、总览和 11 个主题目录。目录下的主题 README 汇总相关内容，原始来源文档保持分开，便于 Agent 查看完整示例、上下文和术语。知识覆盖 PyPTO API / 操作、Kernel 编写、任务图与调度、运行时、性能调优、精度与调试、分布式编程、模型、编译器/IR、NPU 架构与 ISA 等。

这份内容可直接作为 PTOmni 的只读知识源，不需要重新抓取或重建资料库。PTOmni 需要实现的是**运行时读取与上下文控制**：冻结知识快照、按 Case 和环境选取少量相关页面、保留出处与适用范围，并记录 Agent 实际看到的片段。当前目录结构是离线浏览知识库，不等于已有 PTOmni Host 检索 Tool。

### 3.2 PTOAnalyzer

当前实现位于 [`modes/ptomni/pto_analyzer`](../../../ptomni/pto_analyzer/README.md)。Stage 4 已完成九个只读工具的实现与离线验收：Compute、Dataflow、Schedule 各三个。既有回放覆盖 16 份 Profile，5,492 个索引产物哈希前后相同，新增硬件动作为 0；Stage 4 记录 51 项 CPU 测试通过。该状态证明工具实现可在样本归档上离线分析，不证明 PTOmni Agent 已能调用或工具已提升调优效果。

现有工具和权限如下：

| Tuner 专长 | 工具 | 主要观测 |
|---|---|---|
| Compute | `compute_mapping_check` | dispatch program、callable 与 kernel config 映射及源码关联状态 |
| Compute | `compute_unit_activity` | 按 build/rank/dispatch/core 的 PMU 活动计数 |
| Compute | `compute_task_share` | 能可靠关联到依赖图、callable 与 AICore span 的 task 计数 |
| Dataflow | `tile_access_check` | 编译器 Tile-access 提示 |
| Dataflow | `buffer_pressure_check` | MemoryReuse 提示与 Scope 原始计数 |
| Dataflow | `tile_memory_allocation_summary` | AllocateMemoryAddr 产物中的静态分配数量和显式请求字节数 |
| Schedule | `dependency_path_check` | 依赖图 task / edge、深度及端点缺失情况 |
| Schedule | `dispatch_gap_check` | 同一 rank/dispatch/core 上可比 AICore 区间的原始观测间隔 |
| Schedule | `task_distribution_check` | 按 rank/dispatch/core 汇总的 AICore 记录、task token 和区间周期 |

任一工具给出的都是带单位、来源覆盖和解释边界的观测，不是瓶颈判决或优化处方。

Analyzer 已有适合 Host 使用的 Python Interface：`ProfileRef.from_event(session_root, event_seq)`、`open_toolset(tuner, profile_ref)`、`tool_specs`、`initial_summary` 和 `call(name, args)`。它校验确切 Event、Candidate digest、归档索引与保护清单；工具权限由 Tuner 专长静态决定；Lead 没有 Analyzer Tool。当前 `ProfileRef` 要求已完成的 `combined` Profile；因此 PTOmni 初始集成应采用 `combined` 策略，不应在未扩展 Analyzer 契约时改用 split Profile。

Stage 4 明确记录当前**没有 PTOmni Host 调用 `ToolSession` 的入口**。集成应在真实 Host 的原生工具传输处增加薄 Adapter，不创建模拟 Host、第二个 Tool Server 或新的 Profile 采集链。

### 3.3 PTOBench 方法与执行协议

PTOmni 的可执行代码标识为 `ptomni`，方法入口按 [`modes/PROTOCOL.md`](../../../PROTOCOL.md) 实现 `preflight / prepare / run / collect`。实验方法负责 Agent 编排、知识、Analyzer 接线、状态和方法记录；Launcher 负责方法生命周期；Evaluator/PTOBench 负责 Case、Workspace、预算、原始 Profile、正确性、Clean Benchmark 和正式结果。

Host 的 Runner 通过公共 `ptobench evaluate/profile/fork` CLI 执行动作，角色通过受控工具请求授权操作。当前 `profile` 成功动作消耗一次硬件动作，但不检查输出 correctness、不生成 Clean Latency、不产生可选 Snapshot；`evaluate` 才能建立 Agent Candidate 的正确性与探索性能结果。官方最终验收由受控 finish 流程单独完成，不应让 Agent 直接改写最终成绩。硬件计数和评测事实均沿用 PTOBench 账本。

Launcher 已按 `mode.yaml` 动态加载方法，不需要为 PTOmni 增加专属分发分支；但当前隔离运行时通过 `evaluator.common.MODE_SOURCE_DIRS` 静态枚举要收集、挂载和纳入完整性保护的方法源码目录，其中尚无 `ptomni`。而 `evaluator.isolation.copy_runtime()` 目前只收集这些 mode 目录的顶层 Python 文件，不会带上现有的 `modes/ptomni/pto_analyzer/` 子包。因此首次以隔离 mode 运行 PTOmni，公共运行时接入需同时纳入 `ptomni` 并包含其子包；Host、角色和工具实现仍放在 `modes/ptomni/`。严格要求零公共代码改动时，当前运行时还不满足条件。

## 4. 领域对象与记录单位

| 对象 | 定义 | 权威来源 / 生命周期 |
|---|---|---|
| **Case** | PTOBench 固定的待优化任务及输入、Oracle、评测约束 | PTOBench；PTOmni 读取，不修改 |
| **Candidate** | 可执行源码与相关编译配置的一个具体版本 | PTOmni 维护工作区和身份引用；PTOBench Event 记录实际被执行的版本 |
| **Round** | 围绕一个连贯决策问题的一次规划、探索、综合、最终候选验证和总结过程 | PTOmni 逻辑分组；不是 PTOBench 硬件动作 |
| **Experiment** | 一个 Tuner 或 Assembler 提交的 Candidate 变体、假设、改动和相关证据 | PTOmni 方法记录；引用本 Round 共享的 Parent Profile Event，以及该实验相关的 Evaluate / 可选诊断 Profile Event |
| **PTOBench Event** | 一次受管 `profile`、`evaluate` 或 `fork` 的结果记录 | PTOBench 账本；原始事实不可由 Agent 修改 |
| **EvidenceRef** | 指向一个可复查的 Event、Profile 观测、知识来源或 Candidate 身份的引用 | 源记录由各自来源所有；引用进入 ExperimentResult / State |
| **RoundPlan** | Lead 对当前 Round 的问题、角色、动作权限和预算安排 | PTOmni Host 校验后冻结；不能授权超出全局预算或角色能力的操作 |
| **Round Archive** | 当前 Case 各轮的计划、Candidate、实验结果、Assembler 决定和来源引用 | PTOmni 按 Round 保存；后续团队可按需查阅，不自动注入全部历史 |

不要把 Round、Experiment 和 PTOBench CLI Event 混成一个轮次计数：一个 Round 可含多个 Experiment，一个 Experiment 可含多次 PTOBench Event；Profile 或 Evaluate Event 不自动开启新的 Round。

### 4.1 Candidate 与证据身份

Candidate 的基本身份至少覆盖源码快照摘要和影响代码生成的编译配置。某项观测的可比身份还要带上其 Case / Shape、设备、PyPTO / CANN / 相关软件版本，以及 Profile 或 Evaluate 配置。PTOBench 已提供的 Candidate / Event 身份优先复用，不另建竞争性的权威标识。

任何 Profile、Analyzer 观测、正确性结果和 benchmark 结果都必须引用实际被执行的 Candidate/Event。不同源码、配置或环境的证据不能直接合并为一个结论；比较条件不足时标为 incomparable，并保留原始引用。

## 5. 总体架构

```text
PTOBench Method Protocol
  preflight / prepare / run / collect
                  │
                  ▼
┌──────────────────────── PTOmni Host ─────────────────────────┐
│                                                              │
│  Sequential Run Loop                                         │
│    ├── Context ─────────── Case + Parent + RunState          │
│    │                    ├─ Wiki Reader (read-only)            │
│    │                    ├─ CASE_MEMORY.md (on demand)          │
│    │                    └─ prior Round files (on demand)      │
│    ├── Role Session Adapter ── Lead / Tuner / Assembler       │
│    │                         ├─ Challenger (on demand)         │
│    │                         └─ Curator (once per Round)       │
│    ├── Tool Adapter ───────── PTOAnalyzer ToolSession          │
│    ├── Runner ─────────────── ptobench profile/evaluate/fork  │
│    └── Round files + CASE_MEMORY.md + EventRef + RunState     │
└──────────────────────────┬───────────────────────────────────┘
                           │ managed public CLI
                           ▼
                   PTOBench / Evaluator
             Case · Workspace · budget · events
             Profile archive · correctness · clean result
```

这些是职责边界，不是首版必须分别实现的子系统。轻量实现可以把它们放在一个 Python Host 内：

1. **Method Host**：遵循方法入口协议，拥有一次 Run 的进程生命周期；按固定阶段顺序协调角色调用并维护最小推进状态。
2. **Team Orchestrator**：根据当前上下文调用 Lead，校验 RoundPlan，按计划调用 Tuner 和 Assembler；Round 收尾时调用 Curator 更新记忆，必要时调用 Challenger。
3. **Guidance Adapters**：Wiki Reader 返回只读知识片段；Analyzer Adapter 将有效 Profile Event 映射到专长工具；History Reader 提供 `CASE_MEMORY.md` 或指定 Round 记录。
4. **Runner**：校验执行角色、RoundPlan、workspace 与预算，再调用公共 PTOBench CLI；不自行计算评测结果。
5. **Run Records**：以少量文件保存 RoundPlan、角色结果、Assembler 决定、PTOBench EventRef 和 Run 级 `CASE_MEMORY.md`；Host 只维护可重建的最小 RunState，不另建重复事实账本或独立记忆服务。

角色会话可以短时顺序调用；Wiki Reader 和 PTOAnalyzer Adapter 使用现有本地资源和接口。只有 PTOBench 硬件动作通过公共 CLI 边界执行。格式解析、身份检查和授权仍需保留，但不必包装成服务或通用框架。

| 模块 | 面向调用方的 Interface | 模块内部负责 | 不应泄漏给调用方的细节 |
|---|---|---|---|
| Team Orchestrator | `run_round(context) -> round_result` | RoundPlan 校验、角色顺序、触发器、阶段收敛 | Agent backend 命令、会话文件布局、PTOBench 内部状态 |
| Role Session Adapter | `invoke(role, task_context, allowed_tools) -> role_output` | 创建短时角色会话、记录输入输出、限制工具权限 | Provider 认证、native session 解析和清理方式 |
| Wiki Reader | `search(query, case_context, limit) -> KnowledgeHit[]` | 冻结快照、索引读取、上下文过滤、来源定位 | Wiki 文件树、索引构建与底层检索算法 |
| PTOAnalyzer Adapter | `open(role, specialty_scope, profile_event_ref) -> ToolSession`；Host 另提供 `read_profile_artifact(...)` | 绑定经 Host 授权的 Profile Event、按角色与专长限制工具；按需只读呈现事件内原始产物；映射调用与错误 | 原始 Profile 路径、产物解析和 Cursor 编码 |
| Runner | `profile/evaluate/fork(workspace, authorization) -> EventRef` | RoundPlan 权限、workspace 和预算检查、受管 CLI 调用 | PTOBench 锁、Evaluator 命令和原始目录内部结构 |
| Run Records | `write_round(record)` / `read_round(round_id)` / `append_case_memory(entry, summary)` | 保存和读取 Round 记录；原子追加 Case Memory 条目并更新顶部摘要；从 PTOBench 引用恢复评测事实 | 本地文件布局与序列化细节 |

每个 Interface 同时定义身份绑定、权限、排序、不可用语义和成本来源，而不只是函数参数。Wiki Reader 和 PTOAnalyzer Adapter 的实现可分别由假数据/fixture 替代；Team Orchestrator 测试跨越同一 Interface，不需真实硬件或在线模型。

## 6. Agent Team

角色按任务启动和结束。角色名表示输入、权限与输出契约，不暗示独立常驻 Agent、独立模型或必然并行。

| 角色 | 输入 | 可执行动作 | 输出与限制 |
|---|---|---|---|
| **Lead** | 当前 Case / Parent、最小 Run 状态、可按需查阅的历史 Round、剩余预算 | 规划和分配下一轮团队，不写代码、不调用 Runner 或 Analyzer | 一个短 RoundPlan；不能改写事实或选择未经 Assembler 验证的 Candidate |
| **Tuner** | RoundPlan、只读 Parent workspace、自身可写 workspace、相关 Wiki、自己的专长 Analyzer Tool 和本轮共享 Profile；历史 Round 可按需查看 | 只读查看 Parent、只写自身 workspace；调用自己的只读 Analyzer Tool；在计划授权范围内请求 Evaluate，不请求 Profile | ExperimentResult，包含改动、理由、假设、观测解释和结果；Host 不提供同轮其他 Tuner 的 workspace 路径；不能改 Case / Oracle / Evaluator / PTOBench 账本 |
| **Assembler** | 本轮所有入选 Tuner 的 workspace / 记录的只读查看入口、ExperimentResult、Candidate / diff、PTOBench Profile / Evaluate Event 引用与可核验事实 | 比较各方案；必要时请求 Host / Runner 创建组装 workspace、组合或修改 Candidate、执行经授权的 Evaluate；若组合结果需要诊断，可请求额外 Profile 并使用 Host 按需开放的相关 PTOAnalyzer 工具 | 综合正确性、可比性能、兼容性、证据质量和集成风险，决定本轮交付和下一轮 Parent Candidate；主动评估现成候选与有依据的组合候选，不预设结果偏好。任何新组合都作为新 Candidate 重新验证。需要改变 Tuner 团队时由 Lead 另开 Round 决定 |
| **Challenger** | 一个待复核的具体主张 / 决策，以及必要的计划、实验结果和来源 | 只读审查 | 返回最强反例、证据缺口、可能的替代解释和一个区分性检查建议；不写代码、不调用 Profile / Evaluate、不否决，也不替 Lead 改计划 |
| **Curator** | 当前 Round 的计划、改动摘要 / diff 引用、实验结果、Assembler 决定、PTOBench EventRef，以及已有 Case Memory 的短当前摘要 | 每个 Round 收尾时核对本轮结果并整理长期记忆更新 | 返回一条有来源的 Round 记忆条目和更新后的短当前摘要；Host 将其追加 / 更新到 `CASE_MEMORY.md`；Curator 不改写 Round 原始结果、不写 Candidate、不替 Lead 决策 |

Tuner 与 Assembler 的职责不同，即使它们都可能在授权范围内使用 Evaluate 或 PTOAnalyzer：Tuner 围绕分配给自己的机制独立修改 Candidate，并用自己的专长工具分析 Parent Profile；Assembler 横向检查所有 Tuner 的方案，决定是否组合，并对组合 Candidate 做验证和必要诊断。Assembler 不默认获得全部 Analyzer 工具；Host 只在获准的组合 Profile 上开放与组合改动相关的专长，组合确实跨越多个机制时可以开放多个专长工具集。

两个辅助角色都由 Host 通过现有 Role Session Adapter 顺序调用。Curator 每个 Round 固定调用一次，输入限于本轮已归档的结构化记录和 Case Memory 的短当前摘要；Challenger 的输入限于当前待审查问题需要的结果和证据。二者不创建 Candidate workspace、不请求 PTOBench 动作，也不形成新的权威事实来源。Curator 只返回记忆更新内容；Host 负责写入 `CASE_MEMORY.md`，因此 Curator 没有通用文件写权限。

### 6.1 Tuner 专长

当前 Tuner 专长暂定为：

- **Compute**：计算表达、冗余、归约、融合与计算布局。
- **Dataflow**：Tiling、数据布局与复用、搬运、Buffer、Pipeline。
- **Schedule**：任务粒度、并行度、Core 分配、依赖与负载组织。

它们是可动态选择的机制标签，不与 Tensor / Tile / Block 一一绑定。本次 Run 的首个优化 Round 固定各启用一个；之后 Lead 可从当前可用专长中选择任意有效组合。Lead 应为每个实验指定一个主要机制与可能受影响的次要机制；跨机制发现记录在 ExperimentResult 中，供后续计划参考。专长覆盖范围须结合实际 Case 的改动能力继续校准。

### 6.2 团队大小与协作开销

- 本次 Run 的第一个优化 Round 固定选择 Compute、Dataflow、Schedule 三个 Tuner。之后每个 Round 的数量和组合由 Lead 自行决定；提示中不放置人数偏好或引导性示例，Host 只做角色是否可用、权限和预算校验，不自动增减 Lead 的有效选择，也不因 Tuner 数量本身要求修改计划。
- 对后续 Round，Lead 可选择任意有效数量和组合的可用 Tuner 专长；架构不设默认人数、推荐人数或“人数越多/越少越好”的策略。若 Lead 不打算启动优化实验，应结束或暂停，而不创建没有 Tuner 的空转 Round。
- 每个 Tuner 从同一 Parent 获得独立 workspace；Host 只向它提供 Parent 和自身 workspace 的路径，不主动暴露同轮其他 Tuner 的 workspace。共享 Shell 下不保证主动搜索不可达。Assembler 可只读查看所有入选 Tuner 的 workspace 和工作记录；只有需要组合或修改时才创建 Assembler 临时 workspace。
- 角色和 Tuner 任务默认顺序执行；这描述执行顺序，不代表推荐任何 Tuner 人数。每个 Round 的硬件动作也经 Runner 串行执行。
- Host 对每个入选 Tuner 从同一个 Parent 创建一个 fork workspace；这个 fork 是轮次启动的准备动作，不是 Agent 高频执行的 CLI。Tuner 在该 workspace 内可完成多次修改和授权的 Evaluate。Assembler 可查看这些 workspace，但只有在综合修改时才由 Host 为它从明确 Parent 创建临时 workspace。
- Assembler 应比较所有现成 Candidate 与有依据的组合方案，不预设优先直接采用或组合。若组合改动兼容、符合本轮目标且预算允许，就形成组合 Candidate 并由 Host / Runner 执行 Evaluate；若有明确诊断问题，可请求额外 Profile。只在 Profile Event 与 Candidate 绑定、相关工具范围明确且本轮授权和 PTOBench 预算允许时，Host 才为 Assembler 开放对应的 PTOAnalyzer 工具。Profile / Analyzer 不作为每轮必跑步骤。
- Challenger 仅在 Lead 明确提出待审查问题且满足 RoundPlan 中的调用条件时短时运行；不能成为每轮固定步骤。
- Curator 在每个 Round 的 Assembler 决定和候选验证之后固定运行一次；即使本轮因 Profile、预算或执行错误而未能完成实验，也整理已知状态并明确标记缺失信息。它只更新同一份 `CASE_MEMORY.md`，不搜索其他 Case。

### 6.3 Workspace 权限与候选选择

每个 Tuner 使用从同一个 Parent fork 出来的独立 workspace，避免多个实验互相覆盖。Host 只把 Parent 和当前 Tuner 自己的 workspace 路径交给它，不主动提供同轮其他 Tuner 的路径；Tuner 之间仍不互相开放 workspace。Assembler 是本轮的综合角色，能查看所有入选 Tuner 的 workspace、改动及其工作记录，包括 Analyzer 观测、Profile / Evaluate Event、改动理由、预期效果、结果解释和失败尝试；Host 也将结构化 ExperimentResult 汇总给它。Assembler 对 Tuner workspace 只读是角色权限约定；共享 Shell 下不能保证文件系统强隔离。需要组合时，Host 从明确的 Parent 建立独立 Assembler workspace，Assembler 在此形成新 Candidate，不应直接修改源 Tuner workspace。上一轮目录保留并可按需读取，不自动进入角色上下文。

Assembler 的决定对象是“本轮交付候选 / 下一轮 Parent”，不等同于更新全局 `best_candidate`。它比较已验证的 Tuner Candidate、Parent 和有证据支持的组合方案；对合理、兼容且获授权的组合，应在预算允许时实际验证，不因单个 Tuner 结果现成就跳过跨方案综合。它可以进行多轮组装尝试，最终也可以选择某个 Tuner Candidate 或 Parent；需记录没有组合的原因、组合失败及其 PTOBench 结果。Assembler 综合正确性、可比 PTOBench 性能数据、稳定性或兼容性证据、改动范围、证据可信度与集成风险；Profile 只作诊断证据，不形成性能排名。若要求补充实验，只能在 Lead 已选团队的授权范围内执行；要改变 Tuner 组合则由 Lead 开启新 Round 决定。Host 再依据 PTOBench 的正确性与可比评测事实分别更新 `current_candidate` 和 `best_candidate`，因此 Assembler 选作下一轮 Parent 的 Candidate 可以不同于全局最佳测量 Candidate。

## 7. Guidance 设计

### 7.1 PTO Wiki：机制与约束资料

Wiki 的职责是回答“PyPTO、编译器、运行时和目标设备有哪些已知机制、约束与适用条件”。它不回答“当前 Candidate 的实测性能如何”，也不决定改动。

**内容与冻结：** `pto_wiki/pypto_wiki` 是主知识源。一次 Run 使用固定的只读快照，至少记录 source tree manifest / 文件哈希、构建或整理版本、Run 中实际提供给 Agent 的页面引用。不得在实验中途自动切换知识版本。方法的 `prepare` 阶段保存只读资源与 manifest，遵循 PTOBench 方法协议。

**检索路径：** 依据 Case 的 module / entry、当前设备与软件版本、本轮问题和可选的历史 Round 结论，先从问题索引和主题目录缩小范围，再选取少量来源页面或片段。PTO Wiki 现有的 [`INDEX.md`](../../../../pto_wiki/pypto_wiki/INDEX.md) 可作为问题入口。第一版优先复用现有目录和索引，使用本地关键词/元数据方式定位；不需要向量数据库、在线搜索或整库 Prompt 注入。

**最小 Interface：**

```text
search(query, case_context, limit) -> KnowledgeHit[]
KnowledgeHit = {text, source_path, section, applicability, wiki_revision}
```

`case_context` 至少包含 Case / Entry、设备和可确定的软件版本。结果数量与文本长度受限，保留出处和适用性；找不到合适内容时明确返回空结果。Lead 不拥有自由查询 Tool：Host 在 RoundContext 组装时提供少量相关资料；Tuner 可按需使用只读查询入口进一步定位。查询能力是否也提供给其他角色列为待讨论项。

### 7.2 PTOAnalyzer：Candidate 的结构化 Profile 观测

Analyzer 的职责是把 PTOBench 保存的 Profile 产物变成可复核的观测。它不调用 PTOBench、不读取任意 Agent 路径、不修改 Candidate、不调用 LLM，也不推导瓶颈。PTOBench 采集、归档并记账；Analyzer 绑定一条准确 Profile Event 后离线读取；获准的 Tuner 或 Assembler 负责解释观测。Tuner 面向自身专长提出改动，Assembler 面向跨候选比较和集成。

Host Adapter 使用现有 Python Interface，不复制解析器：

```python
from modes.ptomni.pto_analyzer import ProfileRef, open_toolset

profile_ref = ProfileRef.from_event(session_root, event_seq)
tool_session = open_toolset("Dataflow", profile_ref)
specs = tool_session.tool_specs
summary = tool_session.initial_summary
detail = tool_session.call("tile_memory_allocation_summary", {})
```

`ProfileRef` 由 Host 根据 PTOBench 已完成 Event 创建，不由 Agent 传入路径或挑选“最新 Profile”。当前实现校验 Session / Event / Candidate / Artifact Index / PTOBench Protection Manifest，并在读取文件时复核哈希。ToolSession 绑定 Profile Event、Candidate、调用角色、专长范围和 Tool；明细分页默认 20、上限 50。不可比、缺失、空或损坏的来源应保留其各自状态。

按专长开放 PTOAnalyzer Tools，不等于禁止查看原始 Profile。Lead、Tuner、Assembler、Challenger 和 Curator 都可在任务需要时，请 Host 只读呈现与当前任务相关的 Profile 原始产物；它们可以自行决定是否请求查看，不由 Host 默认推送。请求绑定明确的 PTOBench Profile Event 和其中的产物标识，由 Host 校验事件、Candidate 与保护清单后读取；角色不直接拿归档路径、不选择任意 Session / 文件，也不能修改原始数据。大型产物按需查看相关文件或片段，不把整份 Profile 自动注入上下文。该读取入口与 PTOAnalyzer 的结构化专长工具分开：前者呈现原始内容，后者提供按问题组织的观测、来源和解释边界。这是 PTOmni Host 的目标能力，当前尚未接入角色会话。

本轮 Parent Profile 的 Analyzer 工具按 Compute / Dataflow / Schedule 静态权限表开放给入选 Tuner；Lead 和 Challenger 不获得 Analyzer Tool。Assembler 可读取所有 Tuner 提交的分析结果与来源引用。若 Assembler 形成组合 Candidate 后遇到需要 Profile 诊断的具体问题，可向 Host 请求额外 Profile；Host 校验 RoundPlan 中的组装 / 诊断授权、预算和 Candidate 身份后执行。成功后只为 Assembler 打开绑定该 Profile Event 的 ToolSession，权限范围按组合改动涉及的专长收窄；组合跨多个专长时可开放对应的多个专长工具集，不默认开放完整 Analyzer。Assembler 默认不另开 Parent Profile 的 Analyzer ToolSession；若需核对原始内容，可按需通过 Host 查看任务相关的 Parent Profile 原始产物。

当前 Analyzer 要求完成的 `combined` Profile。首版固定采用以下采集流程：每个有 Tuner 的优化 Round，在 Lead 的 Tuner 组合通过 Host 校验后、任何 Tuner 修改代码前，由 Host / Runner 对该 Round 的 Parent Candidate 采集**一份新的 `combined` Profile**。该 Profile Event 通过各自的专长工具集共享给本轮所有入选 Tuner；不为每个 Tuner 重复采集，也不复用前一 Round 或更早的 Profile，即使 Candidate 身份匹配。Lead 选择的 Tuner 数量不改变每轮一份 Profile 的规则。Profile 额度在启动 Round 前纳入 PTOBench 全局预算校验；无法完成这份 Profile 时，不启动本轮 Tuner 修改流程，也不拿旧 Profile 冒充当前 Parent 的读数。

这次 Profile 是当前 Parent 的共同诊断基线，不是后续实验 Candidate 的测量结果。每个 Tuner 只获得自己的 Analyzer 专长工具，但可针对同一个 Profile Event 离线分析；Assembler 可读取 Tuner 已交付的观测和证据引用，不重复采集这份 Parent Profile。Assembler 仅在组合 Candidate 的具体诊断需要时，才可通过 Host 请求另一份绑定组合 Candidate 的 Profile，并按涉及机制使用受限的 Analyzer 工具集。若未来要在一个 Round 为 Tuner 采多份基线 Profile 或改为 split 类型，须先单独修订并验证 Profile 次数和来源契约。

**解释边界：**

- 单个 PMU 计数不等于计算瓶颈；静态分配字节数不等于运行时峰值；依赖数量不等于调度瓶颈。
- Profile 结果不能替代 Evaluate；Profile 延迟、PMU 或静态编译观测不能作为正式性能排名。
- Analyzer 对超大依赖图保留完整观测与分页，但首屏已测得约 20 秒和约 509 MiB 临时峰值；Host 应按需打开相关专长工具并控制重复分析，不把完整高基数明细塞入 Agent Context。

### 7.3 Run 级 Case Memory：每轮更新、贯穿 Session 生命周期

Host 为每个 Round 保存详细原始记录，包括 RoundPlan、Tuner 结果、代码差异引用、PTOBench EventRef、Assembler 决定和未解决问题；完整 Agent 对话和中间文件保留在本轮归档中。每个 Run 另有一份普通 Markdown 文件 `CASE_MEMORY.md`，由 Curator 在每个 Round 的 Assembler 决定和验证状态确定后固定更新一次。它贯穿整个 PTOBench Session / Run 生命周期，包含短的当前状态摘要和按 Round 顺序追加的历史条目，使后续角色能连续看到此前分析、改动和结果。

Case Memory 面向后续决策，原始 Round 记录仍是完整证据。Curator 不能只写“做过优化”这类空泛摘要；每个 Round 条目至少包括：

- **问题与假设**：本轮试图回答什么，依据是什么。
- **改动**：改了哪些部分，链接到 Candidate 和 diff / workspace 产物。
- **实验与结果**：Profile / Evaluate 的 PTOBench EventRef、正确性和可比性能结果；失败或未执行也明确记录。
- **判断与决定**：哪些是 PTOBench 事实，哪些是 Agent 的解释；Assembler 选择了什么、为什么。
- **经验与后续问题**：结论适用条件、反例或不确定处、尚待验证的问题。

每项实验结论都带 Round / Candidate / EventRef，避免长期记忆脱离证据。Curator 收到当前 Round 记录和已有的短状态摘要即可，不必把整份历史重新读入会话；Host 替换顶部摘要、追加当前 Round 条目，并保留所有既有条目。Case Memory 不复制完整对话和大型工具输出。首版不做向量检索、跨 Case 记忆、额外数据库或多层摘要管线。

EAT 的 [`launch_stateless.sh`](../references/EAT/agent_team/launch_stateless.sh) 提供了可参考的文件交接方式：每轮结果落入 `TEAM_OUTPUT.md`，下一次 Supervisor 调用再结合近期记录构造上下文；EAT 也支持跨轮保留 Supervisor 会话。PTOmni 的角色使用彼此独立的短时会话，因此采用前一种思路，将必要经验落到 Run 级文件，而不依赖某个 Agent 会话一直存在。`CASE_MEMORY.md` 是便于后续决策的索引和摘要，Round 档案仍保存完整依据。

Curator 的轻量调用契约为：

```text
update_case_memory(round_record, current_summary) -> {updated_summary, round_entry}
```

Host 把当前 Round 已提交的结构化记录、Case Memory 的短当前摘要和来源引用交给 Curator。Curator 区分 PTOBench 实际记录的事实和 Agent 解释；证据不足时标记不确定，不推断根因。若 Round 被中断，也记录已完成和未完成部分。Host 校验新摘要、条目格式和来源引用，再原子更新文件：替换顶部当前摘要、向历史区追加当前 Round 条目，既有条目保持不变；以稳定的 Round 编号识别条目，保证恢复重试不会重复追加。更新失败时保留旧记忆与本轮原始记录，Round 保持在 `curating`；恢复时只重试记忆整理或写入，不重跑硬件动作。一个 Round 只有记忆更新成功后才关闭。

## 8. Host、Context 和 Agent Session

### 8.1 Host 职责

Host 是一次 PTOmni Run 的控制点。它接收方法协议的请求和 PTOBench 公开运行环境，构造 Context、执行状态转换、调用角色 Session、建立当前角色权限、持有 Analyzer ToolSession、按需读取经授权的 Profile 原始产物、调用 Runner 并记录结果。角色 LLM 不能绕开 Host 直接访问 PTOBench 内部 Session 状态或自行定位 Analyzer 归档；但任一角色都可请求 Host 读取与任务相关的 Profile Event 原始内容。

Host 的对外依赖尽量少：

```text
invoke_role(role, task_context, allowed_tools) -> RoleOutput
run_profile(workspace, authorization) -> PTOBenchEventRef
run_evaluate(workspace, authorization) -> PTOBenchEventRef
search_wiki(query, case_context, limit) -> KnowledgeHit[]
open_analyzer(role, specialty_scope, profile_event_ref) -> ToolSession
read_profile_artifact(role, profile_event_ref, artifact_id, selection) -> read_only_content
update_case_memory(round_record, current_summary) -> {updated_summary, round_entry}
```

上述是职责层面的 Interface，不要求第一版逐项暴露成网络 API。Role Session、知识检索和 Analyzer 可由本地 Host 调用；Runner 的硬件执行仍使用 PTOBench 公共 CLI。

### 8.2 Context 组装

Lead 的 RoundContext 包含：Case Contract 摘要、当前 Candidate / Parent 身份、基线和已验证 Best 的 PTOBench 事实、当前 Run 的最小状态、剩余全局预算与当前轮限制。Lead 可按需读取 Round Archive、历史 Profile 摘要和相关 Wiki；Host 不预先注入全部历史。后续 Tuner 人数不由 Host 的默认值或推荐值决定。

Tuner Context 在此基础上增加：已批准的 RoundPlan、目标机制、Parent 与自身 workspace 路径、相关源码/编译信息、按需 Wiki 片段、该 Tuner 可用的 Analyzer Tools 与本 Round 新采 Profile 的摘要。Host 不主动提供同轮其他 Tuner 的路径或结果；上一轮和更早的 Round Archive 可按需读取。共享 Shell 下这属于最小暴露约定，不是访问控制边界。

Assembler Context 包含所有入选 Tuner workspace 的只读路径 / 查看入口、代码与差异、结构化工作记录、ExperimentResult、Profile / Evaluate Event 和 Analyzer 证据引用、各 Tuner 提交的改动理由与结果解释，以及剩余预算。它可以检查各候选源码和相关工作记录，但不默认收到完整原始 Profile、无关历史或完整角色会话记录；若需复查原始 Profile，应根据来源引用请求 Host 读取相关事件的产物。需要修改时只能写 Host 为组合工作创建的临时 workspace。

各角色都可按需请求 Host 读取与任务相关的 Profile 原始产物，适用同一条 Event 绑定、只读和来源校验规则；不默认把原始文件推送到任何角色的 Context。Lead 可查阅与规划相关的 Profile，Tuner 可查阅当前任务涉及的 Profile，Assembler 可复查 Tuner 或组合 Candidate 所依据的 Profile，Challenger 可查看待复核主张涉及的 Profile，Curator 可在整理本轮记忆确有需要时查看对应 Profile。角色不因此获得任意归档路径、跨任务 Profile 或 PTOBench 账本的访问权。

Assembler 可通过 Host 请求经授权的 Evaluate；这主要用于评估新组合 Candidate，已有 Candidate 的有效结果可以直接引用。对组合 Candidate 的 Profile 不是例行步骤：若 Evaluate 或代码差异暴露具体诊断问题，且 RoundPlan 的额外 Profile 权限与 PTOBench 硬件预算允许，Assembler 可请求 Host / Runner Profile 该 Candidate。Host 随后仅为此事件开放与组合改动相关的 PTOAnalyzer 专长工具；涉及多个专长时可开放对应的多个工具集，若组合确实涉及全部专长则可开放全部相关工具，但不默认授予所有 Analyzer 能力。Profile / Analyzer 用于诊断，不能取代 Evaluate，也不自动让 Assembler 获得新的独立 Tuner 实验权限。

Challenger Context 只包括被质疑的假设、必要的事实与来源、团队提出的解释；默认只读，不带无关工作区路径。Curator Context 包含当前 Round 的结构化记录、diff / Candidate / Event 引用和 Case Memory 的短当前摘要；不带活动 Tuner workspace、完整 Agent 对话或整份历史文件。Host 将 Curator 返回的更新应用到同一份 Run 级记忆文件。

Context Builder 应设置 token/记录大小上限；超出时先保留当前 Candidate 身份、最新事实、来源引用和 RoundPlan 约束，再减少旧历史与长明细。Agent 收到的截断或缺失信息要显式标出，不能通过隐藏状态伪装为完整上下文。

### 8.3 Session 执行模型

角色是逻辑任务。首版由一个受管 Host 顺序调用 Agent backend；每次角色调用使用一个短时独立 Session，同一次调用内可保持多轮工具交互。不同角色和不同 Round 之间不复用对话历史，必要信息通过 Round 文件交接。Host 按方法协议记录可取得的输入、输出、工具授权和 Session 引用。这样避免共享会话导致权限串线和上下文膨胀，也不需要另建 Agent 间通信机制。

若 Host 启动多个 Agent 子进程，所有进程必须留在 PTOBench 方法拥有的进程组内，确保预算耗尽、中断或异常关闭时由公共生命周期机制完整清理。禁止 detached worker。并行能力不是第一版前提。

## 9. RoundPlan 与 ExperimentResult 契约

### 9.1 RoundPlan

Lead 生成结构化计划，Host 进行确定性校验。计划不得增大 PTOBench 全局剩余预算、授权未启用 Tuner、授权 Lead 执行硬件动作或包含对 Case Contract / Evaluator 的修改。

```yaml
round_id: "round-..."
parent_candidate: "candidate-ref"
decision_question: "本轮要回答的单一决策问题"
hypotheses:
  - id: "hypothesis-1"
    claim: "可证伪的机制假设"
    primary_mechanism: dataflow
    secondary_mechanisms: [schedule]
    evidence_for: []
    disconfirming_observation: "什么结果会推翻假设"
team:
  tuners: "<Lead-selected list of assignments>"
  challenger: {enabled: false, question: "", trigger: ""}
profile_policy:
  parent_baseline:
    collection: once_before_tuners
    target: parent_candidate
    profile_type: combined
    reuse_previous_round: false
  assembler_diagnostic_profile:
    authorization: "由 Lead 明确授予；否则不执行"
    max_actions: "Lead 分配的额外 Profile 上限，受 PTOBench 全局硬件动作预算约束"
    target: assembled_candidate_only
evaluate_policy:
  max_actions: "本 Round 各角色共用的 Evaluate 上限，由 Lead 规划并受全局预算约束"
knowledge_topics: ["性能和优化", "API 和操作"]
stop_condition: "候选不可行、证据无信息增量或剩余预算不足"
```

此段是结构示意，不是可直接解析的 YAML 配置；`team.tuners` 的完整条目集合由 Lead 提交。首个优化 Round 必须包含三个专长；之后 Host 不设人数默认、偏好、最低/最高建议或自动增减，只校验 Lead 所选角色是否可用以及相应计划、权限和预算是否合法。此处不展示任何 Tuner 数量的例子，避免暗示人数偏好。Parent `combined` Profile 固定由 Host 在 Tuner 启动前采集一次并分发给入选 Tuner；Assembler 不重复采集基线。Lead 可针对明确的组合诊断问题，在 RoundPlan 中授权额外 Profile 及其动作上限；无授权时 Assembler 不得请求。Round 内 Evaluate 上限由各角色共用，Host 对 PTOBench Event 派生计数并与全局预算取更严格者；额外 Profile 也必须由 Host 授权并计入 PTOBench 硬件动作预算，不产生第二套账本。Agent 的预算数字必须与 Runner 执行授权可核对。

### 9.2 ExperimentResult

每个 Tuner 交付结构化结果，使 Assembler 能比较不同 Candidate，又不将解释混进 PTOBench 原始事实。结果必须说明改了什么、为什么改、预期改变哪些可观察指标、实际发生什么，以及解释中的不确定性；原始工作记录和差异保存在 Tuner 的 Round workspace / 归档中供 Assembler 只读复查。这里要求的是可审查的分析摘要，不是完整对话记录。

```yaml
round_id: "round-..."
experiment_id: "experiment-..."
parent_candidate: "candidate-ref"
candidate: "candidate-ref"
primary_mechanism: dataflow
secondary_mechanisms: [schedule]
hypothesis: "本次验证的主张"
change_scope: "实际修改范围及代码差异引用"
change_rationale: "为什么选择这些改动，以及它们针对哪个观测或问题"
expected_effect: "预期会发生什么可观察变化"
events:
  parent_profile: {event_seq: 12, status: completed, candidate: "parent-candidate-ref"}
  evaluate: [{event_seq: 13, status: completed, candidate: "candidate-ref"}]
observations:
  correctness: {status: pass, evidence_ref: "ptobench-event:13"}
  clean_benchmark: {status: measured, value_ref: "ptobench-event:13"}
  analyzer: [{tool: "tile_access_check", evidence_ref: "profile-event:12/tool:..."}]
interpretation: "Agent 对观测的解释；注明不确定性"
analysis_summary: "实际结果与预期的对应关系、其他解释和剩余不确定性"
failed_or_rejected_variants: []
resource_cost:
  hardware_actions: "由 PTOBench Event 汇总"
  wall_clock: "若运行时可准确采集"
  tokens: "若 backend 可准确提供"
applicability_and_limits: "可迁移条件与限制"
next_question: "后续需回答的问题"
```

状态值要区分 `not_requested`、`unavailable`、`failed`、`not_run`、`incomparable` 和有效结果。若 backend / Evaluator 没有提供某项成本，不补造估值；记录 unavailable。

## 10. 一个完整优化周期

1. **Preflight。** 验证方法配置、backend、模型设置、工具依赖、Wiki 资源版本、`combined` Profile 策略和 PTOBench 运行条件；此阶段不启动硬件实验。
2. **Prepare。** 建立 Run 方法记录，冻结 Agent 配置与提示，归档 Wiki manifest / 只读快照；为新 Run 初始化空的 `CASE_MEMORY.md`，恢复既有 Run 时保留原文件；从 PTOBench Context 读取 Case / workspace / budget，不覆盖 Bench 事实或控制文件。
3. **建立最小 Run 状态。** 读取当前 Case、Parent Candidate、已有 PTOBench Event 和缓存基线。只有权威基线缺失且预算允许时才由受管 Runner 执行所需动作；不能默认重复基线测量。
4. **构造 RoundContext。** Host 汇总当前候选与必要事实、选择少量相关 Wiki 片段，并提供 Round 历史的轻量目录；不自动注入完整历史。
5. **Lead 规划。** Lead 可按需查看以前 Round 的原始记录和 Curator 注记，再提交 RoundPlan。首个优化 Round 必须包含三个 Tuner；之后的数量和组合由 Lead 自主决定，系统不推荐或自动增减。Host 检查目标、角色和预算；校验失败则要求修正一次或终止本轮。
6. **采集本轮 Parent Profile 并分发指导信息。** Host 在任何 Tuner 改代码前，通过 Runner 对 Parent Candidate 采集一份新的 `combined` Profile。成功后，Host 创建 ProfileRef，并为每位入选 Tuner 打开其专长 ToolSession；同一 Profile Event 可被不同专长离线读取。该步骤不复用历史 Profile。Host 同时提供计划相关 Wiki 片段及只读检索入口；不默认推送原始 Profile 文件，任何角色都可按需请求读取与任务相关的原始产物。
7. **Tuner 探索。** Host 为每个入选 Tuner 从同一个 Parent fork 一个 workspace；Tuner 按顺序在自己的 workspace 中实验。Host 不主动暴露同轮其他 workspace 路径，历史 Round 可按需查看；不承诺共享 Shell 下无法搜索其他目录。Tuner 按计划请求 Evaluate，但不自行触发 Profile。
8. **ExperimentResult。** Tuner 提交 Candidate 身份、差异、假设、PTOBench Event、Analyzer 引用、解释和成本。Host 将结果保存为 Round 记录，并通过 EventRef 引用执行事实。
9. **按需挑战。** 当 RoundPlan 已授权且触发条件成立，Lead 可在高成本决定之前或发现 Tuner 结果冲突、解释与观测不一致、性能回退来源不清、连续尝试无信息增量时，请 Challenger 对一个具体问题做只读复核。若相关证据在计划后才出现，Lead 先明确更新本 Round 的复核授权；Host 不自行扩权。Challenger 只返回反例、证据缺口或区分性检查建议，不授权或执行动作。
10. **Assembler 综合与决策。** Assembler 只读检查所有入选 Tuner 的 workspace、代码差异、工作记录与结构化结果，比较现成 Candidate 和有依据的组合方案，不预设哪类方案更优。若改动合理且兼容，Host 从明确的 Parent 创建 Assembler 临时 workspace，Assembler 形成组合 Candidate 后请求 Runner 执行受管 `evaluate`；可在本 Round 授权范围内针对不同组合进行多次尝试。若评测或代码差异留下具体诊断问题，且计划已授权额外 Profile、预算允许，Assembler 可请求 Runner Profile 该组合 Candidate；Host 为该 Profile Event 按所涉及机制开放受限的 PTOAnalyzer 工具。额外 Profile 是按需动作，不重复 Parent 基线，也不代替 Evaluate。Assembler 比较经过验证的组合结果与现成候选后决定交付项；无合理组合、改动冲突或预算不允许时可选择现成 Candidate 或 Parent，并记录理由和已尝试的结果。
11. **验证与 State 更新。** PTOBench Event 提交后，由确定性逻辑确认 Assembler 所选 Candidate 的正确性并更新 `current_candidate`；另根据已验证且可比的 PTOBench 事实维护 `best_candidate`。两者可以不同，Profile 结果不进入 Clean Benchmark 排名。
12. **Curator 收尾与循环。** Assembler 决定及所需验证状态确定后，Host 每轮固定调用一次 Curator；Curator 将本轮分析、改动、结果、选择和后续问题追加 / 更新到 Run 级 `CASE_MEMORY.md`。下一轮 Lead 和 Tuner 获得 Case Memory 的可读引用，可按需读取相关内容；Host 不把整份长期记忆自动塞入所有 Prompt。新的决策问题或超出当前计划边界的补充实验开启新 Round。
13. **Collect。** 按方法协议收集所需 Agent Session、Prompt / 配置、Wiki 暴露、Analyzer 工具调用、Round 文件和错误记录。保留 PTOBench Event / Candidate 引用，不复制或重写权威结果。
14. **正式完成。** Run 关闭后由 PTOBench / 实验管理流程根据合法 Snapshot 执行正式 finish 与最终验证。PTOmni 不直接提交 final score。

## 11. Runner 与 PTOBench 执行规则

Runner 是 PTOmni 与 PTOBench 执行面的唯一方法侧 seam。它负责检查调用角色、RoundPlan 授权、workspace 身份和动作额度，再调用公共 `ptobench profile`、`ptobench evaluate` 或 `ptobench fork` CLI，并返回可引用的 PTOBench Event。角色通过 Host 暴露的受限动作请求 Runner；Assembler 和 Tuner 都不直接任意执行 CLI。Runner 不执行自定义 NPU 命令、不调用底层 Evaluator 私有接口、不复制 PTOBench 的正确性或性能逻辑。

执行约束：

- **Baseline** 只在缺乏可用、同身份的权威参照时建立；不能盲目重复测量。
- **Profile** 每个有 Tuner 的优化 Round 由 Host 在启动 Tuner 前对 Parent Candidate 采集一次新的 `combined` Profile；本轮入选 Tuner 共享这一个 Event。首版不允许以历史 Profile 代替本轮采集，也不让 Tuner 自行请求额外 Profile。Assembler 可在 Lead 已授权组装候选诊断且硬件预算允许时，请求对自己的组合 Candidate 采额外 Profile；由 Host / Runner 执行，并在该确切 Event 上按组合涉及专长开放 Analyzer 工具。任何 Profile 都消耗一次硬件动作；失败、中断和预算预留依 PTOBench 账本规则记录。Profile 不做 correctness 或 Clean Latency。PTOAnalyzer 对同一 Event 的多次离线 Tool 调用不增加硬件动作。
- **Evaluate** 用于候选正确性与探索性 Clean Benchmark。当前探索 Evaluate 的测量由 PTOBench 控制；Agent 不提供测量轮数。官方 finish 的测量和 Snapshot 规则也由 PTOBench 控制。
- **最终候选** 只有经过正确性校验才能成为 Best / 正式交付版本。Assembler 组合任何修改后必须重新验证。
- **Profile 对比** 只有 Candidate、Shape、设备、Profile 配置和环境身份兼容时才有解释意义。即便兼容，也只是诊断对照。
- **PTOBench 失败 / 中断** 由 Bench 记录其动作与执行状态。Host 不因未收到 CLI JSON 就推断动作未发生，也不绕开账本重试。
- **并行** 需同时满足 Tuner workspace 独立、物理设备租约不重叠、PTOBench 执行域支持并行。当前同一 PTOBench checkout 的 NPU CLI 实验按串行设计；在 Bench 明确支持并验证前，不实现多个独立动作的并发执行。
- **锁** PTOBench 自身执行锁与外层设备租约目的不同。Runner 不重复获取 PTOBench 内部锁，也不以增加锁或复制 checkout 的方式绕过现有执行约束。

所有 `run` 子进程留在方法拥有的进程组内，以便预算耗尽、中断或异常退出时清理。方法一次运行不重置 Session 或 PTOBench 预算。

## 12. 轻量状态与 Round 记录

### 12.1 事实与派生信息

- **PTOBench Events**：Profile / Evaluate / Fork 的权威动作记录；仅由 Bench 更新。
- **Round 文件**：Host 为每轮保存 RoundPlan、ExperimentResult、Assembler 决定、发生时的 ChallengerReview 和必要来源引用；Curator 更新的 Case Memory 是同一 Run 下的汇总导航文件，引用这些 Round 记录，不复制 PTOBench 结果，也不要求所有角色调用都写入通用 Event Ledger。
- **最小 RunState**：只保存继续流程所需的当前 Parent、最佳已验证 Candidate 引用、Round 序号 / 阶段和停止状态。预算直接读取 PTOBench；Candidate 身份与执行结果引用 Bench Event。State 可从 Round 文件和 PTOBench Event 重建，但首版不实现通用 Event-sourcing reducer。
- **历史产物**：Round 目录保留代码差异、必要日志和结果；完整 Session 按 PTOBench 方法协议的归档要求收集。它们供复查或按需读取，不默认组合进 Agent Context。

Round 文件可用 JSON 或 Markdown 保存在 Run 的方法目录；只对会被后续逻辑读取的字段定义稳定格式，不先引入数据库、通用事件框架或跨 Case 服务。收集时把应归档内容冻结并声明给方法协议。Candidate、PTOBench Event、Wiki 和 Tool 结果保留指向源对象的引用；保密凭据不得写入记录。

### 12.2 状态最小字段

```yaml
case_ref: "ptobench-case-ref"
current_candidate: "candidate-ref"
best_candidate: "candidate-ref-or-null"
round: 0
round_status: idle | planning | executing | assembling | verifying | curating | closed
stop_status: continue | stop | budget_exhausted | blocked
```

Round 的阶段按 `planning -> executing -> assembling -> verifying -> curating -> closed` 顺序推进；流程状态用于 Host 控制而不是构造通用状态机。每个 Round 完成候选选择 / 验证后必须成功更新 `CASE_MEMORY.md` 才能关闭；Curator 失败时停留在 `curating`，恢复时只重试记忆更新，不重放硬件命令。失败 / 中断但已形成 Round 的，也要先由 Curator 记录已知状态再关闭。

Assembler 决定本轮交付候选及下一轮 Parent；Host 在候选通过要求的正确性验证后才将它写入 `current_candidate`。如果所选候选验证失败，保留此前有效的 Parent / current 状态并记录失败。`best_candidate` 则由确定性逻辑根据 PTOBench 已验证且可比的评测事实维护，不由 Assembler 直接设置；因此下一轮 Parent 可以是一个审慎选择的候选，而全局最好测量结果仍另行保留。

预算权威仍是 PTOBench Session。`remaining_budget_ref` 只指向 / 缓存 PTOBench 当前公开结果，不成为第二计数器。跨进程恢复以已提交 Event 和方法日志为准；未提交的 Agent 文字不能当成已执行动作。

## 13. 方法入口、提示和权限

PTOmni 作为 `modes/ptomni/` 方法实现，`mode.yaml` 使用 `id: ptomni`。入口脚本按方法协议处理 `preflight / prepare / run / collect`，通用 Launcher 不解释 PTOmni 的角色、Round 或知识资源。

- `preflight` 校验 backend / 模型 / 版本、PTOmni 配置和本地知识 / Analyzer 依赖；无硬件动作。
- `prepare` 冻结 Prompt、Agent profile、Wiki 快照与 manifest，生成只读资源附件和 provenance 记录。
- `run` 在注册 workspace 中由 Host 编排所有角色；PTOBench 操作只经公共 CLI；Agent 子进程保持在方法进程组。
- `collect` 收集完整原生会话、实际曝光的知识和工具、工具输出、Run 状态与错误记录，并归档 `CASE_MEMORY.md` 和各 Round 记录；若记忆更新尚未完成，也归档待整理状态，保留同一 Session 恢复所需的数据。不补造 Agent 原生接口未提供的 Token 或行动数据。

角色权限由 Host 按最小需要传递，不仅依赖 Prompt 声明。轻量首版重点控制受管工具和 workspace 路径，不宣称实现共享 Shell 的文件系统安全隔离：

| 能力 | Lead | Tuner | Assembler | Challenger | Curator |
|---|---:|---:|---:|---:|---:|
| 读取当前 State / RoundContext | 是 | 计划所需子集 | 全部入选 Tuner 结果与本轮决策事实 | 审查所需子集 | 当前 Round 与 Case Memory 当前摘要 |
| 查询/接收 Wiki | 接收 Host 组装片段 | 接收片段；可按需查询 | 默认无 | 默认无 | 否 |
| PTOAnalyzer Tools | 否 | 当前 Tuner 专长 / Parent Profile | 按需开放给已授权组合 Candidate Profile 的相关专长 | 否 | 否 |
| 按需读取原始 Profile 产物 | 规划相关事件 | 当前任务相关事件 | Tuner 或组合 Candidate 相关事件 | 待复核问题相关事件 | 整理本轮记忆所需事件 |
| 读取本轮 Tuner workspace / 记录 | 否 | 仅 Parent 和自身 workspace；不主动提供其他 Tuner 路径 | 所有入选 Tuner workspace 只读，以及提交的工作记录和证据 | 审查所需来源 | 当前摘要和本轮来源 |
| 读取历史 Round / Case Memory | 可按需 | 可按需 | 当前 Round 结果；其他历史按需 | 审查所需来源 | 当前摘要和本轮来源 |
| 修改 Candidate / 记忆 | 否 | 写自身 fork workspace | Host 创建的组装 workspace；Host 写 CASE_MEMORY.md | 否 | 返回记忆更新；Host 写 CASE_MEMORY.md |
| 请求 Profile | 否 | 否；Host 在每个优化 Round 开始时统一采集 Parent Profile | 仅对组装 Candidate 按计划授权和预算请求；Host / Runner 执行 | 否 | 否 |
| 请求 Evaluate | 否 | 计划授权范围内 | 计划授权范围内，主要验证组装 Candidate；Host / Runner 执行 | 否 | 否 |
| 修改 PTOBench 事实 / 预算 | 否 | 否 | 否 | 否 | 否 |

方法自有 Wiki、提示、backend 配置和相关文件通过 `prepare` 的只读 archive 保护并记录哈希；运行中产生的 Round 文件在 `collect` 提交，不能在 `prepare` 时作为冻结附件。公共 `.benchmark_context` 与 Case 文件仍按 PTOBench 协议只读使用。

按 PTOBench 方法协议，Host 新生成的 Agent Prompt、任务导览和 CLI 使用说明采用简明英文；Wiki 内已有来源按原文保留。方法自身的架构和运行记录可用结构化格式，不改变原始知识内容。

## 14. 异常与降级

| 问题 | 处理 |
|---|---|
| Wiki 检索无匹配 / 版本不适用 | 返回无匹配或适用范围；继续使用 Case 与评测事实，不伪造知识结论 |
| 本 Round Parent Profile 未完成 | 记录对应状态和 Event；不创建 ProfileRef、不复用旧 Profile，也不启动本轮 Tuner 修改；报告 Lead 并结束或按新计划重新开始 |
| Assembler 的可选组合诊断 Profile 失败 | 保留组合 Candidate、已有 Evaluate 和失败 Event；标记额外诊断 unavailable / failed。Assembler 可依据已有证据继续比较，或放弃该组合；不自动重复 Profile |
| Profile Event 不完整或 Candidate 身份不符 | Analyzer 拒绝打开；不尝试扫描别的归档或路径；标记 unavailable / incomparable |
| Analyzer Tool 解析部分来源失败 | 保留其他工具 / 来源覆盖；相关字段标为缺失或解析问题，不作为零值 |
| Wiki / Analyzer Host Adapter 错误 | 不自动触发额外硬件动作；保留错误和影响范围，由 Lead 决定是否可继续 |
| Tuner 编译或 Evaluate 失败 | PTOBench 事件和 Candidate 保留；记录失败类型与假设判读，不把失败候选交付 |
| Tuner / Assembler 输出无效 | Host 做结构校验；要求有限次数修正，之后按失败结果关闭或回到上个已验证 Candidate |
| Curator 输出不合规或记忆文件写入失败 | Host 校验事实来源并原子写入；失败时保留上一版记忆和 Round 原始记录，Round 停留在 `curating`。恢复后只重试记忆整理 / 写入，不重跑硬件动作；成功后再关闭 Round |
| Run 被中断或预算耗尽 | 由通用生命周期清理进程；已提交 PTOBench Event 保留，未完成 Round 标记为待整理并由 `collect` 归档原始记录；同一 Run 恢复时先完成 Curator 更新，不根据残缺日志宣称动作成功 |

各步骤的重试上限和哪些基础设施故障可重试需要结合真实 Host 行为确定。任何重试均先检查 PTOBench Ledger，避免重复产生硬件动作。

## 15. 安全、审计与可复现性

- Tuner workspace 从同一个 Parent fork，Host 不主动提供同轮其他 Tuner 的路径；共享 Shell 下不把目录布局视为强隔离。受保护归档和 Candidate / Event 来源仍使用 PTOBench 提供的边界，不能通过任意路径选择 Analyzer 输入。
- Agent 不直接接收 PTOBench sealed 路径或 protection manifest 原始文件，也不能自行选择归档。任何角色都可通过 Host 按需读取任务相关 Profile Event 的原始产物；Host 校验 Event、Candidate 和产物标识，并以只读方式返回内容。ProfileRef 仍由 Host 绑定确切 Event。
- PTOAnalyzer 的工具参数不接受任意文件路径；Cursor 只续读授权 ToolSession 中的稳定排序明细。
- Wiki 资源和提示不可由 Agent 在 Run 中修改；来源文件哈希、版本和实际暴露片段可归档。
- Candidate、Case Contract、Oracle、Evaluator、PTOBench 账本与正式结果的保护规则由 Bench 执行；Host 不提供旁路。
- API key 等认证信息仅经既有 Provider 进程环境提供；不进入 Prompt、方法记录或 archive。
- 收集真实 Agent Session、实际模型设置、Role 输入/输出、工具注册/调用、Wiki 片段引用、Analyzer 结果引用、Run 配置和成本；原生 Agent 若不暴露某类信息，就标记 unavailable。
- 同一组实验固定模型 / backend 配置、Wiki snapshot、Profile strategy、Case 和评测设置；差异环境明确标记，禁止无说明合并。

## 16. 验证策略

验证应按 Interface 分层，CPU 测试覆盖 Host、State、Wiki 与 Analyzer Adapter，不因测试而启动 Agent 或硬件。

1. **协议与 Host 测试**：四种方法操作及 JSON 契约、method process 生命周期、预算 / 退出 / 中断清理、错误归档。
2. **Run 记录测试**：Round 阶段推进、Candidate 身份和 EventRef 关联、Case Memory 每 Round 更新一次、既有历史条目不被覆盖、来源引用有效、原子写入以及从 PTOBench 已提交 Event 恢复；记忆更新重试不得重放硬件动作；不实现通用 Event-sourcing 框架。
3. **Team / workspace 测试**：Lead 无执行 Tool；首个优化 Round 必须启用全部三个 Tuner，后续任意有效 Tuner 组合均原样接受且不做人数引导；每个入选 Tuner 得到独立 Parent fork，Host 不向其提供同轮其他 workspace 路径；Assembler 可只读查看全部入选 Tuner workspace / 工作记录，组合时由 Host 创建独立 workspace；其每个新 Candidate 必须 Evaluate；额外 Profile / Analyzer 只对 Lead 授权、绑定准确 Candidate / Event 且符合预算的请求开放。历史 Round 可按需读取且不会自动进入 Prompt。共享 Shell 的目录搜索不作为强隔离测试。
4. **Wiki 测试**：冻结 manifest、索引跳转、来源引用、设备 / 软件版本适用性、空结果、限量片段和 Run 记录可追踪性。
5. **Profile 原始产物读取测试**：验证所有角色可在任务范围内按需读取绑定 Profile Event 的原始产物；错误 Event / Candidate、未登记产物和越权请求被拒绝；读取只读且不默认注入上下文，不访问 NPU。
6. **Analyzer Adapter 测试**：使用 PTOAnalyzer fixture Profile 验证 `ProfileRef` Event 绑定、专长权限、摘要、Tool 调用、Cursor 翻页、来源覆盖、失败传播和只读性；不访问 NPU。
7. **Runner 测试**：使用可注入的 fake Runner 验证 RoundPlan 权限、额度和 Event 记录；另使用真实 PTOBench CLI 的受控测试验证 Session / workspace 接口。
8. **离线回放**：对既有 Profile 运行 Analyzer 工具，结果与当前 Stage 4 离线报告一致；不新增 hardware action。
9. **端到端硬件验证**：只有在 Agent Host / 工具接线稳定、Case 与设备窗口明确后开展，先跑一个代表 Case；按独立授权和 PTOBench 正式账本进行，不将小样本当作效果统计结论。

## 17. 分阶段实施路径

以可用端到端闭环为先，每阶段都让模块通过真实接口连接；Wiki 和 Analyzer 不必重新开发其已经完成的内容。

### 阶段 0：冻结最小共同契约

确定 Candidate / Event 引用、RoundPlan、ExperimentResult、Round 文件和 Runner 授权规则。保持结构最小，不因以后可能扩展而建通用 Agent 框架或数据库。

### 阶段 1：PTOmni Host 与团队闭环骨架

实现方法入口、单 Host 顺序流程、最小 Run 记录、角色调用和 Runner；每个入选 Tuner 从 Parent fork 一个独立 workspace，Assembler 仅在组装或修改时才额外 fork。Assembler 可读全部 Tuner workspace 和工作记录，评估现成候选并在有依据时验证组合候选；它可在 Lead 授权范围内请求组合 Candidate 的 Evaluate，并按需请求 Profile / 对应专长 Analyzer。Lead、Tuner、Assembler、每轮一次的 Curator 和按需 Challenger 使用相同的短时 Session 适配方式；Curator 只返回记忆更新内容，由 Host 的 Run Records 写入 `CASE_MEMORY.md`；Curator / Challenger 均无硬件工具或 Candidate workspace。可先用 fake Runner / Analyzer 做 CPU 集成验证，但不能把单 Tuner 作为实际运行时默认。真实优化流程的首个 Round 固定启用三个专长 Tuner，并由 Host 在改代码前采集和共享一份 Parent `combined` Profile；后续 Round 的选择由 Lead 决定且不受人数偏好影响。角色逻辑可用短时 Pi Session 执行，硬件动作使用公共 CLI。

### 阶段 2：接入已整理 PTO Wiki

冻结 `pto_wiki/pypto_wiki` 快照，复用现有索引与主题目录，接入有界本地检索和来源记录。先做 CPU 测试和资源可追溯性，再提供给 Lead Context 与按需 Tuner 查询。

### 阶段 3：把已有 PTOAnalyzer 接入 Host

在 Host / Pi 原生工具调用处建立薄 Adapter。Parent `combined` Profile 使用成功的 Profile Event 创建 ProfileRef，并向本轮入选 Tuner 注册其专长工具；Assembler 的组合 Candidate 诊断则按 Lead 授权、实际改动机制和对应 Profile Event 按需开放相关工具。为所有角色提供绑定 Profile Event 的只读原始产物查看入口，不默认推送文件或暴露归档路径。用现有 fixture 和只读档案验证，不重写 Analyzer 工具或另建 Tool Server。

### 阶段 4：完善动态决策和资源策略

根据实际执行轨迹校准 Challenger 的复核时机、Case Memory 条目的长度与字段、Profile 预算管理、上下文缩减和停止条件。Curator 每轮更新固定保留；通过链接原始记录控制记忆文件长度，不把它扩展成跨 Case 搜索服务。不要在 Host 中增加偏向更多或更少 Tuner 的默认、评分或自动改写；先观察 Lead 的团队选择和结果，再判断是否需要调整提示信息。

### 阶段 5：小规模受控端到端验收

在固定配置和 PTOBench Case 上检查候选正确性、Bench 事件可追溯性、Profile / Analyzer 身份正确性、Wiki 来源和暴露记录、动作预算、Run 收尾与最终 finish。之后再确定更大规模效果评估方法。

## 18. 明确的非目标

- 不实现通用多 Agent 平台、长期驻留的固定 Agent 群或跨 Case 自主学习系统。
- 不实现向量数据库、知识图谱、在线知识采集或 PTOAnalyzer 的第二个 Tool Server。
- 不实现常驻 Curator Agent、独立 Case Memory 服务 / 向量索引、Agent 消息总线、通用状态机框架或强文件系统沙箱；Case Memory 是每个 Run 下由 Curator 每轮更新的一份普通文件。
- 不重写 PTOAnalyzer 已验收的离线 Parser / Tools，不让 Analyzer 控制 Profile 采集。
- 不以 Profile 替代 PTOBench correctness / Clean Benchmark，不将 Analyzer 观测包装成性能根因。
- 不允许多个 Tuner 共享一个可写 Candidate，不在 PTOBench 并发能力未明确支持时并行硬件动作。
- 不维护独立于 PTOBench 的硬件动作计数或正式分数。
- 不要求首版具备自动跨 Case 知识迁移、学习型团队规划、复杂 DAG 搜索或大规模候选并行；首版也不预设后续 Round 的 Tuner 人数。

## 19. 待讨论与决策清单

以下问题不会阻止架构基线成立，但实施前或首轮轨迹后应逐项确认：

1. **Wiki 的查询责任**：Lead 只收 Host 预置片段、Tuner 是否获得原生搜索 Tool、Assembler 是否需要读取 Wiki 引用？建议先给 Lead 有界 Context、给 Tuner 按需查询，其他角色默认不查询。
2. **Profile 失败与预算不足时的恢复**：固定规则是每个优化 Round 在任何 Tuner 改代码前，对 Parent 采集一份新的 combined Profile；当 PTOBench 失败或预算不足时，应如何恢复或结束 Round，需结合真实 Host 行为确定。不能复用旧 Profile 作为静默替代。
3. **Analyzer 摘要进入 Lead Context 的范围**：只摘要最新 Candidate，还是保留有限个可比历史 Profile 的差异？差异必须由 Host 验证身份后形成，还是由 Tuner 自行请求工具结果？
4. **Tuner 专长定义**：Compute / Dataflow / Schedule 的边界和实际 Case 覆盖是否充分；一个跨机制变更如何标记 primary / secondary mechanism？
5. **Lead 决策上下文**：需要给 Lead 哪些历史结果和证据摘要，才能让它自主确定后续 Round 的 Tuner 数量与组合，而不由 Host 注入人数偏好？
6. **Case Memory 的上下文读取量**：每轮历史条目及其来源引用在 Run 记录中保留；后续可根据实际 Run 长度确定顶部当前摘要的字段与长度，以及角色每次读取哪些历史条目，不压掉每轮分析、改动和结果的记录。
7. **并行与调度**：当前 PTOBench checkout 约束下保持串行；若后续 Runner / Bench 增加设备绑定与并发支持，怎样定义公平的设备组与 clean measurement window？
8. **成本记录可用性**：Token、墙钟和角色调用次数哪些能从 backend 原生记录中可靠取得；缺失时如何呈现而不误导？
9. **正式停止标准**：预算耗尽之外，怎样判定机会已验证、无收益或信息增量不足，并确保不因“看起来收敛”而覆盖 PTOBench 事实？
