# PTOmni 整体架构与设计

> 日期：2026-11-12
> 状态：当前完整设计基线，供后续架构讨论和实施拆分使用。
> 本文只描述 PTOmni 自身的目标架构。文中标为“待讨论”的事项尚未冻结，不应在实现中默认为已决定。

## 1. 设计摘要

PTOmni 是一个面向 PyPTO/NPU Kernel 优化的**动态轻量 Agent Team**。它围绕一个 PTOBench Case 形成可验证的优化闭环：本次 Run 的第一个优化 Round 固定启用 Compute、Dataflow、Schedule 三个 Tuner；之后每轮启用哪些 Tuner、启用几个，完全由 Lead 决定，提示、校验和运行时都不偏向多选或少选。每个优化 Round 在 Tuner 修改代码前，由 Host 对 Parent Candidate 采集一份新的 `combined` Profile，并将同一事件交给本轮入选 Tuner 的专长 Analyzer；首版不跨 Round 复用 Profile。Tuner 只读 Parent workspace、只写自己的 workspace，其他 Tuner 的 workspace 对它不可见。PTOBench 提供权威的 correctness、Clean Benchmark 和硬件动作记录；Assembler 综合证据决定本轮交付候选；Curator 把有来源的经验浓缩到当前 Case Memory。遇到高风险、证据冲突或停滞时才启用 Challenger。

“Team”描述的是不同职责和权限，不要求五个 Agent 进程同时运行。角色任务默认顺序调用；除首个优化 Round 固定启动三个 Tuner 外，后续每轮的 Tuner 人数和专长由 Lead 自行决定，不存在推荐人数或自动增减。Assembler 不需要直接采集 Profile 或调用 Analyzer；它根据各 Tuner 的结果包和 PTOBench 验证事实，决定本轮交付哪个 Candidate。PTOmni 不训练一个学习型调度器，也不建立第二套评测、硬件预算或事实账本。

Guidance 由三种不同来源组成：

1. **PTO Wiki** 提供经整理的 PyPTO、编译器、运行时、模型和 NPU 机制资料。知识应按需、短片段、带来源与适用范围地呈现。
2. **PTOAnalyzer** 把某一确切 PTOBench Profile Event 的受保护归档转成可追溯的结构化观测。它只读、离线，不采集 Profile，也不输出自动根因判断。
3. **Case Memory** 保存当前 Case 的近期优化经验、失败条件和未解问题，由 Curator 更新。它不是全局 Wiki，也不是完整对话记录。

三种信息都帮助 Agent 提出更好的假设，但它们不能取代 PTOBench 的实际执行和正式测量。当前 Wiki 内容已整理为离线主题资料；PTOAnalyzer 的九个只读工具已通过 CPU 测试与既有归档回放。PTOAnalyzer 仍需接入正式 PTOmni Host，才会成为 Agent 可调用的在线工具。

## 2. 目标与设计原则

### 2.1 目标

- 让 Agent 基于 Case、Candidate、历史实验和适用的机制资料形成**可证伪的优化假设**，减少没有信息增量的硬件尝试。
- 用动态团队按需组织机制专长，让本轮团队规模和角色调用次数由问题、证据缺口和预算决定。
- 让代码改动、Profile、评测、解释与结论绑定到相同的 Candidate 和 PTOBench Event，便于复查与复现。
- 在有限接口后隐藏知识检索、Profile 身份验证、工具权限、候选隔离、PTOBench 调用和状态恢复等实现细节。
- 允许功能从一个 Case 的最小闭环逐步增加，不要求先造通用 Agent 平台或一次性并行所有模块。

### 2.2 原则

1. **PTOBench 是执行事实的权威来源。** PTOmni 不改写 correctness、Clean Benchmark、硬件动作计数或正式结果。
2. **Profile 是诊断证据。** Profile 不提供 correctness 或 Clean Latency，也不能单独证明根因或加速。
3. **Candidate 写入权唯一。** 每个 Tuner 只写自己的隔离 workspace；Assembler 是本轮唯一候选综合与交付决策者。
4. **Agent 解释与观测事实分开。** 机制解释、知识片段和 Profile 指标各有不同来源与语义。
5. **按需组队。** 角色是逻辑职责，不是常驻进程；本次 Run 的首个优化 Round 固定启用三种 Tuner，后续由 Lead 按当时证据决定团队构成，不默认多选或少选。
6. **确定性地维护事实状态。** PTOBench Event 和 Host 记录是事实输入；State 是可重建的确定性投影；Case Memory 是带引用的短摘要。
7. **读取接口收窄，模块实现做深。** Team Loop 不知道 Wiki 文件布局和 Profile 解析格式；知识、Analyzer、Runner 和状态更新各自封装实现。
8. **缺失信息明确表达。** 不可用、未采集、空数据、损坏数据和不兼容证据不能坍缩成数字零或“没有瓶颈”。

## 3. 当前基础与实现状态

### 3.1 PTO Wiki

当前知识库位于 [`pto_wiki/opt_wiki`](../../../../pto_wiki/opt_wiki/README.md)，包括问题索引 `INDEX.md`、总览和 11 个主题目录。目录下的主题 README 汇总相关内容，原始来源文档保持分开，便于 Agent 查看完整示例、上下文和术语。知识覆盖 PyPTO API / 操作、Kernel 编写、任务图与调度、运行时、性能调优、精度与调试、分布式编程、模型、编译器/IR、NPU 架构与 ISA 等。

这份内容可直接作为 PTOmni 的只读知识源，不需要重新抓取或重建资料库。PTOmni 需要实现的是**运行时读取与上下文控制**：冻结知识快照、按 Case 和环境选取少量相关页面、保留出处与适用范围，并记录 Agent 实际看到的片段。当前目录结构是离线浏览知识库，不等于已有 PTOmni Host 检索 Tool。

### 3.2 PTOAnalyzer

当前实现位于 [`modes/ptomni/pto_analyzer`](../../../ptomni/pto_analyzer/README.md)。Stage 4 已完成九个只读工具的实现与离线验收：Compute、Dataflow、Schedule 各三个。既有回放覆盖 16 份 Profile，5,492 个索引产物哈希前后相同，新增硬件动作为 0；Stage 4 记录 51 项 CPU 测试通过。该状态证明工具实现可在样本归档上离线分析，不证明 PTOmni Agent 已能调用或工具已提升调优效果。

现有工具和权限如下：

| Tuner 专长 | 工具 | 主要观测 |
|---|---|---|
| Compute | `compute_mapping_check` | dispatch program、callable 与 kernel config 映射及源码关联状态 |
| Compute | `compute_unit_activity` | 按 build/rank/dispatch/core 的 PMU 活动计数 |
| Compute | `compute_task_share` | 能可靠关联到依赖图、callable 与 AICore span 的 task 计数 |
| Dataflow | `tile_access_check` | 编译器 Tile-access 提示 |
| Dataflow | `buffer_pressure_check` | MemoryReuse 提示与 Scope 原始计数 |
| Dataflow | `tile_memory_allocation_summary` | AllocateMemoryAddr 产物中的静态分配数量和显式请求字节数 |
| Schedule | `dependency_path_check` | 依赖图 task / edge、深度及端点缺失情况 |
| Schedule | `dispatch_gap_check` | 同一 rank/dispatch/core 上可比 AICore 区间的原始观测间隔 |
| Schedule | `task_distribution_check` | 按 rank/dispatch/core 汇总的 AICore 记录、task token 和区间周期 |

任一工具给出的都是带单位、来源覆盖和解释边界的观测，不是瓶颈判决或优化处方。

Analyzer 已有适合 Host 使用的 Python Interface：`ProfileRef.from_event(session_root, event_seq)`、`open_toolset(tuner, profile_ref)`、`tool_specs`、`initial_summary` 和 `call(name, args)`。它校验确切 Event、Candidate digest、归档索引与保护清单；工具权限由 Tuner 专长静态决定；Lead 没有 Analyzer Tool。当前 `ProfileRef` 要求已完成的 `combined` Profile；因此 PTOmni 初始集成应采用 `combined` 策略，不应在未扩展 Analyzer 契约时改用 split Profile。

Stage 4 明确记录当前**没有 PTOmni Host 调用 `ToolSession` 的入口**。集成应在真实 Host 的原生工具传输处增加薄 Adapter，不创建模拟 Host、第二个 Tool Server 或新的 Profile 采集链。

### 3.3 PTOBench 方法与执行协议

PTOmni 的可执行代码标识为 `ptomni`，方法入口按 [`modes/PROTOCOL.md`](../../../PROTOCOL.md) 实现 `preflight / prepare / run / collect`。实验方法负责 Agent 编排、知识、Analyzer 接线、状态和方法记录；Launcher 负责方法生命周期；Evaluator/PTOBench 负责 Case、Workspace、预算、原始 Profile、正确性、Clean Benchmark 和正式结果。

Agent 使用公共 `ptobench evaluate/profile/fork` CLI。当前 Agent `profile` 成功动作消耗一次硬件动作，但不检查输出 correctness、不生成 Clean Latency、不产生可选 Snapshot；`evaluate` 才能建立 Agent Candidate 的正确性与探索性能结果。官方最终验收由受控 finish 流程单独完成，不应让 Agent 直接改写最终成绩。硬件计数和评测事实均沿用 PTOBench 账本。

Launcher 已按 `mode.yaml` 动态加载方法，不需要为 PTOmni 增加专属分发分支；但当前隔离运行时通过 `evaluator.common.MODE_SOURCE_DIRS` 静态枚举要收集、挂载和纳入完整性保护的方法源码目录，其中尚无 `ptomni`。而 `evaluator.isolation.copy_runtime()` 目前只收集这些 mode 目录的顶层 Python 文件，不会带上现有的 `modes/ptomni/pto_analyzer/` 子包。因此首次以隔离 mode 运行 PTOmni，公共运行时接入需同时纳入 `ptomni` 并包含其子包；Host、角色和工具实现仍放在 `modes/ptomni/`。严格要求零公共代码改动时，当前运行时还不满足条件。

## 4. 领域对象与记录单位

| 对象 | 定义 | 权威来源 / 生命周期 |
|---|---|---|
| **Case** | PTOBench 固定的待优化任务及输入、Oracle、评测约束 | PTOBench；PTOmni 读取，不修改 |
| **Candidate** | 可执行源码与相关编译配置的一个具体版本 | PTOmni 维护工作区和身份引用；PTOBench Event 记录实际被执行的版本 |
| **Round** | 围绕一个连贯决策问题的一次规划、探索、综合、最终候选验证和总结过程 | PTOmni 逻辑分组；不是 PTOBench 硬件动作 |
| **Experiment** | 一个 Tuner 或 Assembler 提交的 Candidate 变体、假设、改动和相关证据 | PTOmni 方法记录；引用本 Round 共享的 Parent Profile Event，以及该实验相关的 Evaluate Event |
| **PTOBench Event** | 一次受管 `profile`、`evaluate` 或 `fork` 的结果记录 | PTOBench 账本；原始事实不可由 Agent 修改 |
| **EvidenceRef** | 指向一个可复查的 Event、Profile 观测、知识来源或 Candidate 身份的引用 | 源记录由各自来源所有；引用进入 ExperimentResult / State |
| **RoundPlan** | Lead 对当前 Round 的问题、角色、动作权限和预算安排 | PTOmni Host 校验后冻结；不能授权超出全局预算或角色能力的操作 |
| **Case Memory** | 当前 Case 的短滚动经验摘要 | Curator 生成，可由事件和来源引用重建；不等同于事实账本 |

不要把 Round、Experiment 和 PTOBench CLI Event 混成一个轮次计数：一个 Round 可含多个 Experiment，一个 Experiment 可含多次 PTOBench Event；Profile 或 Evaluate Event 不自动开启新的 Round。

### 4.1 Candidate 与证据身份

Candidate 的基本身份至少覆盖源码快照摘要和影响代码生成的编译配置。某项观测的可比身份还要带上其 Case / Shape、设备、PyPTO / CANN / 相关软件版本，以及 Profile 或 Evaluate 配置。PTOBench 已提供的 Candidate / Event 身份优先复用，不另建竞争性的权威标识。

任何 Profile、Analyzer 观测、正确性结果和 benchmark 结果都必须引用实际被执行的 Candidate/Event。不同源码、配置或环境的证据不能直接合并为一个结论；比较条件不足时标为 incomparable，并保留原始引用。

## 5. 总体架构

```text
PTOBench Method Protocol
  preflight / prepare / run / collect
                  │
                  ▼
┌──────────────────────── PTOmni Host ─────────────────────────┐
│                                                              │
│  Run Controller / State Machine                              │
│    ├── Context Builder ── Case + Candidate + State           │
│    │                    ├─ Wiki Reader (read-only)            │
│    │                    └─ prior Profile facts / Case Memory  │
│    ├── Role Session Adapter ── Lead / Tuner / Assembler       │
│    │                         ├─ Challenger (on demand)         │
│    │                         └─ Curator (round close)          │
│    ├── Tool Adapter ───────── PTOAnalyzer ToolSession          │
│    ├── Runner ─────────────── ptobench profile/evaluate/fork  │
│    └── Event Ledger + deterministic State + Case Memory       │
└──────────────────────────┬───────────────────────────────────┘
                           │ managed public CLI
                           ▼
                   PTOBench / Evaluator
             Case · Workspace · budget · events
             Profile archive · correctness · clean result
```

PTOmni 分为五个逻辑模块：

1. **Method Host**：遵循方法入口协议，拥有一次 Run 的进程生命周期；创建状态机并协调角色调用。
2. **Team Orchestrator**：根据 RoundContext 调 Lead，校验 RoundPlan，按计划调用 Tuner、Assembler、Challenger 和 Curator。
3. **Guidance Adapters**：Wiki Reader 返回只读知识片段；Analyzer Adapter 将有效 Profile Event 映射到专长工具；State Context 提供当前 Case Memory 与历史证据摘要。
4. **Runner**：校验执行角色、RoundPlan、workspace 与预算，再调用公共 PTOBench CLI；不自行计算评测结果。
5. **State / Recording**：保存方法事件和 Agent 产物；从 PTOBench 事实投影当前状态，并保存 Curator 的短记忆。

这些是职责模块，不要求一一对应独立进程或部署服务。第一版可以由一个 Python Host 和一个本地运行时组成；模块通过少量稳定 Interface 相连，格式解析、授权检查和资源组织留在实现内部。

| 模块 | 面向调用方的 Interface | 模块内部负责 | 不应泄漏给调用方的细节 |
|---|---|---|---|
| Team Orchestrator | `run_round(context) -> round_result` | RoundPlan 校验、角色顺序、触发器、阶段收敛 | Agent backend 命令、会话文件布局、PTOBench 内部状态 |
| Role Session Adapter | `invoke(role, task_context, allowed_tools) -> role_output` | 创建/恢复角色会话、记录输入输出、限制工具权限 | Provider 认证、native session 解析和清理方式 |
| Wiki Reader | `search(query, case_context, limit) -> KnowledgeHit[]` | 冻结快照、索引读取、上下文过滤、来源定位 | Wiki 文件树、索引构建与底层检索算法 |
| PTOAnalyzer Adapter | `open(tuner_specialty, profile_event_ref) -> ToolSession` | ProfileRef 建立、专长权限、工具调用与错误映射 | 原始 Profile 路径、产物解析和 Cursor 编码 |
| Runner | `profile/evaluate/fork(workspace, authorization) -> EventRef` | RoundPlan 权限、workspace 和预算检查、受管 CLI 调用 | PTOBench 锁、Evaluator 命令和原始目录内部结构 |
| State / Recording | `append(event)` / `rebuild(events) -> state` | 追加事件、确定性归约、恢复和归档 | JSONL / JSON 持久化细节与原始归档索引 |

每个 Interface 同时定义身份绑定、权限、排序、不可用语义和成本来源，而不只是函数参数。Wiki Reader 和 PTOAnalyzer Adapter 的实现可分别由假数据/fixture 替代；Team Orchestrator 测试跨越同一 Interface，不需真实硬件或在线模型。

## 6. Agent Team

角色按任务启动和结束。角色名表示输入、权限与输出契约，不暗示独立常驻 Agent、独立模型或必然并行。

| 角色 | 输入 | 可执行动作 | 输出与限制 |
|---|---|---|---|
| **Lead** | RoundContext、剩余预算、已存在的 Wiki / Profile 摘要、Case Memory | 规划和分配下一轮团队，不写代码、不调用 Runner 或 Analyzer | 一个短 RoundPlan；不能改写事实或选择未经 Assembler 验证的 Candidate |
| **Tuner** | RoundPlan 的目标/假设/约束、只读 Parent workspace、自身可写 workspace、相关 Wiki、自己的专长 Analyzer Tool 和本轮共享 Profile | 只读查看 Parent、只写自身 workspace；调用自己的只读 Analyzer Tool；在计划授权范围内请求 Evaluate，不请求 Profile | ExperimentResult；看不到其他 Tuner workspace；不能改 Case / Oracle / Evaluator / PTOBench 账本 |
| **Assembler** | 本轮 Tuner 的结果包、经 Host 提供的候选产物和 PTOBench 验证事实 | 接受一个候选、组合兼容改动、保留父版本，或要求已选团队在现有授权内补充实验 | 综合正确性、可比性能、兼容性、证据质量和集成风险，决定本轮交付和下一轮 Parent Candidate；不必选择单项性能最高的版本，也不必选择自己组合的版本；任何新组合都作为新 Candidate 重新验证。需要改变 Tuner 团队时由 Lead 另开 Round 决定 |
| **Challenger** | 需复查的计划、假设、解释和证据 | 只读审查 | 替代解释、证据缺口和区分性实验建议；不写代码、不运行硬件、不否决 |
| **Curator** | 本轮 Event Ledger 摘要、实验结果、上次 Case Memory | 更新 Case Memory | Round Note；不修改事实、不把推断写成测量结论、不反写全局 Wiki |

### 6.1 Tuner 专长

当前 Tuner 专长暂定为：

- **Compute**：计算表达、冗余、归约、融合与计算布局。
- **Dataflow**：Tiling、数据布局与复用、搬运、Buffer、Pipeline。
- **Schedule**：任务粒度、并行度、Core 分配、依赖与负载组织。

它们是可动态选择的机制标签，不与 Tensor / Tile / Block 一一绑定。本次 Run 的首个优化 Round 固定各启用一个；之后 Lead 可从当前可用专长中选择任意有效组合。Lead 应为每个实验指定一个主要机制与可能受影响的次要机制；跨机制发现记录在 ExperimentResult 中，供后续计划参考。专长覆盖范围须结合实际 Case 的改动能力继续校准。

### 6.2 团队大小与协作开销

- 本次 Run 的第一个优化 Round 固定选择 Compute、Dataflow、Schedule 三个 Tuner。之后每个 Round 的数量和组合由 Lead 自行决定；提示中不放置人数偏好或引导性示例，Host 只做角色是否可用、权限和预算校验，不自动增减 Lead 的有效选择，也不因 Tuner 数量本身要求修改计划。
- 对后续 Round，Lead 可选择任意有效数量和组合的可用 Tuner 专长；架构不设默认人数、推荐人数或“人数越多/越少越好”的策略。若 Lead 不打算启动优化实验，应结束或暂停，而不创建没有 Tuner 的空转 Round。
- 每个 Tuner 只能读取只读的 Parent workspace，并读写分配给自己的 workspace；其他 Tuner 的 workspace 对它不可见、不可挂载、不可访问。Host 仅向 Assembler 提供其决策所需的候选快照、结果包或受控只读引用，不暴露 Tuner 工作区的直接访问权。
- 角色和 Tuner 任务默认顺序执行；这描述执行顺序，不代表推荐任何 Tuner 人数。每个 Round 的硬件动作也经 Runner 串行执行。
- Challenger 仅在触发条件成立时短时运行；不能成为每轮固定步骤。

### 6.3 Workspace 权限与候选选择

workspace 可见性必须由 Host 的进程隔离、挂载范围和文件权限实际执行，不能只靠 Prompt 声明。Tuner Session 只获得 Parent workspace 的只读视图和自己 workspace 的读写视图；不提供其他 Tuner workspace 的路径或挂载。即使 Agent 猜到其他目录路径，隔离层也应拒绝读取和写入。Tuner 的输出通过结构化 ExperimentResult 和 Host 管理的 Candidate 引用交接给 Assembler。

Assembler 的决定对象是“本轮交付候选 / 下一轮 Parent”，不等同于更新全局 `best_candidate`。它可以选择某个已验证 Tuner Candidate、保留 Parent，或将兼容改动组装成新 Candidate。Assembler 可综合正确性、可比的 PTOBench 性能数据、稳定性或兼容性证据、改动范围、证据可信度与集成风险；Profile 只作诊断证据，不形成性能排名。若要求补充实验，只能在 Lead 已选团队的授权范围内执行；要改变 Tuner 组合则由 Lead 开启新 Round 决定。若选择新组装 Candidate，Host 必须先经 Runner 验证。Host 再依据 PTOBench 的正确性与可比评测事实分别更新 `current_candidate` 和 `best_candidate`，因此 Assembler 选作下一轮 Parent 的 Candidate 可以不同于全局最佳测量 Candidate。

## 7. Guidance 设计

### 7.1 PTO Wiki：机制与约束资料

Wiki 的职责是回答“PyPTO、编译器、运行时和目标设备有哪些已知机制、约束与适用条件”。它不回答“当前 Candidate 的实测性能如何”，也不决定改动。

**内容与冻结：** `pto_wiki/opt_wiki` 是主知识源。一次 Run 使用固定的只读快照，至少记录 source tree manifest / 文件哈希、构建或整理版本、Run 中实际提供给 Agent 的页面引用。不得在实验中途自动切换知识版本。方法的 `prepare` 阶段保存只读资源与 manifest，遵循 PTOBench 方法协议。

**检索路径：** 依据 Case 的 module / entry、当前设备与软件版本、Case Memory 和已知瓶颈，先从问题索引和主题目录缩小范围，再选取少量来源页面或片段。PTO Wiki 现有的 [`INDEX.md`](../../../../pto_wiki/opt_wiki/INDEX.md) 可作为问题入口。第一版优先复用现有目录和索引，使用本地关键词/元数据方式定位；不需要向量数据库、在线搜索或整库 Prompt 注入。

**最小 Interface：**

```text
search(query, case_context, limit) -> KnowledgeHit[]
KnowledgeHit = {text, source_path, section, applicability, wiki_revision}
```

`case_context` 至少包含 Case / Entry、设备和可确定的软件版本。结果数量与文本长度受限，保留出处和适用性；找不到合适内容时明确返回空结果。Lead 不拥有自由查询 Tool：Host 在 RoundContext 组装时提供少量相关资料；Tuner 可按需使用只读查询入口进一步定位。查询能力是否也提供给其他角色列为待讨论项。

### 7.2 PTOAnalyzer：Candidate 的结构化 Profile 观测

Analyzer 的职责是把 PTOBench 保存的 Profile 产物变成可复核的观测。它不调用 PTOBench、不读取任意 Agent 路径、不修改 Candidate、不调用 LLM，也不推导瓶颈。PTOBench 采集、归档并记账；Analyzer 绑定一条准确 Profile Event 后离线读取；Tuner 才负责解释和提出改动。

Host Adapter 使用现有 Python Interface，不复制解析器：

```python
from modes.ptomni.pto_analyzer import ProfileRef, open_toolset

profile_ref = ProfileRef.from_event(session_root, event_seq)
tool_session = open_toolset("Dataflow", profile_ref)
specs = tool_session.tool_specs
summary = tool_session.initial_summary
detail = tool_session.call("tile_memory_allocation_summary", {})
```

`ProfileRef` 由 Host 根据 PTOBench 已完成 Event 创建，不由 Agent 传入路径或挑选“最新 Profile”。当前实现校验 Session / Event / Candidate / Artifact Index / PTOBench Protection Manifest，并在读取文件时复核哈希。Cursor 绑定 Profile Event、Candidate、Tuner 和 Tool；明细分页默认 20、上限 50。不可比、缺失、空或损坏的来源应保留其各自状态。

工具调用仅对当前 RoundPlan 启用的 Tuner 开放，并按 Compute / Dataflow / Schedule 的静态权限表配置。Lead、Assembler、Challenger 和 Curator 不直接获得 Analyzer Tool。Lead 可在下一次 RoundContext 中消费由 Host 保存的已有摘要与来源引用；Tuner 的工具结果仍由 Tuner 决定如何解释。

当前 Analyzer 要求完成的 `combined` Profile。首版固定采用以下采集流程：每个有 Tuner 的优化 Round，在 Lead 的 Tuner 组合通过 Host 校验后、任何 Tuner 修改代码前，由 Host / Runner 对该 Round 的 Parent Candidate 采集**一份新的 `combined` Profile**。该 Profile Event 通过各自的专长工具集共享给本轮所有入选 Tuner；不为每个 Tuner 重复采集，也不复用前一 Round 或更早的 Profile，即使 Candidate 身份匹配。Lead 选择的 Tuner 数量不改变每轮一份 Profile 的规则。Profile 额度在启动 Round 前纳入 PTOBench 全局预算校验；无法完成这份 Profile 时，不启动本轮 Tuner 修改流程，也不拿旧 Profile 冒充当前 Parent 的读数。

这次 Profile 是当前 Parent 的共同诊断基线，不是后续实验 Candidate 的测量结果。每个 Tuner 只获得自己的 Analyzer 专长工具，但可针对同一个 Profile Event 离线分析；Assembler 不直接获得 Analyzer Tool，也不负责采集 Profile，可以读取 Host 交付的结果摘要和证据引用。若未来要在一个 Round 采多份 Profile 或改为 split 类型，须先单独修订并验证 Profile 次数和来源契约。

**解释边界：**

- 单个 PMU 计数不等于计算瓶颈；静态分配字节数不等于运行时峰值；依赖数量不等于调度瓶颈。
- Profile 结果不能替代 Evaluate；Profile 延迟、PMU 或静态编译观测不能作为正式性能排名。
- Analyzer 对超大依赖图保留完整观测与分页，但首屏已测得约 20 秒和约 509 MiB 临时峰值；Host 应按需打开相关专长工具并控制重复分析，不把完整高基数明细塞入 Agent Context。

### 7.3 Case Memory：当前 Case 的经验

Case Memory 只覆盖一个 Case，保存最近且有助于后续选择的经验：已验证事实引用、有限定条件的解释、被否定假设与失败原因、未解决问题和后续候选方向。它不重复保存完整 Profile 文件、全部对话或全局 API 文档。

每个正常完成的 Round 调用一次 Curator：在最终 Candidate（或明确保留的 Parent）验证状态记入 Event Ledger 后、Round 进入 `closed` 前。Experiment 或 PTOBench Event 不会单独触发 Curator；恢复时不得重复提交已完成的 Round Note。硬中断或预算耗尽导致 Round 未能进入收尾时，是否恢复后补写基于已提交事实的部分 Note，留待恢复策略确定。所有“已测事实”都应指向 Event / EvidenceRef；“解释”和“建议”单独标记为 Agent 产物。若 Curator 输出失败，PTOBench 事实和 Event Ledger 仍完整，系统可带着旧 Case Memory 结束或恢复。

记忆的最大长度、保留最近几轮、合并/淘汰规则尚未冻结，应通过 Context 窗口与重复尝试数据确定；第一版应设定硬上限并优先保留证据引用和未解决问题。

## 8. Host、Context 和 Agent Session

### 8.1 Host 职责

Host 是一次 PTOmni Run 的控制点。它接收方法协议的请求和 PTOBench 公开运行环境，构造 Context、执行状态转换、调用角色 Session、建立当前角色权限、持有 Analyzer ToolSession、调用 Runner 并记录结果。角色 LLM 不能绕开 Host 直接访问 PTOBench 内部 Session 状态或 Analyzer 归档路径。

Host 的对外依赖尽量少：

```text
invoke_role(role, task_context, allowed_tools) -> RoleOutput
run_profile(workspace, authorization) -> PTOBenchEventRef
run_evaluate(workspace, authorization) -> PTOBenchEventRef
search_wiki(query, case_context, limit) -> KnowledgeHit[]
open_analyzer(tuner_specialty, profile_event_ref) -> ToolSession
```

上述是职责层面的 Interface，不要求第一版逐项暴露成网络 API。Role Session、知识检索和 Analyzer 可由本地 Host 调用；Runner 的硬件执行仍使用 PTOBench 公共 CLI。

### 8.2 Context 组装

Lead 的 RoundContext 包含：Case Contract 摘要、当前 Candidate / Parent 身份、基线和已验证 Best 的 PTOBench 事实、最近 Round / Experiment 摘要、历史 Profile 的 Analyzer 摘要及其身份、Case Memory、Wiki 相关片段、剩余全局预算与当前轮限制。后续 Tuner 人数不由 Host 的默认值或推荐值决定。

Tuner Context 在此基础上增加：已批准的 RoundPlan、目标机制、只读 Parent workspace、自身可读写 workspace、相关源码/编译信息、按需 Wiki 片段、该 Tuner 可用的 Analyzer Tools 与本 Round 新采 Profile 的摘要。Tuner 不接收其他 Tuner 的 workspace 路径、挂载或文件；Host 通过执行隔离强制这一点。

Assembler Context 包含各 Tuner 的 ExperimentResult、Candidate 差异摘要、可比的 PTOBench 事实、Profile 观测引用与剩余预算，不暴露无关的完整原始 Profile 或所有历史对话。

Challenger Context 只包括被质疑的假设、必要的事实与来源、团队提出的解释；默认只读。Curator Context 只包括本轮已提交事实、解释分类、已有 Case Memory 和本轮 Candidate 决策。

Context Builder 应设置 token/记录大小上限；超出时先保留当前 Candidate 身份、最新事实、来源引用和 RoundPlan 约束，再减少旧历史与长明细。Agent 收到的截断或缺失信息要显式标出，不能通过隐藏状态伪装为完整上下文。

### 8.3 Session 执行模型

角色是逻辑任务。首版建议一个受管 Host 顺序调用当前 Agent backend 执行短时角色 Session，并把每次输入、输出、工具授权和 Session 标识记入 Run。是否在多角色间复用 Pi conversation、每个角色创建独立对话，或复用后以提示隔离，是待讨论的上下文设计决定；无论采用哪种模式，都不得将一个角色的写权限或工具权限意外带入另一个角色。

若 Host 启动多个 Agent 子进程，所有进程必须留在 PTOBench 方法拥有的进程组内，确保预算耗尽、中断或异常关闭时由公共生命周期机制完整清理。禁止 detached worker。并行能力不是第一版前提。

## 9. RoundPlan 与 ExperimentResult 契约

### 9.1 RoundPlan

Lead 生成结构化计划，Host 进行确定性校验。计划不得增大 PTOBench 全局剩余预算、授权未启用 Tuner、授权 Lead 执行硬件动作或包含对 Case Contract / Evaluator 的修改。

```yaml
round_id: "round-..."
parent_candidate: "candidate-ref"
decision_question: "本轮要回答的单一决策问题"
hypotheses:
  - id: "hypothesis-1"
    claim: "可证伪的机制假设"
    primary_mechanism: dataflow
    secondary_mechanisms: [schedule]
    evidence_for: []
    disconfirming_observation: "什么结果会推翻假设"
team:
  tuners: "<Lead-selected list of assignments>"
  challenger: {enabled: false, reason: ""}
profile_policy:
  collection: once_before_tuners
  target: parent_candidate
  profile_type: combined
  reuse_previous_round: false
evaluate_policy:
  max_actions: 2
knowledge_topics: ["性能和优化", "API 和操作"]
stop_condition: "候选不可行、证据无信息增量或剩余预算不足"
```

此段是结构示意，不是可直接解析的 YAML 配置；`team.tuners` 的完整条目集合由 Lead 提交。首个优化 Round 必须包含三个专长；之后 Host 不设人数默认、偏好、最低/最高建议或自动增减，只校验 Lead 所选角色是否可用以及相应计划、权限和预算是否合法。此处不展示任何 Tuner 数量的例子，避免暗示人数偏好。Tuner 的动作权限不含 Profile：一份 Parent `combined` Profile 是 Host 在 Tuner 启动前按固定流程采集并分发的。Evaluate 的 Round 内动作上限由 Host 对 PTOBench Event 派生计数，并与全局预算取更严格者；不产生第二套硬件账本。Agent 的预算数字必须与 Runner 执行授权可核对。

### 9.2 ExperimentResult

每个 Tuner 交付结构化结果，使 Assembler 能比较不同 Candidate，又不将解释混进 PTOBench 原始事实。

```yaml
round_id: "round-..."
experiment_id: "experiment-..."
parent_candidate: "candidate-ref"
candidate: "candidate-ref"
primary_mechanism: dataflow
secondary_mechanisms: [schedule]
hypothesis: "本次验证的主张"
change_scope: "实际修改范围及代码差异引用"
events:
  parent_profile: {event_seq: 12, status: completed, candidate: "parent-candidate-ref"}
  evaluate: [{event_seq: 13, status: completed, candidate: "candidate-ref"}]
observations:
  correctness: {status: pass, evidence_ref: "ptobench-event:13"}
  clean_benchmark: {status: measured, value_ref: "ptobench-event:13"}
  analyzer: [{tool: "tile_access_check", evidence_ref: "profile-event:12/tool:..."}]
interpretation: "Agent 对观测的解释；注明不确定性"
failed_or_rejected_variants: []
resource_cost:
  hardware_actions: "由 PTOBench Event 汇总"
  wall_clock: "若运行时可准确采集"
  tokens: "若 backend 可准确提供"
applicability_and_limits: "可迁移条件与限制"
next_question: "后续需回答的问题"
```

状态值要区分 `not_requested`、`unavailable`、`failed`、`not_run`、`incomparable` 和有效结果。若 backend / Evaluator 没有提供某项成本，不补造估值；记录 unavailable。

## 10. 一个完整优化周期

1. **Preflight。** 验证方法配置、backend、模型设置、工具依赖、Wiki 资源版本、`combined` Profile 策略和 PTOBench 运行条件；此阶段不启动硬件实验。
2. **Prepare。** 建立 Run 方法记录，冻结 Agent 配置与提示，归档 Wiki manifest/只读快照；从 PTOBench Context 读取 Case / workspace / budget，不覆盖 Bench 事实或控制文件。
3. **建立初始 State。** 读取当前 Case、Candidate、已有 PTOBench Event、缓存基线和 Case Memory。只有权威基线缺失且预算允许时才由受管 Runner 执行所需动作；不能默认重复基线测量。
4. **构造 RoundContext。** State / Context Builder 取最新候选与证据、压缩 Case Memory，选择相关 Wiki 片段，并展示历史 Analyzer 摘要及其 Event / Candidate 身份。
5. **Lead 规划。** Lead 只读上下文并提交 RoundPlan。首个优化 Round 必须包含三个 Tuner；之后的数量和组合由 Lead 自主决定，系统不推荐或自动增减。Host 检查目标、角色、workspace、预算与权限；校验失败则要求修正一次或终止本轮。
6. **采集本轮 Parent Profile 并分发指导信息。** Host 在任何 Tuner 改代码前，通过 Runner 对 Parent Candidate 采集一份新的 `combined` Profile。成功后，Host 创建 ProfileRef，并为每位入选 Tuner 打开其专长 ToolSession；同一 Profile Event 可被不同专长离线读取。该步骤不复用历史 Profile。Host 同时提供计划相关 Wiki 片段及只读检索入口。
7. **Tuner 探索。** Profile 已就绪后，各 Tuner 在各自隔离 workspace 中提出小范围改动。每个 Tuner 可读 Parent、读写自己的 workspace，不能访问其他 Tuner 的 workspace；它按计划请求 Evaluate，但不自行触发 Profile。
8. **ExperimentResult。** Tuner 提交 Candidate 身份、差异、假设、PTOBench Event、Analyzer 引用、解释和成本。Host 将 Event 事实写入 Ledger，解释另存。
9. **按需挑战。** 若高成本动作即将发生、Tuner 结果冲突、解释与观测不一致、性能回退来源不清或连续尝试无信息增量，Lead 可安排 Challenger 只读检查；其输出是建议，不直接授权动作。
10. **Assembler 决策。** Assembler 综合正确性、可比性能、兼容性、证据质量和集成风险，可选单一候选、组合兼容改动或保留 Parent；它不必选择性能数字最高的候选，也不必选择自己组合的新候选。任何尚未验证的新组合都先经 Runner 执行受管 `evaluate`。
11. **验证与 State 更新。** PTOBench Event 提交后，由确定性逻辑确认 Assembler 所选 Candidate 的正确性并更新 `current_candidate`；另根据已验证且可比的 PTOBench 事实维护 `best_candidate`。两者可以不同，Profile 结果不进入 Clean Benchmark 排名。
12. **总结与循环。** Curator 更新本 Case Memory；Lead 基于新状态决定下一 Round、转向、暂停或停止。新的决策问题或超出当前计划边界的补充实验开启新 Round。
13. **Collect。** 记录实际 Agent Session、最终 Prompt / 配置、Wiki 暴露、Analyzer 工具调用、RoundPlan、ExperimentResult、方法日志与状态摘要。保留 PTOBench Event / Candidate 引用，不复制或重写权威结果。
14. **正式完成。** Run 关闭后由 PTOBench / 实验管理流程根据合法 Snapshot 执行正式 finish 与最终验证。PTOmni 不直接提交 final score。

## 11. Runner 与 PTOBench 执行规则

Runner 是 PTOmni 与 PTOBench 执行面的唯一方法侧 seam。它负责检查调用角色、RoundPlan 授权、workspace 身份和动作额度，再调用公共 `ptobench profile`、`ptobench evaluate` 或 `ptobench fork` CLI，并返回可引用的 PTOBench Event。它不执行自定义 NPU 命令、不调用底层 Evaluator 私有接口、不复制 PTOBench 的正确性或性能逻辑。

执行约束：

- **Baseline** 只在缺乏可用、同身份的权威参照时建立；不能盲目重复测量。
- **Profile** 每个有 Tuner 的优化 Round 由 Host 在启动 Tuner 前对 Parent Candidate 采集一次新的 `combined` Profile；本轮入选 Tuner 共享这一个 Event。首版不允许以历史 Profile 代替本轮采集，也不让 Tuner 自行请求重复 Profile。它消耗一次硬件动作；失败、中断和预算预留依 PTOBench 账本规则记录。Profile 不做 correctness 或 Clean Latency。PTOAnalyzer 对同一 Event 的多次离线 Tool 调用不增加硬件动作。
- **Evaluate** 用于候选正确性与探索性 Clean Benchmark。当前探索 Evaluate 的测量由 PTOBench 控制；Agent 不提供测量轮数。官方 finish 的测量和 Snapshot 规则也由 PTOBench 控制。
- **最终候选** 只有经过正确性校验才能成为 Best / 正式交付版本。Assembler 组合任何修改后必须重新验证。
- **Profile 对比** 只有 Candidate、Shape、设备、Profile 配置和环境身份兼容时才有解释意义。即便兼容，也只是诊断对照。
- **PTOBench 失败 / 中断** 由 Bench 记录其动作与执行状态。Host 不因未收到 CLI JSON 就推断动作未发生，也不绕开账本重试。
- **并行** 需同时满足 Tuner workspace 独立、物理设备租约不重叠、PTOBench 执行域支持并行。当前同一 PTOBench checkout 的 NPU CLI 实验按串行设计；在 Bench 明确支持并验证前，不实现多个独立动作的并发执行。
- **锁** PTOBench 自身执行锁与外层设备租约目的不同。Runner 不重复获取 PTOBench 内部锁，也不以增加锁或复制 checkout 的方式绕过现有执行约束。

所有 `run` 子进程留在方法拥有的进程组内，以便预算耗尽、中断或异常退出时清理。方法一次运行不重置 Session 或 PTOBench 预算。

## 12. State、Event Ledger 与持久记录

### 12.1 事实与派生信息

- **PTOBench Events**：Profile / Evaluate / Fork 的权威动作记录；仅由 Bench 更新。
- **PTOmni Event Ledger**：追加记录 RoundPlan、角色执行、Candidate 变更引用、Wiki / Analyzer 暴露、错误、Assembler 决策和 Case Memory 更新；PTOBench 事实以 EventRef 引用，不复制为另一份权威记录。
- **Progress State**：通过确定性 reducer 从 PTOBench Events 与 PTOmni Ledger 计算当前 Candidate、Best、预算余量、活跃 Round、完成状态和可用 EvidenceRef。可重建，不能由 LLM 直接编辑事实字段。
- **Case Memory**：Curator 生成的派生摘要，保存内容版本和来源引用。它可以由 LLM 生成，但只能作为后续上下文，不能覆盖 Ledger 或 Bench 结果。
- **Agent Artifacts**：角色原始会话、实际上下文、工具调用、提示与解释；作为可审计记录，不当作测量事实。

首版可在 Run 的 `method/` 或 `agent/` 目录以 JSONL / JSON 文件保存，采用原子写入和显式 schema version；不先引入数据库或跨 Case 服务。收集时把应归档内容冻结并声明给方法协议。每条 Candidate / Event / Wiki / Tool 记录需可通过引用找到源对象；保密凭据不得写入记录。

### 12.2 状态最小字段

```yaml
schema_version: 1
case_ref: "ptobench-case-ref"
baseline_candidate: "candidate-ref"
current_candidate: "candidate-ref"
best_candidate: "candidate-ref-or-null"
active_round: "round-id-or-null"
round_status: idle | planning | executing | assembling | verifying | closed
remaining_budget_ref: "ptobench-session-state"
latest_events: []
evidence_refs: []
case_memory_ref: "memory-version"
stop_status: continue | stop | budget_exhausted | blocked
```

Round 的建议状态转移为 `planning -> executing -> assembling -> verifying -> closed`；在规划前为 `idle`。只有本轮有效 Candidate 已由 Assembler 选择或明确保留父 Candidate，且最终验证状态已记录，才能进入 `closed`。State reducer 拒绝跳过执行授权或把未验证 Candidate 设为 Best。失败/中断可形成带原因的关闭状态，或按 PTOBench 已提交 Event 恢复；恢复时不重放硬件命令。

Assembler 决定本轮交付候选及下一轮 Parent；Host 在候选通过要求的正确性验证后才将它写入 `current_candidate`。如果所选候选验证失败，保留此前有效的 Parent / current 状态并记录失败。`best_candidate` 则由确定性逻辑根据 PTOBench 已验证且可比的评测事实维护，不由 Assembler 直接设置；因此下一轮 Parent 可以是一个审慎选择的候选，而全局最好测量结果仍另行保留。

预算权威仍是 PTOBench Session。`remaining_budget_ref` 只指向 / 缓存 PTOBench 当前公开结果，不成为第二计数器。跨进程恢复以已提交 Event 和方法日志为准；未提交的 Agent 文字不能当成已执行动作。

## 13. 方法入口、提示和权限

PTOmni 作为 `modes/ptomni/` 方法实现，`mode.yaml` 使用 `id: ptomni`。入口脚本按方法协议处理 `preflight / prepare / run / collect`，通用 Launcher 不解释 PTOmni 的角色、Round 或知识资源。

- `preflight` 校验 backend / 模型 / 版本、PTOmni 配置和本地知识 / Analyzer 依赖；无硬件动作。
- `prepare` 冻结 Prompt、Agent profile、Wiki 快照与 manifest，生成只读资源附件和 provenance 记录。
- `run` 在注册 workspace 中由 Host 编排所有角色；PTOBench 操作只经公共 CLI；Agent 子进程保持在方法进程组。
- `collect` 收集完整原生会话、实际曝光的知识和工具、工具输出、状态与错误记录；不补造 Agent 原生接口未提供的 Token 或行动数据。

角色权限由 Host 授予，不仅依赖 Prompt 声明：

| 能力 | Lead | Tuner | Assembler | Challenger | Curator |
|---|---:|---:|---:|---:|---:|
| 读取当前 State / RoundContext | 是 | 计划所需子集 | 本轮结果子集 | 审查所需子集 | 本轮结束上下文 |
| 查询/接收 Wiki | 接收 Host 组装片段 | 接收片段；可按需查询 | 默认无 | 默认无 | 默认无 |
| PTOAnalyzer Tools | 否 | 仅当前专长 | 否 | 否 | 否 |
| 修改 Candidate | 否 | 只读 Parent、只写自身 workspace | 仅 Host 提供的组装 workspace（产生新 Candidate） | 否 | 否 |
| 请求 Profile | 否 | 否；由 Host 在每个优化 Round 开始时统一采集 | 否 | 否 | 否 |
| 请求 Evaluate | 否 | 计划授权范围内 | 最终候选验证由受控流程提交 | 否 | 否 |
| 修改 PTOBench 事实 / 预算 | 否 | 否 | 否 | 否 | 否 |
| 写 Case Memory | 否 | 否 | 否 | 否 | 是，仅追加版本 |

方法自有 Wiki、提示、backend 配置和相关文件通过 `prepare` 的只读 archive 保护并记录哈希；运行中可变的 Round 日志、Case Memory 和事件在 `collect` 提交，不能在 `prepare` 时作为冻结附件。公共 `.benchmark_context` 与 Case 文件仍按 PTOBench 协议只读使用。

按 PTOBench 方法协议，Host 新生成的 Agent Prompt、任务导览和 CLI 使用说明采用简明英文；Wiki 内已有来源按原文保留。方法自身的架构和运行记录可用结构化格式，不改变原始知识内容。

## 14. 异常与降级

| 问题 | 处理 |
|---|---|
| Wiki 检索无匹配 / 版本不适用 | 返回无匹配或适用范围；继续使用 Case 与评测事实，不伪造知识结论 |
| 本 Round Parent Profile 未完成 | 记录对应状态和 Event；不创建 ProfileRef、不复用旧 Profile，也不启动本轮 Tuner 修改；报告 Lead 并结束或按新计划重新开始 |
| Profile Event 不完整或 Candidate 身份不符 | Analyzer 拒绝打开；不尝试扫描别的归档或路径；标记 unavailable / incomparable |
| Analyzer Tool 解析部分来源失败 | 保留其他工具 / 来源覆盖；相关字段标为缺失或解析问题，不作为零值 |
| Wiki / Analyzer Host Adapter 错误 | 不自动触发额外硬件动作；保留错误和影响范围，由 Lead 决定是否可继续 |
| Tuner 编译或 Evaluate 失败 | PTOBench 事件和 Candidate 保留；记录失败类型与假设判读，不把失败候选交付 |
| Tuner / Assembler 输出无效 | Host 做结构校验；要求有限次数修正，之后按失败结果关闭或回到上个已验证 Candidate |
| Curator 失败 | 使用上一个有效 Case Memory；事实状态不受影响，并记录收尾不完整 |
| Run 被中断或预算耗尽 | 由通用生命周期清理进程；已提交 PTOBench Event 保留；不根据残缺日志宣称动作成功 |

各步骤的重试上限和哪些基础设施故障可重试需要结合真实 Host 行为确定。任何重试均先检查 PTOBench Ledger，避免重复产生硬件动作。

## 15. 安全、审计与可复现性

- Agent 只在 PTOBench 注册 workspace 工作；Tuner Session 只挂载只读 Parent 和自身可写 workspace，不能读取或写入其他 Tuner workspace，也不能读取其他 Run 的 Candidate、Session 或受保护目录。此限制须由隔离执行环境实际强制。
- Agent 不接收 PTOBench sealed 路径、protection manifest 原始文件或可自行选择归档的接口；ProfileRef 由 Host 绑定确切 Event。
- PTOAnalyzer 的工具参数不接受任意文件路径；Cursor 只续读授权 ToolSession 中的稳定排序明细。
- Wiki 资源和提示不可由 Agent 在 Run 中修改；来源文件哈希、版本和实际暴露片段可归档。
- Candidate、Case Contract、Oracle、Evaluator、PTOBench 账本与正式结果的保护规则由 Bench 执行；Host 不提供旁路。
- API key 等认证信息仅经既有 Provider 进程环境提供；不进入 Prompt、方法记录或 archive。
- 收集真实 Agent Session、实际模型设置、Role 输入/输出、工具注册/调用、Wiki 片段引用、Analyzer 结果引用、Run 配置和成本；原生 Agent 若不暴露某类信息，就标记 unavailable。
- 同一组实验固定模型 / backend 配置、Wiki snapshot、Profile strategy、Case 和评测设置；差异环境明确标记，禁止无说明合并。

## 16. 验证策略

验证应按 Interface 分层，CPU 测试覆盖 Host、State、Wiki 与 Analyzer Adapter，不因测试而启动 Agent 或硬件。

1. **协议与 Host 测试**：四种方法操作及 JSON 契约、method process 生命周期、预算 / 退出 / 中断清理、错误归档。
2. **State 测试**：Round 状态机转移、重复 Event、Candidate 身份、原子提交、从 Ledger 重建、未提交动作恢复。
3. **Team 权限测试**：Lead 无执行 Tool；首个优化 Round 必须启用全部三个 Tuner，后续任意有效 Tuner 组合均原样接受且不做人数引导；Tuner 只看到本专长 Analyzer Tool，只读 Parent、只写自身 workspace，无法枚举或访问其他 Tuner workspace；Assembler 的新 Candidate 强制验证；Curator 无事实写入权限。
4. **Wiki 测试**：冻结 manifest、索引跳转、来源引用、设备 / 软件版本适用性、空结果、限量片段和 Run 记录可追踪性。
5. **Analyzer Adapter 测试**：使用 PTOAnalyzer fixture Profile 验证 `ProfileRef` Event 绑定、角色权限、摘要、Tool 调用、Cursor 翻页、来源覆盖、失败传播和只读性；不访问 NPU。
6. **Runner 测试**：使用可注入的 fake Runner 验证 RoundPlan 权限、额度和 Event 记录；另使用真实 PTOBench CLI 的受控测试验证 Session / workspace 接口。
7. **离线回放**：对既有 Profile 运行 Analyzer 工具，结果与当前 Stage 4 离线报告一致；不新增 hardware action。
8. **端到端硬件验证**：只有在 Agent Host / 工具接线稳定、Case 与设备窗口明确后开展，先跑一个代表 Case；按独立授权和 PTOBench 正式账本进行，不将小样本当作效果统计结论。

## 17. 分阶段实施路径

以可用端到端闭环为先，每阶段都让模块通过真实接口连接；Wiki 和 Analyzer 不必重新开发其已经完成的内容。

### 阶段 0：冻结最小共同契约

确定 Candidate / Event 引用、RoundPlan、ExperimentResult、Case Memory 版本、状态提交和 Runner 授权规则。保持结构最小，不因以后可能扩展而建通用 Agent 框架或数据库。

### 阶段 1：PTOmni Host 与团队闭环骨架

实现方法入口、Host、角色权限和状态流程；可先用 fake Runner / Analyzer 做 CPU 集成验证，但不能把单 Tuner 作为实际运行时默认。真实优化流程的首个 Round 固定启用三个专长 Tuner，并由 Host 在改代码前采集和共享一份 Parent `combined` Profile；后续 Round 的选择由 Lead 决定且不受人数偏好影响。角色逻辑可用短时 Pi Session 执行，硬件动作使用公共 CLI。

### 阶段 2：接入已整理 PTO Wiki

冻结 `pto_wiki/opt_wiki` 快照，复用现有索引与主题目录，接入有界本地检索和来源记录。先做 CPU 测试和资源可追溯性，再提供给 Lead Context 与按需 Tuner 查询。

### 阶段 3：把已有 PTOAnalyzer 接入 Host

在 Host / Pi 原生工具调用处建立薄 Adapter。Profile 使用 `combined`；Host 通过成功 Profile Event 创建 ProfileRef，并只向已授权的 Tuner 专长注册对应工具。用现有 fixture 和只读档案验证，不重写 Analyzer 工具或另建 Tool Server。

### 阶段 4：完善动态决策和资源策略

根据实际执行轨迹改善 Lead 可用的证据上下文、Challenger 触发、Profile 预算管理、上下文缩减、Case Memory 长度及停止条件。不要在 Host 中增加偏向更多或更少 Tuner 的默认、评分或自动改写；先观察 Lead 的团队选择和结果，再判断是否需要调整提示信息。

### 阶段 5：小规模受控端到端验收

在固定配置和 PTOBench Case 上检查候选正确性、Bench 事件可追溯性、Profile / Analyzer 身份正确性、Wiki 来源和暴露记录、动作预算、Run 收尾与最终 finish。之后再确定更大规模效果评估方法。

## 18. 明确的非目标

- 不实现通用多 Agent 平台、长期驻留的固定 Agent 群或跨 Case 自主学习系统。
- 不实现向量数据库、知识图谱、在线知识采集或 PTOAnalyzer 的第二个 Tool Server。
- 不重写 PTOAnalyzer 已验收的离线 Parser / Tools，不让 Analyzer 控制 Profile 采集。
- 不以 Profile 替代 PTOBench correctness / Clean Benchmark，不将 Analyzer 观测包装成性能根因。
- 不允许多个 Tuner 共享一个可写 Candidate，不在 PTOBench 并发能力未明确支持时并行硬件动作。
- 不维护独立于 PTOBench 的硬件动作计数或正式分数。
- 不要求首版具备自动跨 Case 知识迁移、学习型团队规划、复杂 DAG 搜索或大规模候选并行；首版也不预设后续 Round 的 Tuner 人数。

## 19. 待讨论与决策清单

以下问题不会阻止架构基线成立，但实施前或首轮轨迹后应逐项确认：

1. **Role Session 的上下文生命周期**：各角色使用独立会话还是共享单一 Pi 会话；如何保留必要历史又避免权限串线和上下文膨胀？
2. **Wiki 的查询责任**：Lead 只收 Host 预置片段、Tuner 是否获得原生搜索 Tool、Assembler 是否需要读取 Wiki 引用？建议先给 Lead 有界 Context、给 Tuner 按需查询，其他角色默认不查询。
3. **Profile 失败与预算不足时的恢复**：固定规则是每个优化 Round 在任何 Tuner 改代码前，对 Parent 采集一份新的 combined Profile；当 PTOBench 失败或预算不足时，应如何恢复或结束 Round，需结合真实运行状态机确定。不能复用旧 Profile 作为静默替代。
4. **Analyzer 摘要进入 Lead Context 的范围**：只摘要最新 Candidate，还是保留有限个可比历史 Profile 的差异？差异必须由 Host 验证身份后形成，还是由 Tuner 自行请求工具结果？
5. **Tuner 专长定义**：Compute / Dataflow / Schedule 的边界和实际 Case 覆盖是否充分；一个跨机制变更如何标记 primary / secondary mechanism？
6. **Lead 决策上下文**：需要给 Lead 哪些历史结果和证据摘要，才能让它自主确定后续 Round 的 Tuner 数量与组合，而不由 Host 注入人数偏好？
7. **Case Memory 上限与保留策略**：最多保留多少轮或 Token；何时折叠旧事实；如何保留引用同时避免重复写入过期经验？
8. **并行与调度**：当前 PTOBench checkout 约束下保持串行；若后续 Runner / Bench 增加设备绑定与并发支持，怎样定义公平的设备组与 clean measurement window？
9. **成本记录可用性**：Token、墙钟和角色调用次数哪些能从 backend 原生记录中可靠取得；缺失时如何呈现而不误导？
10. **正式停止标准**：预算耗尽之外，怎样判定机会已验证、无收益或信息增量不足，并确保不因“看起来收敛”而覆盖 PTOBench 事实？
