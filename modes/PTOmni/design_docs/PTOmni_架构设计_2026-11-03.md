# PTOmni 架构设计

> **版本**：2026-11-08 · Tuner Tool 分配与执行流修订版（沿用稳定文件名）
> **范围**：只描述 PTOmni；不修改 PTOBench 实现，也不依赖 `archeved` 目录。
> **定位**：目标架构，不代表所有功能已经实现。

## 1. 设计目标

PTOmni 是一个以实证证据为中心的 NPU Kernel 优化团队。它的重点不是增加 Agent 数量，而是用更少的无效尝试，更快判断下一项值得验证的优化假设。

PTOmni 对应论文中的两项设计：

- **Optimization Guidance**：把离线知识、结构化 Profiling 和当前 Case 的历史经验整理成可使用的证据。
- **Adaptive Team**：根据当前瓶颈、证据缺口和优化进展，动态安排 Tuner、Challenger 等能力。

PTOmni 不预设“更多 Agent 一定更好”。团队规模、Profile 次数和硬件实验都应由当前证据和预算决定。

## 2. 当前角色命名

PTOmni 当前采用下面五个逻辑 Agent 角色。角色是职责，不要求五个长期运行的进程；同一个 Pi Session Runner 可以按不同任务提示执行它们。

| 角色 | 核心职责 | 为什么使用这个名字 |
|---|---|---|
| **Lead** | 定义本轮目标、预算和团队计划，决定继续、转向或停止 | 简短，表达方向负责人 |
| **Assembler** | 综合多个 Tuner 的结果，选择、组合或放弃候选，并负责本轮最终交付决策 | 负责把有效改动组装成一个经过验证的本轮交付版本；不要求亲自实现每项优化 |
| **Tuner** | 针对一个优化假设修改候选并进行真实实验；可以有多个并行 Tuner | 比 `Perf` 更准确地表达“调优并验证” |
| **Challenger** | 在高风险、结果冲突或搜索停滞时挑战假设和替代解释 | 保留清楚且有辨识度的名字 |
| **Curator** | 整理事实、失败条件和可复用经验，更新当前 Case Memory | 保留；它负责蒸馏经验，不负责改写事实 |

`Runner` 是执行与资源调度模块，不是 Agent 角色。它负责调用 PTOBench CLI、分配设备、检查权限和记录执行事件。

不再使用以下容易造成误解的命名：

- **Picker**：暗示只从候选中选一个，无法表达综合多个 Tuner 的兼容改动。
- **Perf**：容易被理解为单纯的性能测量器，无法体现“提出假设、改代码、验证”的完整工作。
- **Dev**：含义过宽，容易让人以为该角色亲自完成所有代码修改；实际改动由 Tuner 在隔离 workspace 中探索，最终角色负责集成和版本决策。
- **Synth**：简短，但含义不够直观；`Assembler` 更直接地表达把兼容改动组织成候选版本的职责。
- **HW**、**Review**：不作为固定 Agent。硬件分析可以由 Tuner 或 Challenger 按需承担；实验计划审查是 Lead 的计划门槛和 Runner 的约束检查。
- **Supervisor / Owner / Specialist**：这是论文叙事中的抽象职责，PTOmni 实现统一使用 Lead / Assembler / Tuner，避免同一角色有两套名称。对应关系为：Lead≈Supervisor，Assembler≈Owner，Tuner≈Specialist。

### 2.1 品牌名与代码标识

方法的展示名保持 **PTOmni**；实现时使用小写代码标识 **`ptomni`**。未来的可执行 mode 应采用 `modes/ptomni/`、`mode.yaml` 中的 `id: ptomni`，实验配置写 `mode: ptomni`。PTOBench 当前加载器只接受小写 mode ID，并要求它与 mode 目录名及 `mode.yaml` 的 ID 一致（见 [`launcher/methods.py`](../../../launcher/methods.py)）。

当前 `modes/PTOmni/` 只存放设计文档和历史 artifact，不是 Python 包或可执行 mode；不要用它作为运行时代码的 import 路径。文档、论文和面向用户的输出继续使用 **PTOmni**。

## 3. 总体架构

```text
Offline KB / Case Memory / Progress State
                    │ existing context
                    ▼
                 Lead ──RoundPlan──> 已启用的 Tuner(s)
                                          ▲
已有 Profile ──只读证据──> PTOAnalyzer 专属 Tools
                           Compute / Dataflow / Schedule

Tuner workspace ──profile/evaluate 请求──> Runner ──受管 CLI──> PTOBench
       ▲                                      │                    │
       └────────────测试结果与记录─────────────┘                    └──事实──> Event Ledger
       │                                                                    │
       └── ExperimentResult ──> Assembler ──最终候选验证请求──> Runner       ▼
                                                               │      Progress State
                                                               └──> PTOBench
                                                                    Check / Clean Bench

Event Ledger ──> Curator ──> Case Memory ──> Lead
Challenger* ──只读审查──> Lead / Tuner / Assembler
* 只在触发条件满足时启用；没有代码写入、实验执行或否决权限
```

架构分为四个平面：

1. **Guidance 平面**：提供与当前 Case、设备和候选身份匹配的知识与证据。
2. **Team 平面**：Lead 组织本轮工作，Tuner 探索，Assembler 综合并决定交付版本，Challenger 按需质疑，Curator 总结。
3. **Execution 平面**：Runner 统一执行 PTOBench CLI 和设备调度。
4. **State 平面**：保存客观事件、候选身份、预算和 Case Memory。PTOBench 是正确性、正式性能和硬件计数的权威来源。

## 4. 角色职责与权限

### 4.1 Lead

Lead 只消费状态层预先提供的 RoundContext，包括当前 Candidate、PTOBench 结果、已有 Profile 分析、Case Memory、相关知识片段和剩余预算；它不调用额外的信息查询 Tool。Lead 基于这些已有信息生成简短的 `RoundPlan`，不持有 PTOAnalyzer、Runner 或 PTOBench Tool，也不请求或启动真机动作。每个 Round 只围绕一个连贯的决策问题；多个 Tuner 可以检验该问题下彼此相关的假设或候选方案，不应把无关优化合并进同一轮。计划至少说明：

- 本轮要回答的决策问题及其性能瓶颈；
- 可证伪的优化假设；
- 允许的改动范围和候选数量；
- 预期观察信号与推翻条件；
- 是否允许被启用的 Tuner 请求 Profiling、预算上限，以及是否启用 Challenger；
- 本轮的时间、Token 和硬件预算。

Lead 只规划和分配权限边界，不调用执行接口；它不直接改写 PTOBench 事实，也不代替 Assembler 选择最终 Candidate。

### 4.2 Tuner

Tuner 是实际修改候选并执行优化实验的角色。当前暂定三种**机制专长**：Compute、Dataflow、Schedule。它们是 Tuner 的能力标签，不是三个必须常驻的独立 Agent；每轮按问题需要启用相应专长。

| 专长 Tuner | 主要关注 | 典型优化方向 |
|---|---|---|
| **Compute Tuner** | 计算表达和计算结构 | 计算重组、冗余消除、融合、归约与计算布局 |
| **Dataflow Tuner** | 数据访问与片上执行 | Tiling、数据布局与复用、搬运、Buffer、Pipeline |
| **Schedule Tuner** | 并行执行与任务组织 | 任务粒度、Core 分配、并行度、负载均衡与调度 |

三种专长不与 Tensor / Tile / Block 一一对应。一次改动应标注一个主要机制和可能受影响的次要机制：例如 Tile 调整主要属于 Dataflow，也可能改变 Schedule 的任务数量和并行度。Tuner 可以跨层分析，Lead 只根据当前问题选择必要的专长，不要求每轮调用全部三种 Tuner。专长名称和边界仍是暂定设计，应结合 Case 中实际可控的优化机制校准。

每个 Tuner：

1. 接收同一份 RoundPlan 中分配的假设和约束，以及主要/次要机制标签；
2. 在独立 workspace 中修改候选；
3. 使用专长对应的 PTOAnalyzer Tools 检查已有 Profile；若 RoundPlan 允许且证据不足，可通过 Runner 请求 `profile`；
4. 通过 Runner 请求 `evaluate` 验证候选；
5. 返回结构化的 `ExperimentResult`，让 Assembler 能横向比较不同 Tuner 的结果。

`ExperimentResult` 至少包含：

```yaml
round_id: "..."
experiment_id: "..."
parent_candidate: "..."
candidate: "..."
primary_mechanism: compute | dataflow | schedule
secondary_mechanisms: []
hypothesis: "..."
change_scope: "..."
correctness:
  status: pass | fail | not_run
  evidence_ref: "..."
clean_benchmark:
  status: measured | not_run
  result: "..."
  evidence_ref: "..."
profile:
  status: measured | not_requested | unavailable
  evidence_ref: "..."
interpretation: "..."
resource_cost:
  hardware_actions: "..."
  wall_clock: "..."
  tokens: "..."
failed_or_rejected_variants: []
applicability_and_limits: "..."
next_question: "..."
```

PTOBench 原始结果和 Agent 对结果的解释必须分开保存；失败、未测和不可比结果应明确标记，不能填成推测值。字段表达最低交接信息，不要求第一版固定为 YAML。

Tuner 可以实际修改代码并执行实验，但只能写自己的隔离 workspace，不能写入其他 Tuner 或正式 Candidate 的 workspace。它不能修改 Case Contract、Oracle、Evaluator、预算或 PTOBench 账本，也不能绕过 Runner 直接启动 NPU 命令。

多个 Tuner 可以并行准备和实验，但前提是 workspace 独立、设备租约不重叠、PTOBench 执行域允许并行。并行是资源调度结果，不是 Tuner 的直接权限。

### 4.3 Assembler

Assembler 是本轮的**综合者和最终交付决策者**，不是简单的 Picker。它读取所有 Tuner 的结果包，比较：

- 正确性和编译状态；
- Clean Benchmark 与 Profile 证据；
- 假设是否得到支持；
- 改动之间是否兼容；
- 硬件、风险和剩余预算；
- 结果是否足以支持下一轮方向。

Assembler 可以：

1. 接受一个 Tuner 候选；
2. 组合多个兼容的 Tuner 改动；
3. 拒绝所有候选并保留父版本；
4. 要求一次有明确目的的补充实验。

如果 Assembler 组合或实质修改了候选，组合结果必须作为新的 Candidate/Experiment 重新经过 PTOBench 验证。若候选与已验证版本完全一致，且测量配置和环境身份相同，可按 PTOBench 规则复用已有证据。Assembler 不能修改测量事实，也不能把未通过正确性检查的版本标记为通过。最终 Candidate 只有在验证完成后才能进入下一轮或更新 Best。

Assembler 的权限边界是：它拥有本轮最终版本的决策权，不能把决策权下放给某一个 Tuner；但它也不能用主观偏好替代 PTOBench 的客观验证。

### 4.4 Challenger

Challenger 不是常驻的反对者，也不评价某个 Agent 的表现。它审查的是**优化假设、证据解释和实验决策**，目标是尽早发现可能导致无效硬件尝试的推理缺口。以下情况可考虑启用：

- 需要支付较高硬件成本前；
- 多个 Tuner 的假设或结果互相冲突；
- 性能下降的原因不清楚；
- 连续尝试没有信息增量；
- 准备放弃一个仍有价值的优化机会。

它输出替代解释、关键证据缺口、建议的判别实验和可能结果的判读方式。当前约定 Challenger 只读、不写代码、不跑实验，也没有否决权；它不能修改 Candidate 或 PTOBench 事实。Lead 决定是否安排建议中的实验，Tuner 负责执行，Assembler 根据 PTOBench 结果决定候选交付。具体触发门槛与审查输出格式仍待讨论。

### 4.5 Curator

Curator 在本轮最终 Candidate 完成验证后运行一次，读取本轮的客观事件和已有 Case Memory，输出简短的 Round Note 并更新当前 Case Memory。记录至少区分：

- 已观察到的事实；
- 有证据支持但仍有限定条件的解释；
- 被否定的假设和失败原因；
- 尚未解决的问题；
- 下一轮可能值得检查的方向。

Curator 不能改写 PTOBench 结果、Candidate 状态或硬件计数，也不能把推测写成已验证结论。它不向 Offline Knowledge Base 反写 Case 特有经验。

## 5. Guidance 设计

### 5.1 Offline Knowledge Base

知识库保存经核验的 PyPTO、PyPTO-Lib 和目标 Ascend 硬件资料。查询必须带上 Case、设备和软件版本等上下文，返回短片段、来源定位和适用范围；不把整库注入每个 Agent。

知识库回答“有哪些可能的机制和约束”，不能替代真实候选的正确性和性能验证。一个评测批次内使用固定版本的知识快照，避免知识版本变化影响比较。

### 5.2 Structured Profiling

Profiling 是按需获取的结构化证据，不是单独的智能体。它应复用实际 PyPTO/PTOBench 环境提供的分析产物，并标明：Candidate 身份、源码和编译配置、Shape、设备、软件版本、Profile 模式、缺失项和质量标记。

Profile 结果用于解释机制和缩小搜索范围；Clean Benchmark 才用于正式性能比较和 Best 更新。只有身份和环境可比时，才允许比较两个候选的 Profile。

PTOBench CLI 与 PyPTO 负责受控采集和原始产物归档；PTOAnalyzer 只整理这些证据，不另建采集链。Lead 只能消费已有分析结果；被启用的 Tuner 可使用自己的只读 Analyzer Tools，并在 RoundPlan 许可范围内通过 Runner 请求 Profile。工具候选及职责见 [PTOAnalyzer 设计与验证计划](../../ptomni/pto_analyzer/README.md)。

### 5.3 Dynamic Case Memory

Case Memory 是当前 Case 的短滚动经验，由 Curator 更新，并引用 Round、Experiment 和 Evidence ID。它不是全局知识库，也不是完整对话存档；应优先保留能减少重复尝试的证据、失败条件和未解决问题。

Guidance 的最小闭环是：

```text
Case / Candidate
  → 检索相关知识与历史
  → Lead 根据现有信息形成 RoundPlan
  → 被启用的 Tuner 按计划需要通过 Runner 请求 Profile
  → Tuner 用专属 Analyzer Tools 解释证据并实验
  → Assembler 使用 Tuner 结果和 PTOBench 验证做交付决策
  → Curator 把结果写回 Case Memory
```

## 6. Round、Experiment 与 PTOBench CLI Test

### 6.1 概念边界

- **Round**：一个围绕单一、连贯决策问题的优化周期；问题可涉及一个或多个机制专长，但不应混入无关优化。从 Lead 发布 RoundPlan 开始，经若干相关 Tuner Experiment、Assembler 综合、最终验证和 Curator 总结后结束。
- **Experiment**：一个独立的候选变体及其代码变化，关联父/子 Candidate、Hypothesis、Evidence 和成本。
- **PTOBench CLI Test**：一次 `evaluate` 或 `profile` 命令及其原始结果，是 Experiment 中的测试事件，不单独算一轮。

一条 Experiment 可以包含编译失败、正确性失败、性能下降、Profile 和必要的重跑；这些结果都要记录。一次 Round 可以包含多个 Tuner Experiment，作为对同一决策问题的比较证据；每个 Tuner 都以 `ExperimentResult` 交接。一个 Round 只能产生一个本轮正式交付的最终 Candidate，或明确记录保留父版本。

如果补充实验改变了主要假设或超出 RoundPlan 范围，Lead 应结束当前 Round 并创建新的 Round，而不是无限延长当前轮。

### 6.2 Round 流程

```text
建立 Baseline
  → Lead 发布 RoundPlan
  → 计划门槛与资源检查
  → 被启用的 Tuner 按需经 Runner 请求 Profile，并使用专属 PTOAnalyzer Tools
  → 多个 Tuner 围绕同一决策问题，在隔离 workspace 探索
  → Tuner 提交结构化 ExperimentResult
  → 按需调用 Challenger
  → Assembler 综合候选或保留父版本
  → PTOBench 对最终 Candidate 做 Check / Clean Benchmark
  → Event Ledger 与 Progress State 更新
  → Curator 更新 Case Memory
  → Lead 决定下一 Round、转向或停止
```

Baseline 只建立参照，不算优化 Round。只有测量波动或评测规则要求时才重复 Baseline，不预设盲跑次数；只有基线不足以形成合理假设时，Lead 才在 RoundPlan 中允许相应 Tuner 使用 Profile 预算，由 Tuner 决定是否向 Runner 请求。

### 6.3 事实与状态

事实只记录一次：

- Event Ledger：追加记录 CLI Test、候选变化、设备映射、错误、成本和结果；
- Progress State：由确定性逻辑投影当前 Candidate、Best、预算、活跃计划和机会状态；
- Case Memory：Curator 生成的可重建短摘要。

Candidate 和 Evidence 的可比身份至少包括源码快照、编译配置、Shape、设备及相关软件版本。任何 Profile 或 Benchmark 都必须引用实际评测的 Candidate，不能跨身份复用结果。

## 7. Runner、PTOBench 与设备并行

Runner 是 PTOmni 与 PTOBench 之间唯一的执行入口，负责：

1. 校验请求属于当前 RoundPlan 和执行阶段：探索请求来自已启用的 Tuner，最终候选验证来自 Assembler 或受管流程；Lead 不直接提交执行请求；
2. 检查 workspace、预算和设备需求；
3. 为单卡或多卡 Case 原子分配完整设备组；
4. 调用受管的 PTOBench `evaluate` / `profile` CLI；
5. 返回 PTOBench 结果、实际设备映射和预算事件；
6. 确认子进程结束后释放设备租约。

Tuner 不直接调用 NPU 命令，也不直接获取 PTOBench 锁。Runner 先取得设备租约，再调用 PTOBench；不在外层重复获取 PTOBench 内部执行锁。

Lead 不持有 Runner Tool，不能直接请求或启动 `profile` / `evaluate`。RoundPlan 只定义被启用 Tuner 可使用的动作范围和预算；探索请求由 Tuner 发起，最终候选验证由 Assembler 或受管流程提交，均由 Runner 校验执行。

设备租约和 PTOBench checkout 锁解决的是不同问题：

- 设备租约保证不同作业不争用同一物理卡；
- PTOBench 锁保护其自身的执行状态和共享资产，不自动等于物理设备独占。

因此设计上应允许设备集合不相交的 Tuner 实验并行；需要多卡的 Case 必须一次性分配完整兼容卡组，不能先占一部分设备再等待。最终 Candidate 的 Clean Benchmark 应进入隔离测量窗口，避免并行争用污染性能结果。

当前 PTOBench 若尚未支持 Runner 传入设备绑定、独立 action 状态或同一 checkout 中的安全并发，PTOmni 不能通过增加一把锁或复制嵌套 checkout 绕过它。该能力是 PTOBench 的一个受控修缮依赖；在完成前，同一 checkout 的 NPU CLI 测试保持串行。PTOmni 只在设计文档中明确接口和约束，不在这里实现它。

所有实际执行 NPU 工作负载的 `evaluate`、`profile`、失败或中断事件，都沿用 PTOBench 的硬件交互计数和执行时间记录。PTOmni 不复制另一套硬件预算账本；知识检索、静态分析和 workspace fork 等不触发 NPU 的操作不计硬件交互。

## 8. 关键不变量

1. 只有通过 PTOBench 正确性检查的 Candidate 才能成为最终交付版本或 Best。
2. PTOBench 是正确性、Clean Benchmark、硬件交互计数和正式排名的权威来源。
3. Tuner 只能写隔离 workspace；Assembler 是本轮候选综合和最终交付决策的唯一逻辑决策者；事实状态由确定性状态层提交。
4. Assembler 组合多个改动后，组合 Candidate 必须重新验证；不能把多个独立结果直接相加。
5. Challenger、Curator 和 Guidance 工具不能修改 PTOBench 事实；未验证解释不能升级为结论。
6. 每个 Candidate、CLI Test、Profile 和解释都能追溯到 Round、Experiment 和 Candidate 身份。
7. 并行必须同时满足 workspace 独立、设备集合不相交和 PTOBench 执行域允许；设备空闲不代表任意卡组都兼容。
8. Profile 是诊断证据，不是 Clean Benchmark；不能跨设备、Shape、配置或软件环境无标记比较。
9. 当证据冲突、瓶颈变化、连续尝试没有信息增量或预算临近耗尽时，Lead 必须重新规划或停止。

## 9. 两个论文消融如何对应架构

### PTOmni-NoGuidance

移除 PTOmni 专门组织的 Offline Knowledge、Structured Profiling 和 Dynamic Case Memory Guidance。仍保留基础任务说明、基本 PyPTO 文档、PTOBench 的正确性与性能反馈，以及相同的 Team/Runner/预算约束。这样测量的是 Guidance 的增量，而不是剥夺 Agent 的基本工作条件。

### PTOmni-FixedTeam

保留 Guidance、Runner、预算和 Assembler/Curator，但在实验开始前固定 Tuner 配置和调用顺序，禁用 Lead 根据当前证据重新选择 Tuner 或 Challenger。固定配置仍可使用同样的工具和信息，比较重点是 Adaptive Team 的增量。

不再新增角色级消融。Challenger、Curator 或某一种 Profile 形式是否单独有效，可以作为分析指标或案例观察，不扩展主实验矩阵。

## 10. 第一版范围

第一版只需要形成一个可验证的闭环：

- Baseline 与 Case Contract；
- 一个 Lead、一个 Assembler 和一个已启用专长 Tuner（Compute、Dataflow、Schedule 之一）的最小运行；
- 少量隔离 Tuner workspace；
- Runner 统一调用 PTOBench CLI；
- 按需 Profile 和轻量知识检索；
- Assembler 的候选综合与最终验证；
- 每轮一次 Curator 摘要和 Case Memory 更新。

Challenger 在高风险或停滞场景启用；多个 Tuner 的并行度由 Runner 和硬件资源决定。暂不做通用 Agent 平台、六个长期 Agent、共享 workspace 多写者、大规模分支搜索、向量数据库、自研 Profiler、学习型调度或跨 Case 自动迁移经验。

EAT 只作为分阶段运行、协作和记录闭环的参考，不是 PTOmni 的运行依赖。PTOmni 的核心仍然是：用 Guidance 减少盲目搜索，用 Adaptive Team 组织必要的专业能力，用真实 PTOBench 结果决定候选是否值得继续。

## 11. 待讨论项

- **Challenger 边界**：已确定只读、不写代码、不跑实验、没有否决权；后续讨论触发门槛和标准审查输出。
- **Tuner 专长边界**：Compute、Dataflow、Schedule 是暂定分类；应结合正式 Case 的可编辑源码与实证轨迹确认分类是否清晰、覆盖是否充分。
