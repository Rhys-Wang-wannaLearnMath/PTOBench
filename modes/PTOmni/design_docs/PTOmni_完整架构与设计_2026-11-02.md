## 0. 一页概览

### 0.1 PTOmni 到底是什么？

PTOmni 是一个**轻量、机制引导的自适应 Multi-Agent Kernel 优化系统**。它围绕当前程序的真实性能问题组织专业 Agent，形成和挑战优化假设，通过 PTOBench 验证候选实现，并将每轮实验经验沉淀为当前 Case 的动态知识，持续调整后续团队与优化方向。

**一句话流程：**

**Specialize → Challenge → Optimize → Verify → Learn → Adapt**

即：专业分工 → 挑战关键假设 → 实施优化 → 正式验证 → 沉淀经验 → 调整团队/搜索方向。

与“让很多 Agent 并行改代码”不同，PTOmni 强调**针对相互影响的优化机制进行专业协作**，并在证据变化后及时调整分工。

### 0.2 最核心的设计决定

| 项目 | 当前设计 |
|---|---|
| 核心研究问题 | 如何在相互耦合、不断变化的 Kernel 性能机制中高效协调专业 Agent |
| Agent 角色 | Supervisor、Owner、G、D、I、Hardware、Challenger、Curator，共 **8 种逻辑角色** |
| 实际运行方式 | Owner 持续工作；专家与 Challenger 按需启用；Curator 每轮正式优化尝试后总结；Supervisor 在关键节点规划 |
| 专家划分 | G：Graph/Scheduling；D：Decomposition/Granularity；I：InCore/Dataflow；Hardware：跨层硬件约束 |
| Offline Knowledge Base | 已修正、硬件对齐的 **PyPTO 文档 + PyPTO-Lib 文档 + Ascend 硬件知识**；轻量索引、按需获取 |
| Profiling Tool | 复用 PyPTO 原生工具，提供简洁 Summary 和 Before/After Compare |
| Dynamic Knowledge | Curator 总结**当前 Case、本轮优化**，再更新本 Case 的滚动记忆；不跨 Case 传播 |
| 优化边界 | 只修改 PTOBench 暴露给 Agent 的测试用例源码和白名单编译选项 |
| 工程哲学 | 复用 Pi、PTOBench 和原生工具，少量编排逻辑，避免独立框架和过度设计 |
| 外部 Baseline | **Basic Pi**、**CANNBot Pi** |
| 主要消融 | **FixedRoles、StaticKnowledge、NoCurator**；NoChallenger 可作为次要分析 |

### 0.3 哪些是已经确定的，哪些还需要验证？

- **已确定的架构方向**：专业化 Multi-Agent、G/D/I 机制视角、Hardware/Challenger 按需协作、Curator 每轮总结、三源静态知识库、轻量 Profiling、受控 PTOBench 评测。
- **建议采用的工程默认值**：常规只启用 0–2 名临时 Specialist；以 Episode 为团队规划周期，以 Round 为评测与总结周期；Owner 独占正式 Candidate 的写入。
- **仍需实证验证的研究假设**：动态团队比固定团队更有效；Challenger 能减少无效尝试；Curator 的定向总结优于普通历史摘要；机制引导的分工确实能改善跨机制权衡和搜索效率。

## 1. 研究目标、PyPTO 特性和设计原则

### 1.1 研究目标

给定一个 PTOBench Case、初始正确实现、允许的优化范围和有限预算，PTOmni 通过多轮优化，尽可能高效地找到**正确且高性能**的候选实现。

我们不仅关心最终 Speedup，也关心：

- 在给定硬件交互预算下，能多快接近高性能实现；
- 是否减少错误瓶颈判断、重复尝试和无效探索；
- 多 Agent 协作引入了多少 Token、时间和调度成本；
- 优化过程中是否能有效利用先前的实验经验。

### 1.2 为什么以 PyPTO 作为重要研究场景？

PyPTO 的重要特点是：**开发者可在源码中较精细地控制执行组织**，包括任务划分、依赖、并行策略、Tile、InCore Pipeline、Dataflow 等。不同控制决策可能共同影响最终性能。

例如：

1. 增大 Task Granularity 可能减少 Dispatch；
2. 但是过大的 Task 又可能降低可利用的并行度，或者增加片上资源压力；
3. 更深的 Pipeline 可能改善重叠，但要求额外的 Buffer 资源；
4. 一个优化成功后，新的主瓶颈可能从 Scheduling 转向 InCore，或反过来。

因此，这不是一个完全独立的参数搜索问题，而是一个**受执行机制及其相互制约关系影响的持续优化过程**。

**注意：**文中的 G/D/I 是 PTOmni 用来组织专业能力和知识的**工作分类**，不是将 PyPTO 官方 API 强行划分为三个互斥层级；一个变换可能同时涉及多个分类。

### 1.3 系统边界

PTOBench 给 Agent 明确的任务契约（Case Contract）。PTOmni 只能：

- 修改该 Case **明确暴露、允许编辑的源码文件**；
- 调整**允许的编译选项**；
- 调用 PTOBench 公开的编译、正确性、Clean Benchmark、Profiling 等接口；
- 阅读已授权的静态技术知识及当前 Case 的公开结果。

PTOmni **不能**：

- 修改 PyPTO Compiler、Runtime、底层 CodeGen、Evaluator 或基准规则；
- 读取或修改隐藏 Fixture、Oracle、sealed Reference、隐藏测试数据；
- 通过直接改写生成代码或中间产物绕过 Case 的编辑范围；
- 自行重写正式测试结果、预算和历史事实。

这属于工程与实验边界，**不必成为论文 Introduction 反复强调的故事主角**。

### 1.4 总体设计哲学

1. **机制优先**：团队围绕性能问题及跨机制权衡组织，而非为了多 Agent 而多 Agent。
2. **最小必要团队**：简单问题由 Owner 完成；复杂问题再召集专家。
3. **证据优先**：性能结论来自真实编译、正确性、Benchmark 与可用 Profile，Agent 解释与硬事实分开。
4. **保留经验但不过度记忆**：当前 Case 的动态记忆持续更新；原始事实仍由确定性账本保存。
5. **轻量复用**：Knowledge Base 和 Profiling 均以实用为主，尽量复用现有资源。
6. **成本可控**：硬件交互、LLM 调用、墙钟时间及 Profiling 成本应可记录和限制。

## 2. 论文故事线：问题、洞察与方法

> **建议标题**：*PTOmni: Mechanism-Guided Adaptive Collaboration for Kernel Optimization*

### 2.1 Problem：Coupled and Evolving Optimization Mechanisms

PyPTO 让优化者能够控制多个执行层面的行为，但这些控制并不相互独立。

**三个具体挑战：**

1. **Coupled Optimization Mechanisms（机制耦合）**  
   某项优化改善一个方面，可能损害另一个方面。例如减少 Dispatch 的同时降低并行度。

2. **Evolving Bottlenecks（瓶颈变化）**  
   随着优化进行，之前最重要的限制可能变得次要，之前受阻的优化也可能重新可行。固定的优化关注点不能始终适用。

3. **Unreliable Hypotheses and Repeated Exploration（假设误判与重复探索）**  
   Agent 可能根据不充分的证据误判瓶颈，或者在后续轮次重新尝试已被证明无效的方向。

### 2.2 Key Insight

> **The optimization mechanism determines the required expertise; hardware evidence and accumulated experience determine how that expertise should evolve.**

直白说：**当前性能问题决定应该让谁一起优化；真实实验和历史经验决定团队下一步应该怎样变。**

### 2.3 两个主要方法机制

**Method A — Mechanism-Guided Adaptive Collaboration**

- 依据当前优化假设及其潜在跨机制影响，动态配置 G/D/I/Hardware Specialist；
- Challenger 在有必要时质疑瓶颈判断、因果解释和优化权衡；
- Owner 统一实现，避免多个 Agent 无序修改同一份程序。

**Method B — Evidence-Conditioned Optimization Adaptation**

- 利用 PTOBench 真实验证和轻量 Structured Profiling 检查优化结果；
- Curator 将**本轮**经过验证的经验蒸馏为可复用的当前 Case 记忆；
- Supervisor 结合新证据和记忆决定继续、调整团队、重新检查旧机会或停止。

Offline Knowledge Base 和 Profiling Tool 是这两个机制的**必要支撑组件**，不需要各自被包装成很强的独立创新。

### 2.4 不应该采用的叙事

- 不把“多个 Agent 比一个 Agent 多”当作核心新颖性；
- 不把“增加了 Challenger / Curator / Profiling”当作单独创新；
- 不笼统宣称已有 Kernel Agent 没有专用知识、没有性能分析或不会使用历史；
- 不以某个既有团队框架为论文的主线或命名参照；
- 不把论文写成修改 PyPTO Compiler/Runtime 的系统工作。

论文应论证的是：**机制耦合怎样造成优化决策困难，以及 PTOmni 怎样让专业协作随真实执行约束变化。**

### 3.1 四个逻辑部分

| 部分 | 职责 | 是否需要复杂创新 |
|---|---|---|
| **Adaptive Agent Team** | 专业分工、挑战、执行与自适应调度 | **核心研究机制** |
| **Offline Knowledge Base** | 提供经过硬件对齐的 PyPTO、PyPTO-Lib、Ascend 知识 | **轻量实用** |
| **Profiling & PTOBench** | 提供可比较、可追溯的真实性能与正确性证据 | **轻量实用** |
| **Online Case Memory & State** | 保存每轮经验、当前机会和可信事实，支持下一步调整 | **核心闭环的组成部分** |

### 3.2 一个重要的工程约束

**逻辑角色多，不等于必须编写很多 Agent 子系统。**

所有在线角色都可以由统一的 **Pi Session Runner** 启动，区别主要来自 Prompt、输入知识、当前任务和权限；只有很薄的一层 Team Orchestrator 负责组织它们。

## 4. Agent 角色与职责

共有 **8 种逻辑角色**：Supervisor、Owner、G、D、I、Hardware、Challenger、Curator。

### 4.1 角色总表

| 角色 | 主要职责 | 典型输入 | 典型输出 | 何时运行 |
|---|---|---|---|---|
| **Supervisor** | 规划优化方向和团队、分配知识/预算、决定切换和停止 | 当前 State、Case Memory、候选 Hypotheses、剩余预算 | `TeamPlan` / Replan / Stop | 初始化及关键事件 |
| **Owner** | 主优化与代码实现、调试、提出候选、发起评测 | 当前 Candidate、TeamPlan、专家建议、知识和证据 | Candidate Diff、优化 Hypothesis、下一步建议 | 持续 |
| **G Specialist** | Task Graph、Dependency、Scheduling、Dispatch、并行执行 | 相关源码、调度证据、G 知识 | 调度诊断、候选方案、风险/测量建议 | 按需 |
| **D Specialist** | Decomposition、Task Granularity、Tile、工作划分 | 相关源码、粒度与资源信息、D 知识 | 分解方案、权衡分析 | 按需 |
| **I Specialist** | InCore Pipeline、Dataflow、计算与数据搬运 | InCore 代码、Compiler Hints、InCore 知识 | 核内优化建议、资源/正确性风险 | 按需 |
| **Hardware Specialist** | Ascend 架构、片上资源、计算/访存边界、设备适用性 | 硬件配置、相关性能现象、硬件文档 | 资源约束分析、可行性审查 | 按需 |
| **Challenger** | 挑战关键假设与证据，识别替代解释、跨机制副作用 | 当前 Hypothesis、专家建议、已有证据 | `ChallengeReport` | 按需 |
| **Curator** | 总结本轮优化，并更新当前 Case 动态知识 | 本轮 Attempt、真实评测、相关 Profile、上次 Memory | `RoundNote`、新的 `CaseMemory` | 每轮正式尝试结束后 |

### 4.2 G / D / I 的分工

**G — Graph & Scheduling**

- Task 依赖及其对并行的限制；
- Scheduling / Dispatch / Core 空闲；
- 任务执行关系和调度策略。

**D — Decomposition & Granularity**

- Tile 大小与工作粒度；
- Task 划分、Fusion/Splitting 的适用性；
- Dispatch 成本与并行度、资源压力之间的权衡。

**I — InCore & Dataflow**

- InCore 计算组织、Pipeline；
- 数据搬运与计算重叠、片上数据复用；
- 单 Task 计算/访存效率及相关资源条件。

这些专家可以**跨层联合**，而不是机械地将同一变换只分给一个角色。

### 4.3 Hardware Specialist：跨层约束专家

Hardware Specialist 不只是第四个普通调参 Agent，而是负责回答：

- 该策略在**当前 Ascend 型号和软件栈**上是否可行？
- 资源容量、Buffer、带宽、AIC/AIV 等条件是否支持该方案？
- 一种优化是否改变另一个机制的资源前提？
- 当前编译提示和真实 Profile 是否与硬件知识一致？

它可以与 D/I 或 G/D 联合工作，但**不常驻**。

### 4.4 Challenger：挑战什么？

Challenger 不负责无原则唱反调，主要挑战三类问题：

1. **Diagnosis Challenge**：瓶颈判断是否准确？是否存在其他同样合理的解释？
2. **Trade-off Challenge**：当前优化是否会损害并行度、资源占用或其他性能机制？
3. **Evidence Challenge**：是否有足够数据支持“优化有效 / 无效”的判断？测量是否可比？

推荐输出固定为：

```yaml
challenged_assumption: "Low utilization is caused by dispatch overhead"
alternative_explanation: "Dependency may limit ready work"
cheapest_useful_check: "Inspect ready-but-idle vs. no-ready-work evidence"
impact_if_wrong: "Increasing task granularity may reduce parallelism"
```

Challenger 应**只在有价值的时候调用**：竞争性诊断、跨机制冲突、连续停滞、异常实验结果、高成本决策或准备放弃重要机会。

### 4.5 Curator：每轮的动态知识蒸馏

Curator **每次只总结本轮正式优化尝试**，并参考已有的简短 Case Memory，更新当前 Case 的滚动知识。它不负责读完所有历史对话，也不把动态经验写回 Offline Knowledge Base。

其职责严格区分：

- **Observations（事实）**：来自测试/Benchmark/Profile，例如正确性通过、Task Count 下降；
- **Interpretations（解释）**：例如“可能存在资源压力”，需标注未验证；
- **Lessons / Constraints（经验与限制）**：当前 Case 哪些方案已试过、何时有效/无效；
- **Open Opportunities（下一步机会）**：还应检查什么、哪些旧机会可以重新考虑。

事实写入与最佳候选更新由确定性 State Layer 执行，**Curator 只能解释和整理，不能创造或改写测量结果**。

### 4.6 Owner 与其他 Agent 的写入权限

- **Owner**：唯一负责向当前正式 Candidate 提交源码/编译选项修改的角色；
- **Specialists / Hardware / Challenger**：默认只读，返回建议、补充假设及证据需求；
- **Curator**：只更新允许的 Case Memory 文本，不修改 Candidate 或测量结果；
- **Supervisor**：调整 TeamPlan 和规划，不直接改变性能事实。

这样保留专业协作，但无需实现复杂的多分支协同编辑系统。后续如果要支持 Specialist 隔离探索分支，可作为选配，而不是第一版必需。

## 5. Team Orchestration：什么时候谁来工作？

### 5.1 两层节奏

**Optimization Episode（优化阶段）**：围绕一个主要性能问题或相关假设开展连续工作，例如“降低 Dispatch 成本”。一个 Episode 可包含多个 Round，团队通常保持相对稳定。

**Optimization Round（优化尝试）**：一次有明确 Hypothesis 的正式候选尝试及其编译/正确性/性能结果；完成后由 Curator 总结。

> 对于编译失败、正确性失败和性能下降的正式 Attempt，同样应有 Round Note。Owner 在同一 Attempt 内修复小问题、修改一两行代码，不必每次触发 Curator。

### 5.2 默认团队配置

**最小配置是 `Owner`；常规配置是 `Owner + 1 Specialist`；较复杂问题可以 `Owner + 2 Specialists`。**

Challenger 在必要时独立审查，Curator 在 Round 结束后单独总结。Supervisor 只在关键节点决定配置。

| 当前问题 | 推荐团队 | 典型关注 |
|---|---|---|
| 已明确的局部优化或普通修复 | Owner | 直接实施和验证 |
| Dispatch / Dependency | Owner + G | 调度和任务关系 |
| Task Granularity 与并行度权衡 | Owner + G + D | 任务划分与调度协同 |
| InCore Pipeline / Dataflow | Owner + I | 核内效率 |
| Tile 或 Pipeline 遇到资源问题 | Owner + D/I + Hardware（按需组合） | 资源可行性、跨机制影响 |
| 假设冲突或连续停滞 | Owner + 相关 Specialist + Challenger | 验证重要前提或竞争解释 |

### 5.3 Supervisor 每次输出什么？

`TeamPlan` 保持非常小：

```yaml
episode_goal: "Reduce task dispatch overhead"
active_specialists: [G, D]
use_challenger: false
knowledge_topics: [task_scheduling, task_granularity]
needed_evidence: [task_count, scheduler_overhead, clean_latency]
round_budget: 4  # 示例；具体预算由实验配置确定
```

Supervisor 不需要通过一个独立的策略模型学习 Team Scoring。可先由 LLM 生成 TeamPlan，外层以简单规则校验工具权限、角色数量和预算。

### 5.4 触发重新规划的事件

通常**不需要每轮重组团队**。建议在以下事件发生时调用 Supervisor：

1. 初始化新 Case 或 Episode；
2. 当前主要性能瓶颈/优化约束发生显著变化；
3. 预期效果与实测结果矛盾，或出现关键证据缺口；
4. 某项优化受硬件/编译/正确性条件阻塞，需要其他专业能力；
5. 原先受阻的优化前提改变，旧机会值得重新考虑；
6. 多轮没有有效进展，需要重新审查假设；
7. 预算接近耗尽，需要重新确定优先级或结束。

**轻量兜底**：即使没有触发特定结构化事件，持续停滞时也可允许 Supervisor 自由反思一次，避免系统变成僵硬规则表。

### 5.5 简化的调度逻辑

```python
if first_episode or significant_state_change or stalled:
    team_plan = supervisor.plan(state, case_memory, offline_knowledge_index)

owner.work(team_plan)

if team_plan.needs_specialists:
    suggestions = run_selected_specialists(team_plan)
    owner.consider(suggestions)

if high_risk_hypothesis or conflicting_evidence:
    challenge = challenger.review(current_hypothesis, evidence)
    owner.consider(challenge)

result = ptobench.evaluate(owner.candidate)  # budget, correctness, benchmark
record_immutable_attempt(result)

if useful_diagnostic_gap:
    evidence = profiling.summary_or_compare(...)

round_note, case_memory = curator.distill(current_round, evidence, case_memory)
state = deterministic_reduce(events)

# 继续当前 Episode，或在有意义的事件时重新规划
```

这只是控制流程示意：具体 `challenge` 可发生在昂贵评测**之前**，也可发生在异常结果**之后**；不会机械地每轮执行全部角色。

## 6. Offline Knowledge Base：初步设计（实用优先）

### 6.1 现有三类知识源

**直接保留你已经修正并与目标硬件对齐的三份资料作为权威基础。**

| 来源 | 主要覆盖 | 主要服务对象 |
|---|---|---|
| **PyPTO Documentation** | API、语义、Task/Dependency、Pipeline、正确使用条件、编译行为 | Owner、G/D/I |
| **PyPTO-Lib Documentation** | 具体算子实现、代码范例、优化技巧、实际调参经验 | Owner、G/D/I |
| **Ascend NPU Hardware Knowledge** | 硬件结构、片上资源、计算与访存、设备差异、性能限制 | Hardware Specialist、其他专家 |

明确**不使用 Git 历史作为当前主要知识源**；不引入其他 Case 的在线优化记录，不把测试答案写入通用知识。

### 6.2 为什么不直接把全部原文塞给所有 Agent？

完整原文可以保留，但每次给 Agent 全部内容通常会：

- 增加上下文和 Token 成本；
- 淹没当前问题真正相关的 API、约束和案例；
- 让不同 Specialist 难以保持专业侧重点；
- 增加不同版本或硬件条件混用的风险。

因此建议：**保留原文作为可追溯知识源，但在线按需暴露相关章节。**

### 6.3 三项轻量预处理

**Step A — 按章节保留与切分**

- 保留完整 Markdown/文档内容及代码示例；
- 使用原有章节标题、源文件路径和段落锚点组织；
- 不把代码与前提条件、注意事项拆散；
- 删除明显无效的导航和重复页面，但不进行大规模重写。

**Step B — 建立一个简单 Topic Index**

每个章节记录：`section_id`、`source`、`title`、`tags`、`device_applicability`（若存在）、`path`。

示例：

```yaml
section_id: pypto.pipeline.incore
source: pypto_docs
title: InCore Pipeline
tags: [I, pipeline, buffering, memory]
path: pypto/incore/pipeline.md
related_topics: [tile_size, resource_pressure]
```

检索可先使用**标题/关键词/BM25**；规模不大时可以简单全文检索。**暂时不必建设向量数据库或复杂 RAG。**

**Step C — 整理目标 Hardware Profile**

包含实际设备与软件版本的核验信息，例如：

```yaml
target:
  device_model: "<verified Ascend model>"
  pypto_version: "<version>"
  cann_version: "<version>"

resources:
  aic_aiv: "<verified configuration>"
  on_chip_memory: "<verified capacities>"
  supported_features: ["<verified features>"]

source_references:
  - "<documentation section id>"
```

这里只保存已核实事实，不让 LLM 猜设备资源或把某款 Ascend 的参数直接套给其他型号。

### 6.4 在线如何向 Agent 提供知识？

采用 **Core Context + On-Demand Retrieval**：

**Core Context（每个 Agent 默认获得）**

- 当前 Case、设备型号和版本；
- PTOBench 的权限/正确性约束；
- 知识目录与检索方法；
- 当前 Episode 的简短目标。

**On-Demand Knowledge（按问题获取）**

- G：Dependency、Task Graph、Scheduling、SPMD；
- D：Granularity、Tile、Decomposition、Task Fusion；
- I：InCore、Pipeline、Dataflow、Memory；
- Hardware：Ascend 资源、指令/管线约束、计算与访存特性；
- Challenger：当前假设相关的前提、风险和替代解释。

这只是默认优先级，**不是知识访问隔离**。D 遇到资源问题也可以读硬件文档，I 需要调度背景也能查询 G 内容。

### 6.5 建议接口

```python
knowledge_search(query, tags=None, device=None)
knowledge_read(section_id)
```

返回章节正文、所属文档、硬件/版本适用性及来源引用；不需要强制生成复杂的机制卡。

### 6.6 Offline Knowledge 与 Dynamic Memory 的边界

- **Offline Knowledge**：跨 Case 通用，预先构建，评测期间固定；
- **Dynamic Case Memory**：仅当前 Case 的优化历史经验，Curator 每轮更新；
- **不得在评测时**将当前 Case 的失败、成功或答案反写到 Offline Knowledge，或将前一个 Case 的在线经验隐式注入后一个 Case。

这既简单，也更有利于实验公平性和避免信息泄漏。

## 7. Profiling Tool：初步设计（原生工具 + 薄 Adapter）

### 7.1 定位

**Structured Profiling 的目标是实用，不以自研底层 Profiler 或复杂自动诊断为论文主要创新点。**

它负责把已有 PyPTO / PTOBench 所能提供的编译与运行时性能信息转换为 Agent 易读、与程序版本绑定的**短证据**。

### 7.2 复用的已有分析能力

按实际 PyPTO/PTOBench 版本和目标设备支持情况，优先接入：

| 类别 | 可能的原生来源 | 用途 |
|---|---|---|
| 编译提示 | 如 `perf_hints.log` | 识别编译器给出的资源/性能提示 |
| 任务结构 | 如 Task DAG / `deps.json` | 观察依赖、可并行性和调度限制 |
| 任务时序 | 如 Task/Chip Swimlane | 观察任务数量、执行和等待情况 |
| 关键路径/调度分析 | Critical Path、Scheduler Overhead 分析（若可用） | 区分主要计算、依赖或调度等待 |
| 硬件计数器 | PMU（若可用） | 补充计算/访存相关证据 |
| 编译/资源信息 | IR Trace、Memory Map、资源提示（若可用） | 判断预期变换和资源条件 |
| 正式性能 | PTOBench Clean Benchmark | 最终延迟/Speedup 的可信依据 |

**上述是适配候选清单，不意味着当前实验版本保证全部可用。** 接入时必须做能力探测；缺少的数据应明确返回 `unavailable`。

### 7.3 两个最小对外接口

**接口 1：Profile Summary**

```python
profile_summary(candidate_id, focus=None)
```

回答：**当前程序有哪些与 `focus` 相关的性能现象？**

如 `focus="dispatch"`：返回 Task Count、相关等待指标、关键区间和必要的编译提示，而不是全部原始时序记录。

**接口 2：Profile Compare**

```python
profile_compare(before_id, after_id, focus=None)
```

回答：**这次修改前后，什么机制指标真的发生变化？这种变化与 Clean Latency 是否一致？**

### 7.4 Evidence Bundle 的最小格式

```yaml
candidate_id: P4
comparison_id: P3  # 可选
focus: task_granularity

context:
  input_shape_id: "<shape identifier>"
  device: "<device model>"
  compile_config_id: "<config hash>"

observations:
  - metric: task_count
    before: 320
    after: 176
    provenance: "<profile artifact reference>"
    quality: measured

  - metric: clean_latency_us
    before: 820
    after: 805
    provenance: "<benchmark result reference>"
    quality: measured

missing_data:
  - "resource_occupancy unavailable"

note: "Task count decreased; latency benefit is small. Cause not established."
```

以上数字只用于说明接口结构。`note` 应始终避免将相关性写成确定因果。

### 7.5 Adapter 具体做哪些事？

1. **读取/调用原生工具**：不重复实现底层硬件分析；
2. **少量指标提取**：只选当前问题相关字段，按需 Drill-down；
3. **绑定版本身份**：源码版本、输入 Shape、设备、编译选项、Profile 模式；
4. **前后比较**：对齐可比配置，统一单位，标注差值；
5. **数据质量检查**：缺失、无法比较、采集扰动或分析不完整时显式标注；
6. **简洁呈现**：优先输出数值和中性事实，不自动生成强因果结论。

### 7.6 第一版不做什么？

- 不自研硬件采样和 Critical Path 算法；
- 不必引入专门的 Profiling LLM Agent；
- 不建大型诊断知识图谱；
- 不强制所有 Case 每轮完整采集 Profile；
- 不由 Adapter 代替 Agent 判断应该优化哪种源码机制。

### 7.7 正式性能与 Profiling 必须分开

Profiling 本身可能改变执行时序。**Speedup、是否刷新 Best 等正式结论只来自可复现的 Clean Benchmark**。

Profiler 中观察到“调度等待下降”可以说明现象有变化，但不能单独证明某项优化已在端到端表现上获益。

如果后续不同 Case、Shape 或编译选项不可比，Adapter 应拒绝生成直接对比或标为 `not_comparable`。

## 8. Online Case Memory 与 Progress State

### 8.1 记忆分成两层

**A. Deterministic Progress State：可信事实状态**

由 PTOBench 的结果和事件重放产生，包括：

- 当前 ProgramVersion；
- 最佳已通过正确性验证的 Candidate；
- 所有正式 Attempt 与结果；
- Profile / Benchmark 证据引用；
- 当前预算消耗；
- 活跃 Episode、TeamPlan 与优化假设状态。

**B. Dynamic Case Memory：经验摘要**

由 Curator 每轮更新，包括：

- 已观察到的性能事实；
- 仍未证实的解释与假设；
- 已经尝试过的失败配置及适用条件；
- 当前值得探索或重新检查的机会；
- 后续专业团队可能需要的上下文。

**事实状态是权威来源；Curator 的文字是可更新的解释层。**

### 8.2 Optimization Hypothesis：最小协作对象

无需庞大 Hypothesis Graph，每次重要优化只记录一个简洁的 Ticket：

```yaml
id: H7
candidate_version: P4
mechanism_tags: [G, D]
hypothesis: "Too many small tasks cause dispatch overhead"
action: "Increase task granularity"
expected_effects: ["task count decreases", "scheduling overhead decreases"]
possible_tradeoffs: ["lower parallelism", "higher buffer pressure"]
required_evidence: [task_count, scheduler_overhead, clean_latency]
status: proposed
```

状态可以是：`proposed`、`testing`、`supported`、`weakened`、`blocked`、`invalidated`、`unresolved`。

一个 Hypothesis 可以经过多次 Attempt，但每个 Attempt 必须准确关联**它测试的是哪个程序版本和哪种具体变换**。

### 8.3 Curator 每轮输出

**Round Note（仅本轮）**

```yaml
round: 5
candidate: P5
parent_candidate: P4
hypothesis: H7

action: "Increased tile size"
observations:
  - "Correctness passed"
  - "Task count decreased"
  - "Clean latency did not improve reliably"
interpretations:
  - "Resource pressure or reduced parallelism may offset gains; unverified"
next_checks:
  - "Inspect resource usage and available parallelism"
```

**Case Memory（本 Case 的滚动摘要）**

```markdown
## Verified findings
- Moderate task-granularity increase reduced dispatch-related metrics on P3.

## Negative or blocked attempts
- Larger tile on P5 had no reliable clean-latency gain.

## Open questions
- Is larger-tile performance limited by reduced parallelism or memory resources?

## Next opportunities
- Examine D/I trade-off; request hardware expertise if resource evidence appears.
```

这里 `Case Memory` 持续更新，但其中每条事实必须可追溯到相应 `Attempt`、程序版本和证据。

### 8.4 Opportunity Frontier：保持轻量

不必构建复杂图结构，只维护少量待探索机会与状态：

- `ready`：当前可以尝试；
- `needs_evidence`：先补关键证据；
- `blocked`：受条件约束，暂不尝试；
- `recheck`：条件改变后可重新考虑；
- `discarded`：现有证据不支持继续投入。

Supervisor 可利用该列表做下一轮规划。只需对重要机会记录简短的 `blocked_by` / `related_to`，不需要全局搜索图或复杂排序学习算法。

## 9. 单个 Case 的完整执行流程

### 9.1 初始化（Once per Case）

1. PTOBench 加载 `OptimizationContract`：可编辑路径、编译选项白名单、正确性、输入、正式测量规则、预算；
2. 对初始 Candidate 进行必要的合法性/性能基线验证；
3. 记录目标设备和软件版本，加载 Offline Knowledge Index；
4. 初始化 ProgramVersion、Best、Event Ledger、Case Memory、Opportunity Frontier；
5. 创建 Owner Session 和初始 Supervisor TeamPlan。

### 9.2 初始诊断与团队组织（Episode Start）

1. Owner 阅读源码和必要的静态知识，提出 1–3 个可行动的优化假设；
2. 若无法区分主要瓶颈，可调用轻量 Profile Summary；
3. Supervisor 根据机制标签、风险和当前证据选择活跃 Specialist 与知识主题；
4. 对需要深入讨论的跨机制问题，选择 1–2 个 Specialist，必要时加入 Challenger。

### 9.3 一轮正式优化（Round）

1. Owner 与活跃 Specialist 确定本轮优先测试的 Hypothesis；
2. 高风险/关键分歧时，由 Challenger 提出反例或最低成本的证据检查；
3. Owner 实施一次受控源码或编译选项修改；
4. PTOBench 编译、正确性检查、Clean Benchmark；
5. 结果不足以解释时，按需运行 Profiling，必要时比较修改前后版本；
6. 追加不可变 Attempt / Evidence 事实，确定性更新 Best 与预算；
7. Curator 只围绕**本轮**结果生成 Round Note，并更新 Case Memory；
8. State Reducer 更新当前 Hypothesis、Opportunity Frontier 和 Team 状态。

### 9.4 继续还是重新组队（After Round）

**继续当前 Episode**：假设仍然有价值、团队能够推进、预算允许。

**触发 Supervisor Replan**：性能瓶颈明显转移、重要解释被反驳、资源或正确性约束要求其他专家、先前阻塞条件解除，或者持续停滞。

**结束**：预算耗尽、没有值得探索的机会、或继续搜索不划算。

### 9.5 最终输出

- `best_verified_candidate`：最佳正确实现及允许的编译配置；
- `final_evaluation`：在干净工作空间重新执行的正式正确性/性能验证；
- `attempts.jsonl`：受控优化轨迹；
- `evidence/`：与程序版本绑定的公开证据；
- `rounds/` 与 `case_memory.md`：当前 Case 的动态经验；
- `team_trace.jsonl`：重要的组队和切换事件（供论文分析）。

## 10. 一个贯穿 G/D/I 的具体例子

> 这是**示意性流程**，不是当前系统已经复现的实验结果。

### Episode A：Dispatch 问题

- 初始 Profile 显示大量短 Task，并存在调度相关等待；
- Supervisor 选择 `Owner + G + D`；
- G 关注调度与依赖，D 研究 Task Granularity；
- Owner 调整 Tile/工作粒度，PTOBench 验证；
- 若 Task Count 和 Clean Latency 同时改善，Curator 记录本 Case 下的有效配置与证据。

### Episode B：更大 Tile 不再带来收益

- Owner 继续增大 Tile；Task Count 虽下降，Clean Latency 却不改善；
- Challenger 检查“Dispatch 仍是主瓶颈”这个假设是否成立；
- Curator 将新的资源/并行度风险记录为**未验证解释**；
- Supervisor 不盲目继续 G 方向，而是调整为 `D + I`，必要时增加 Hardware Specialist。

### Episode C：InCore 与资源协作

- I 提出改善 Pipeline / Dataflow；Hardware 检查当前 NPU 的 Buffer 和相关限制；
- 若编译或 Profile 显示预期条件不满足，优先处理限制条件，而不是简单认为优化机制无效；
- Owner 统一修改并验证，Curator 记录新的机会与失败条件；
- 如资源限制解除，可重新考虑先前暂时不可行的优化。

整个故事说明：**团队变化与当前执行机制的权衡相关，Curator 让每阶段产生的经验进入下一阶段。**

## 11. PTOBench、工程实现与最小代码结构

### 11.1 PTOBench 是裁判与实验场

PTOBench 负责：

- Case Contract 与 Workspace；
- 编辑范围与白名单编译选项校验；
- Compile / Test / Benchmark / Profile；
- 正式预算；
- Candidate Version、公开评测结果与最终提交验证。

PTOmni 不另造一套正式 Evaluator。所有 Agent 必须通过受控接口获取结果。

### 11.2 推荐代码组织

```text
sluice/
├── loop.py             # Case / Episode / Round 控制循环、Supervisor 触发
├── agents.py           # 统一 Pi Session Runner、角色 Prompt、TeamPlan
├── knowledge.py        # 章节索引、轻量检索、知识暴露
├── profiling.py        # 原生 Profile 读取、Summary、Compare
├── state.py            # Event Ledger、ProgramVersion、Hypothesis、Best、Budget
├── prompts/
│   ├── supervisor.md
│   ├── owner.md
│   ├── specialist_g.md
│   ├── specialist_d.md
│   ├── specialist_i.md
│   ├── hardware.md
│   ├── challenger.md
│   └── curator.md
└── knowledge/
    ├── index.yaml
    ├── hardware_profile.yaml
    ├── pypto/
    ├── pypto_lib/
    └── ascend/
```

这是逻辑示例；**文件数量不是设计目标**。能够复用已有 PTOBench 或 PTOmni 模块时应直接复用。

### 11.3 少量共享的数据接口即可

推荐的关键对象只有：

1. `OptimizationContract`：任务边界、环境和预算；
2. `ProgramVersion`：候选程序与允许的编译配置；
3. `OptimizationHypothesis`：机制、变换、预期效果、风险、所需证据；
4. `TeamPlan`：当前 Episode 的专家、知识主题与重点；
5. `Attempt`：一次正式尝试及其验证结果；
6. `EvidenceBundle`：可追溯的结构化证据；
7. `CaseMemory`：Curator 的当前 Case 滚动总结。

其余记录可从事件流派生，避免为每种角色增加单独数据库。

### 11.4 运行成本与并行性

- G/D/I/Hardware 可以并行阅读和分析；
- Owner 是当前正式 Candidate 的唯一写入者；
- 编译不同隔离候选可以在资源许可时并行，但第一版不必实现复杂并行分支；
- 正式 NPU Benchmark 尽量隔离、受统一预算控制，避免并发测试污染性能；
- Curator 每轮仅一次，Supervisor 按事件调用，降低 LLM Token/时间开销；
- Profile 按需采集并缓存可复用结果，避免重复高成本分析。

### 11.5 主要安全/正确性不变量

1. 未通过正确性验证的 Candidate 不能更新 Best；
2. Agent 无权直接修改 Benchmark 事实、预算和隐藏数据；
3. 旧程序的 Profile 不可自动当作新程序的观测事实；
4. Curator 的推测不得被升级成经过验证的结论；
5. Profiling 时序不得直接作为正式 Clean Latency；
6. 结束时返回经过干净工作空间验证的最佳正确实现。

## 12. 实验设计：严格按照当前确定的三组组织

### 12.1 Group 1 — Basic Agent

**问题：结构化协作优化是否比直接使用 Coding Agent 更有效？**

- **Basic Pi**：直接使用 Pi 对相同 PTOBench Case 进行优化；
- **PTOmni-Full**：机制引导团队、知识、Profiling、挑战和动态总结的完整闭环。

这一组验证整体方法的增量价值，**不能单独归因到某个模块**。

### 12.2 Group 2 — Existing Specialized Agent

**问题：PTOmni 是否优于已有面向该领域的专用 Kernel Agent？**

- **CANNBot Pi**：明确所用版本、Skills、工具权限和执行配置；
- **PTOmni-Full**：同样的 Case、可修改范围、正式评测环境与预算原则。

避免因为 Baseline 配置不完整、获得的权限或资源不同而夸大优势。

### 12.3 Group 3 — Fixed vs. Adaptive（主要消融）

| 变体 | 保留 | 变化 | 核心问题 |
|---|---|---|---|
| **PTOmni-FixedRoles** | 同样的专家能力、知识、Profile、记忆 | 团队角色/协作方式固定，不随阶段调整 | 动态团队是否必要？ |
| **PTOmni-StaticKnowledge** | 同样的知识文档、动态团队和评测 | 固定知识暴露方式，不随当前问题重新选择相关内容 | 动态知识暴露是否有效？ |
| **PTOmni-NoCurator** | 同样的真实历史、知识和 Profiling | 不用专门 Curator 蒸馏，改用普通历史摘要/固定历史窗口 | 专门的 Case Memory 是否有增量价值？ |
| **PTOmni-Full** | 全部机制 | 无 | 总体收益 |

可选的次要消融：`NoChallenger` 或 `RawProfile vs. StructuredProfile`，优先在代表性 Case 上完成，不必一开始全部扩展到主实验规模。

**注意**：StaticKnowledge **不是剥夺知识库**；NoCurator **不是剥夺全部历史**。对比只应该改变目标机制，而不是同时让变体失去基本信息。

### 12.4 主实验与指标

此前讨论的 **70–80 个 Case** 和每 Case **数十次硬件交互**可作为资源规划起点，正式规模与预算尚需按设备可用性和开发集试验确定，并对所有方法统一执行。

主要指标：

- Final Verified Speedup / 成功率；
- Best-so-far Speedup vs. Hardware Interaction Budget；
- 达到目标性能所需的交互次数；
- 端到端 Wall-clock、LLM Token / Cost；
- 正确性失败、重复/无效尝试以及回退情况。

机制相关分析：

- 跨 G/D/I 优化权衡的代表性 Case；
- 性能瓶颈变化前后 TeamPlan 的差异；
- Challenger 是否有效指出可验证的错误前提；
- Curator 记录的旧经验是否被后续决策真正使用。

### 12.5 实验公平性

- 采用 development / held-out Case 划分；
- 记录模型、Prompt、版本、知识访问、工具、Budget 和设备；
- 对正式 Benchmark 采用统一的 Warmup、重复次数、汇总统计；
- Profile 与 Clean Benchmark 分开；
- 每个 Baseline 和消融都受相同的正式硬件交互规则约束，并报告额外 Token/时间开销；
- 最终以独立干净工作空间验证结果为准。

## 13. 开发优先级与最小落地路线

### P0 — 先让可重复的多轮优化闭环可靠运行

- PTOBench Case Contract 与允许编辑范围清晰、强制执行；
- Owner 通过 Pi Session 可以持续提出方案、修改、验证；
- ProgramVersion、Attempt、Budget、Best 和 Event Ledger 能准确记录；
- Curator 能在每次正式尝试后生成 Round Note 与 Case Memory；
- 初始三源知识能按主题阅读；
- 最终 Candidate 可进行独立验证。

### P1 — 加入专业协作与最小 Profiling

- Supervisor + G/D/I/Hardware 动态 TeamPlan；
- Challenger 的明确触发和结构化建议；
- `profile_summary` / `profile_compare`；
- 关键事件触发 Replan；
- 收集代表性的跨机制优化轨迹。

### P2 — 仅在初步实验有效时再升级

- 更好的机会排序、Budget-aware Profiling 策略；
- 更复杂的多 Agent 并行探索或分支组合；
- 更深入的编译诊断数据；
- 更精细的在线知识召回与自动化评估。

**不建议第一版开发**：大型 Agent Framework、复杂 Role Registry、知识图谱、向量数据库、自研 Profiler、学习型 Controller、跨 Case 在线经验传播、复杂搜索 DAG。

## 14. 研究风险与必须验证的假设

| 风险 | 为什么重要 | 建议如何验证或应对 |
|---|---|---|
| 多 Agent 开销抵消性能收益 | 专家越多不一定越快 | 报告 Token、墙钟和硬件交互；默认最小团队 |
| G/D/I 只是 Prompt 标签 | 可能缺乏实质方法差异 | 用真实跨机制 Case 展示分工如何改变优化决策 |
| Challenger 无法减少错误尝试 | 容易沦为无意义的反对 | 只在关键事件调用；评估挑战是否导致有效验证或方向变化 |
| Curator 总结出错 | 错误经验会长期污染 Case Memory | 事实与解释分开、证据 ID 绑定、确定性状态兜底 |
| Profiling 采集影响测量 | 会产生错误加速判断 | 正式性能仅取 Clean Benchmark；Profile 只提供诊断证据 |
| 动态组队效果来自更多知识或预算 | 消融难以归因 | 固定角色/知识消融保持信息与预算尽量一致 |
| 知识与设备版本不匹配 | 错误资源判断会误导 Agent | Hardware Profile 与来源适用性检查 |
| 缺少真实跨层问题案例 | 故事可能流于概念 | 先做 2–3 个真实 Motivation Cases 与优化轨迹 |

### 尚待决定的具体实现参数

- Supervisor 在什么程度的停滞下触发重组；
- TeamPlan 每 Episode 的默认交互上限；
- 固定团队的具体角色配置；
- Curator 的 Memory 长度限制与过期/冲突处理；
- 目标 PyPTO/CANN 版本实际可用的 Profiling 产物；
- PTOBench 的最终统一预算、Case 划分和正式实验规模。

这些是应在 **development set** 上调试的工程参数，不需要此刻包装为方法贡献。

## 15. 最终定稿式总结

### PTOmni 的核心研究主张

> **Kernel optimization requires coordinating interdependent performance mechanisms. PTOmni dynamically organizes specialized agents around the current optimization problem, validates their hypotheses with hardware evidence, and distills per-round experience to adapt subsequent search and collaboration.**

### 系统最简版本

1. **Supervisor**：决定当前问题、团队、知识和下一步；
2. **Owner**：持续负责实施和正式验证；
3. **G/D/I/Hardware**：按机制与风险提供专业分析；
4. **Challenger**：必要时检查关键假设和副作用；
5. **Offline Knowledge**：保留三份硬件对齐原文，轻量检索；
6. **Profiling**：复用原生工具，输出 Summary / Compare；
7. **Curator**：每轮总结本 Case 经验并更新动态记忆；
8. **State + PTOBench**：保证正确性、可追溯性、公平性和预算；
9. **Adapt**：证据或约束变化时继续、调整团队或停止。

**一句话：PTOmni 不靠堆积 Agent 或工具取胜，而是让专业 Agent 围绕当前真正重要的 Kernel 性能问题协作，并根据每次真实实验的结果持续调整优化方向。**
